## Background

A money transfer is the textbook example of a transaction for a reason: it touches two rows at once, and there is no acceptable middle ground between "both updates happened" and "neither did." This project builds a minimal transfer system between two accounts and deliberately breaks it in the two ways real systems break: a failure mid-transfer, and two transfers racing against each other. You will fix both using the tools this unit covers.

## What You Will Build

A PostgreSQL `accounts` table and a transfer routine that moves money between two accounts safely, wrapped in transactions, with row locking to prevent lost updates.

```text
CREATE TABLE accounts (
    account_id   INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    owner_name   TEXT NOT NULL,
    balance      NUMERIC(12, 2) NOT NULL CHECK (balance >= 0)
);

CREATE TABLE transfers (
    transfer_id       UUID PRIMARY KEY,
    from_account_id   INTEGER NOT NULL REFERENCES accounts(account_id),
    to_account_id     INTEGER NOT NULL REFERENCES accounts(account_id),

);
```

## Tasks

### Task 1: A Safe Transfer

1. Write the transfer as an explicit transaction: `BEGIN`, deduct the amount from the sender, add it to the receiver, then `COMMIT`.

   ```text
   BEGIN;
   UPDATE accounts SET balance = balance - 2000 WHERE account_id = 1;
   UPDATE accounts SET balance = balance + 2000 WHERE account_id = 2;
   COMMIT;
   ```

Expected result: both balance changes commit together. The total balance across the two accounts remains unchanged, which confirms that the transfer moved money rather than creating or losing it.

2. Now try to transfer 10000 out of Rahul's account, an amount larger than his current balance can cover. The debit step (the first `UPDATE`, on Rahul's own row) would take his balance negative, so the `CHECK (balance >= 0)` constraint rejects it immediately and the whole transaction fails before the credit step ever runs. Confirm that Rahul's balance is completely unchanged afterward, not partially deducted, and explain which ACID property this demonstrates.
3. Run the same failing transfer again, but this time issue `ROLLBACK` explicitly after the error instead of letting the session hang. What state is the transaction left in if you try to run another statement before rolling back?

### Task 2: Two Transfers at Once

1. Explain, in your own words, the "lost update" problem: two transfers from the same account, both read the current balance before either writes back, and one update overwrites the other.
2. Rewrite the debit step using `SELECT balance FROM accounts WHERE account_id = 1 FOR UPDATE` before the `UPDATE`, so a second transaction touching the same row has to wait instead of reading a stale balance.
3. Look up PostgreSQL's default isolation level (`READ COMMITTED`) and `SERIALIZABLE`. Which one, on its own without `FOR UPDATE`, would still allow the lost update in step 1, and which one would detect and reject one of the two conflicting transactions?

### Task 3: Surviving a Crash

1. Add a `transfers` ledger table (already in the dataset above) that records every transfer with a unique `transfer_id` generated by the application, not the database.
2. Explain what Write-Ahead Logging guarantees if the database process crashes immediately after a client receives a "COMMIT successful" response, but before the underlying data files are flushed to disk.
3. Design your transfer function so that if the application retries a transfer after a crash or timeout, using the same `transfer_id` a second time does not double the money movement. Write the SQL check you would add at the start of the transfer to make this idempotent.

**Answer these questions after completing all tasks:**
- Task 1.2 relies on a `CHECK` constraint to stop an over-draft. If that constraint did not exist, would the transaction still fail on its own, or would it silently leave Rahul with a negative balance? What does this tell you about validating business rules in the database itself versus only in application code?
- `SELECT ... FOR UPDATE` in Task 2.2 makes a second concurrent transaction wait rather than fail outright. Is a transaction that waits and then succeeds a better or worse experience for a user than one that fails immediately and has to be retried?
- Your idempotency check in Task 3.3 depends on `transfer_id` being generated by the application before the request is sent, not by the database after. Why would generating it in the database (for example with `GENERATED ALWAYS AS IDENTITY`) break the whole idempotency design?
