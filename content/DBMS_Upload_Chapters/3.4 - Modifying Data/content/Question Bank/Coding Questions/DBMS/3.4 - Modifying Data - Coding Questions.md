# Modifying Data — Coding Question Bank

Dialect: **PostgreSQL**. Every statement in this bank has been executed against a live PostgreSQL 16 instance; every `Output`/`AFTER` state shown is the actual result, not a hand-typed guess. Because this chapter is about state changes rather than pure reads, most questions show a table's state **before** the statement and **after** it, so the effect of `INSERT`/`UPDATE`/`DELETE` is concrete and checkable.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the statement.
- **Bug Hunt** — a statement someone already wrote is shown along with its (wrong) effect; find and fix the mistake.
- **Predict the Output** — a statement is already written; state exactly what changes before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; write the better one and explain why.
- **Reverse Engineering** — you're shown the before/after state; work out the statement that caused it.
- **Decision-Making** — a concrete symptom or near-miss is shown; diagnose it and recommend a safer practice.

## Q4. A 10% Price Bump on Blouses

**Topic Tag:** UPDATE: Modifying Existing Rows Safely
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (multi-row update)

**Problem Statement**

A tailoring workshop is raising prices on all blouse orders by 10% to account for rising fabric costs. Before running the update, the shopkeeper wants to know exactly which rows change and what the new prices will be.

**Table: `tailoring_orders`**

| Column | Type | Description |
|---|---|---|
| `order_id` | INTEGER | Unique identifier (PK) |
| `customer_name` | VARCHAR(60) | Customer's name |
| `item_type` | VARCHAR(30) | Type of garment |
| `price` | DECIMAL(8,2) | Price in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE tailoring_orders (
    order_id INTEGER PRIMARY KEY,
    customer_name VARCHAR(60),
    item_type VARCHAR(30),
    price DECIMAL(8,2)
);

INSERT INTO tailoring_orders (order_id, customer_name, item_type, price) VALUES
(1, 'Anushka Sen', 'Blouse', 800.00),
(2, 'Karishma Vyas', 'Kurta', 1200.00),
(3, 'Neel Kashyap', 'Blouse', 950.00);
```

**Before**

```
+----------+---------------+-----------+---------+
| order_id | customer_name | item_type |  price  |
+----------+---------------+-----------+---------+
|        1 | Anushka Sen   | Blouse    |  800.00 |
|        2 | Karishma Vyas | Kurta     | 1200.00 |
|        3 | Neel Kashyap  | Blouse    |  950.00 |
+----------+---------------+-----------+---------+
```

**Query to Analyze**

```sql
UPDATE tailoring_orders
SET price = ROUND(price * 1.10, 2)
WHERE item_type = 'Blouse';
```

**Your Task:** Which rows change, and what are their new prices? Does Karishma Vyas's kurta change too?

**Answer**

```
+----------+---------------+-----------+---------+
| order_id | customer_name | item_type |  price  |
+----------+---------------+-----------+---------+
|        1 | Anushka Sen   | Blouse    |  880.00 |
|        2 | Karishma Vyas | Kurta     | 1200.00 |
|        3 | Neel Kashyap  | Blouse    | 1045.00 |
+----------+---------------+-----------+---------+
```

**Why:** Only the two `'Blouse'` rows match the `WHERE` clause, so only their `price` changes — ₹800.00 → ₹880.00 and ₹950.00 → ₹1045.00. Karishma's kurta at ₹1200.00 never matches `item_type = 'Blouse'`, so `UPDATE` never touches that row at all, exactly like `SELECT` would skip it.

```
+---------+-----------+---------+

|       2 | BK-102    | Retired |
```

## Q6. The Empty Food Bank

**Topic Tag:** DELETE: Removing Rows Without Accidents
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (missing WHERE)

**Problem Statement**

A food bank's inventory clerk wants to clear out only the items that expired before April 2026. Instead, every single item — fresh stock included — vanished from the inventory table.

**Table: `food_bank_inventory`**

| Column | Type | Description |
|---|---|---|
| `item_id` | INTEGER | Unique identifier (PK) |
| `item_name` | VARCHAR(60) | Item name |
| `expiry_date` | DATE | Expiry date |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE food_bank_inventory (
    item_id INTEGER PRIMARY KEY,
    item_name VARCHAR(60),
    expiry_date DATE
);

INSERT INTO food_bank_inventory (item_id, item_name, expiry_date) VALUES
(1, 'Rice 25kg Bag', '2026-08-01'),
(2, 'Canned Beans', '2026-03-10'),
(3, 'Milk Powder', '2026-09-15'),
(4, 'Cooking Oil 5L', '2026-03-05');
```

**Before**

```
+---------+----------------+-------------+
| item_id |   item_name    | expiry_date |
+---------+----------------+-------------+
|       1 | Rice 25kg Bag  | 2026-08-01  |
|       2 | Canned Beans   | 2026-03-10  |
|       3 | Milk Powder    | 2026-09-15  |
|       4 | Cooking Oil 5L | 2026-03-05  |
+---------+----------------+-------------+
```

**Buggy Query (as submitted)**

```sql
DELETE FROM food_bank_inventory;
```

**Buggy After**

```
+---------+-----------+-------------+
| item_id | item_name | expiry_date |
+---------+-----------+-------------+
+---------+-----------+-------------+
(0 rows — the entire inventory is gone)
```

**What's Wrong:** `DELETE FROM food_bank_inventory` has no `WHERE` clause at all, so it removes *every* row in the table — there's nothing in the statement limiting it to expired items. `DELETE` without `WHERE` is one of the most consequential mistakes in SQL: it silently and instantly clears the whole table.

**Solution Query (Fixed)**

```sql
DELETE FROM food_bank_inventory
WHERE expiry_date < '2026-04-01';
```

**Fixed After**

```
+---------+---------------+-------------+
| item_id |   item_name   | expiry_date |
+---------+---------------+-------------+
|       1 | Rice 25kg Bag | 2026-08-01  |
|       3 | Milk Powder   | 2026-09-15  |
+---------+---------------+-------------+
(only the two expired items — Canned Beans and Cooking Oil 5L — were removed)
```

## Q9. Renewing a Membership in One Step

**Topic Tag:** UPSERT and ON CONFLICT: Insert or Update in One Step
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Transform (upsert)

**Problem Statement**

A co-op bookstore's membership desk wants a single statement that works whether a member is renewing (row already exists) or joining fresh (row doesn't exist yet) — no need to check first and branch in application code. Devika Rane, an existing member, is renewing for another year.

|---|---|---|
| `member_id` | INTEGER | Unique identifier (PK) |
| `member_name` | VARCHAR(60) | Member's name |
| `expiry_date` | DATE | Membership expiry date |

Write a statement that inserts `(1, 'Devika Rane', '2027-01-31')`, but if `member_id` 1 already exists, updates its `expiry_date` to the new value instead.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE coop_memberships (
    member_id INTEGER PRIMARY KEY,
    member_name VARCHAR(60),
    expiry_date DATE
);

INSERT INTO coop_memberships (member_id, member_name, expiry_date) VALUES
(1, 'Devika Rane', '2026-01-31'),
(2, 'Yash Thakur', '2026-02-28');
```

**Before**

```
+-----------+-------------+-------------+
| member_id | member_name | expiry_date |
+-----------+-------------+-------------+
|         1 | Devika Rane | 2026-01-31  |
|         2 | Yash Thakur | 2026-02-28  |
+-----------+-------------+-------------+
```

**Solution Query**

```sql
INSERT INTO coop_memberships (member_id, member_name, expiry_date)

DO UPDATE SET expiry_date = EXCLUDED.expiry_date;
```

```
+-----------+-------------+-------------+
| member_id | member_name | expiry_date |
+-----------+-------------+-------------+
|         1 | Devika Rane | 2027-01-31  |
|         2 | Yash Thakur | 2026-02-28  |
+-----------+-------------+-------------+
```

*(No new row was created — the existing row for `member_id` 1 was updated in place, since it conflicted with the primary key.)*

## Q10. Look Before You Delete

**Topic Tag:** Why Modification Needs Discipline?
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Decision-making

**Problem Statement**

A veterinary pharmacy's stock manager is about to run `DELETE FROM vet_pharmacy_stock WHERE expiry_date < '2026-04-01';` to clear expired medicine. Before actually deleting anything, they want to preview exactly which rows would be removed.

**Table: `vet_pharmacy_stock`**

| Column | Type | Description |
|---|---|---|
| `stock_id` | INTEGER | Unique identifier (PK) |
| `medicine_name` | VARCHAR(60) | Medicine name |
| `expiry_date` | DATE | Expiry date |
| `quantity` | INTEGER | Units in stock |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE vet_pharmacy_stock (
    stock_id INTEGER PRIMARY KEY,
    medicine_name VARCHAR(60),
    expiry_date DATE,
    quantity INTEGER
);

INSERT INTO vet_pharmacy_stock (stock_id, medicine_name, expiry_date, quantity) VALUES
(1, 'Amoxicillin Vet 250mg', '2026-03-20', 40),
(2, 'Meloxicam Oral Susp', '2026-06-10', 15),
(3, 'Deworming Tablets', '2026-03-25', 60);
```

**Your Task:** Write the `SELECT` that previews exactly which rows the planned `DELETE` would remove, before it's actually run — and explain why this habit is worth the extra step.

**Solution Query**

```sql
SELECT *
FROM vet_pharmacy_stock
WHERE expiry_date < '2026-04-01';
```

**Output**

```
+----------+-----------------------+-------------+----------+
| stock_id |     medicine_name     | expiry_date | quantity |
+----------+-----------------------+-------------+----------+
|        1 | Amoxicillin Vet 250mg | 2026-03-20  |       40 |
|        3 | Deworming Tablets     | 2026-03-25  |       60 |
+----------+-----------------------+-------------+----------+
```

**Justification:** A `SELECT` with the *exact same* `WHERE` clause the `DELETE` will use costs nothing and destroys nothing — it shows precisely which rows and how many are about to disappear, before the point of no return. If the row count or the rows themselves look wrong (too many, too few, the wrong medicines), that's the moment to catch a typo'd date or a missing condition — not after the data is already gone. This is exactly the discipline that would have caught Q6's missing-`WHERE` disaster before it happened.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE episode_subscribers (
    episode_id INTEGER PRIMARY KEY,
    episode_title VARCHAR(80),
    subscriber_count INTEGER
);

INSERT INTO episode_subscribers (episode_id, episode_title, subscriber_count) VALUES
(1, 'Episode 12: Startup Lessons', 340);
```

```
+------------+-----------------------------+------------------+
| episode_id |        episode_title        | subscriber_count |
+------------+-----------------------------+------------------+
|          1 | Episode 12: Startup Lessons |              340 |
+------------+-----------------------------+------------------+
```

```sql
INSERT INTO episode_subscribers (episode_id, episode_title, subscriber_count)
```

```
+------------+-----------------------------+------------------+
```

*(Notice the count went to 341, not 1 — `ON CONFLICT DO UPDATE` let the update reference the row's existing value via `episode_subscribers.subscriber_count`, rather than the incoming `1` simply overwriting it.)*

## Q26. The Reservation That Went Nowhere

**Topic Tag:** UPSERT and ON CONFLICT: Insert or Update in One Step
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (`DO NOTHING` vs `DO UPDATE`)

**Problem Statement**

A restaurant's reservation system lets a new booking silently replace an old one on the same table, on the theory that whoever books last gets the table. Table 5 was booked by Ankush Verma; when Lavanya Iyer books the same table for a different time, her reservation vanishes — the system still shows Ankush's original booking, completely unaware Lavanya even tried.

**Table: `table_reservations`**

| Column | Type | Description |
|---|---|---|
| `table_number` | INTEGER | Unique identifier (PK) |
| `reserved_by` | VARCHAR(60) | Name of the person who reserved it |
| `reservation_time` | TIME | Reservation time |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE table_reservations (
    table_number INTEGER PRIMARY KEY,
    reserved_by VARCHAR(60),
    reservation_time TIME
);

INSERT INTO table_reservations (table_number, reserved_by, reservation_time) VALUES
(5, 'Ankush Verma', '19:00');
```

**Before**

```
+--------------+--------------+-------------------+
| table_number | reserved_by  | reservation_time  |
+--------------+--------------+-------------------+
|            5 | Ankush Verma | 19:00:00          |
+--------------+--------------+-------------------+
```

**Buggy Query (as submitted)**

```sql
INSERT INTO table_reservations (table_number, reserved_by, reservation_time)
VALUES (5, 'Lavanya Iyer', '20:30')
ON CONFLICT (table_number) DO NOTHING;
```

**Buggy After**

```
+--------------+--------------+-------------------+
| table_number | reserved_by  | reservation_time  |
+--------------+--------------+-------------------+
|            5 | Ankush Verma | 19:00:00          |
+--------------+--------------+-------------------+
(unchanged — Lavanya's booking silently disappeared, with no error at all)
```

**What's Wrong:** `DO NOTHING` means exactly what it says — on a conflict, the statement quietly gives up and leaves the existing row untouched, discarding the new values entirely and without so much as a warning. That's the opposite of what's needed here: table 5's booking should be *replaced* with Lavanya's details, not preserved as Ankush's.

**Solution Query (Fixed)**

```sql
INSERT INTO table_reservations (table_number, reserved_by, reservation_time)
VALUES (5, 'Lavanya Iyer', '20:30')
ON CONFLICT (table_number)
DO UPDATE SET reserved_by = EXCLUDED.reserved_by, reservation_time = EXCLUDED.reservation_time;
```

**Fixed After**

```
+--------------+--------------+-------------------+
| table_number | reserved_by  | reservation_time  |
+--------------+--------------+-------------------+
|            5 | Lavanya Iyer | 20:30:00          |
+--------------+--------------+-------------------+
```

## Q27. Only If It's a New Best

**Topic Tag:** UPSERT and ON CONFLICT: Insert or Update in One Step
**Difficulty:** Hard
**Type:** Reverse Engineering
**Skill Focus:** Reconstruct

**Problem Statement**

A video game's high score board should only overwrite a player's stored best score if their new run actually beats it — never overwrite with a lower score. Player NovaBlade's stored best was 8800; after their latest run scored 9600, the board correctly updated. Work out the single upsert statement that guarantees this "only if higher" behavior, not just an unconditional overwrite.

**Table: `high_scores`**

| Column | Type | Description |
|---|---|---|
| `player_id` | INTEGER | Unique identifier (PK) |
| `player_name` | VARCHAR(40) | Player's handle |
| `best_score` | INTEGER | Best score recorded so far |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE high_scores (
    player_id INTEGER PRIMARY KEY,
    player_name VARCHAR(40),
    best_score INTEGER
);

INSERT INTO high_scores (player_id, player_name, best_score) VALUES
(1, 'NovaBlade', 8800);
```

**Before**

```
+-----------+-------------+------------+
| player_id | player_name | best_score |
+-----------+-------------+------------+
|         1 | NovaBlade   |       8800 |
+-----------+-------------+------------+
```

**Target After (run scored 9600)**

```
+-----------+-------------+------------+
| player_id | player_name | best_score |
+-----------+-------------+------------+
|         1 | NovaBlade   |       9600 |
+-----------+-------------+------------+
```

**Your Task:** Write the upsert statement for this run — and make sure it would correctly do *nothing* to `best_score` if a future run scored, say, 9000 instead (lower than 9600).

**Solution Query**

```sql
INSERT INTO high_scores (player_id, player_name, best_score)
VALUES (1, 'NovaBlade', 9600)
ON CONFLICT (player_id)
DO UPDATE SET best_score = GREATEST(high_scores.best_score, EXCLUDED.best_score);
```

*`GREATEST(...)` compares the existing stored value against the incoming one and keeps whichever is larger — so a future 9000-point run would leave `best_score` at 9600, untouched, instead of incorrectly overwriting a genuine best with a worse score.*

## Q29. Test the Delete Before You Trust It

**Topic Tag:** Why Modification Needs Discipline?
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Decision-making (transactions as a safety net)

**Problem Statement**

A payroll clerk needs to remove duplicate disbursement log entries before month-end reconciliation. Rather than running `DELETE FROM payroll_log WHERE status = 'Duplicate';` directly and hoping it's right, they want to see its effect first and still be able to back out if the result looks wrong.

**Table: `payroll_log`**

| Column | Type | Description |
|---|---|---|
| `log_id` | INTEGER | Unique identifier (PK) |
| `employee_name` | VARCHAR(60) | Employee's name |
| `disbursed_amount` | DECIMAL(10,2) | Amount disbursed in ₹ |
| `status` | VARCHAR(20) | Confirmed / Duplicate |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE payroll_log (
    log_id INTEGER PRIMARY KEY,
    employee_name VARCHAR(60),
    disbursed_amount DECIMAL(10,2),
    status VARCHAR(20)
);

INSERT INTO payroll_log (log_id, employee_name, disbursed_amount, status) VALUES
(1, 'Chetan Oza', 45000.00, 'Duplicate'),
(2, 'Farah Engineer', 52000.00, 'Confirmed'),
(3, 'Ibrahim Qazi', 45000.00, 'Duplicate');
```

**Before**

```
+--------+----------------+------------------+-----------+
| log_id | employee_name  | disbursed_amount |  status   |
+--------+----------------+------------------+-----------+
|      1 | Chetan Oza     |         45000.00 | Duplicate |
|      2 | Farah Engineer |         52000.00 | Confirmed |
|      3 | Ibrahim Qazi   |         45000.00 | Duplicate |
+--------+----------------+------------------+-----------+
```

**Your Task:** Write a sequence that lets the clerk run the `DELETE`, inspect the result, and still safely undo it if something looks off — versus just running the bare `DELETE` and hoping for the best.

**Solution Query**

```sql
BEGIN;

DELETE FROM payroll_log WHERE status = 'Duplicate';

SELECT * FROM payroll_log ORDER BY log_id;
-- inspect the result here — if it looks wrong, ROLLBACK instead of COMMIT

ROLLBACK;  -- or COMMIT; once the result is confirmed correct
```

**State Inside the Transaction (before rollback)**

```
+--------+----------------+------------------+-----------+
| log_id | employee_name  | disbursed_amount |  status   |
+--------+----------------+------------------+-----------+
|      2 | Farah Engineer |         52000.00 | Confirmed |
+--------+----------------+------------------+-----------+
```

**State After ROLLBACK**

```
+--------+----------------+------------------+-----------+
| log_id | employee_name  | disbursed_amount |  status   |
+--------+----------------+------------------+-----------+
|      1 | Chetan Oza     |         45000.00 | Duplicate |
|      2 | Farah Engineer |         52000.00 | Confirmed |
|      3 | Ibrahim Qazi   |         45000.00 | Duplicate |
+--------+----------------+------------------+-----------+
```

**Justification:** Wrapping the `DELETE` in `BEGIN` means nothing is permanently committed until an explicit `COMMIT` — the clerk can run the `DELETE`, immediately `SELECT` the table to confirm exactly two duplicate rows disappeared and Farah Engineer's confirmed payment is untouched, and if anything looked wrong, `ROLLBACK` undoes it completely, as if it never ran. A bare `DELETE` outside a transaction offers no such checkpoint — once it executes, the only way back is a full database restore.

## Q30. A Near-Miss on the Support Desk

**Topic Tag:** Why Modification Needs Discipline?
**Difficulty:** Hard
**Type:** Decision-Making
**Skill Focus:** Decision-making

**Problem Statement**

A support engineer meant to write `DELETE FROM support_tickets WHERE status = 'Closed';` to purge old closed tickets, but copy-pasted from a Slack message and almost ran a version with the `WHERE` clause accidentally commented out. A teammate caught it in code review before it ran. The team has asked you to recommend concrete guardrails so this kind of near-miss doesn't turn into an actual incident next time.

**Table: `support_tickets`**

| Column | Type | Description |
|---|---|---|
| `ticket_id` | INTEGER | Unique identifier (PK) |
| `customer_name` | VARCHAR(60) | Customer's name |
| `status` | VARCHAR(20) | Open / Closed |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE support_tickets (
    ticket_id INTEGER PRIMARY KEY,
    customer_name VARCHAR(60),
    status VARCHAR(20)
);

INSERT INTO support_tickets (ticket_id, customer_name, status) VALUES
(1, 'Devansh Oswal', 'Closed'),
(2, 'Meher Chawla', 'Open'),
(3, 'Yashvi Doshi', 'Closed');
```

**Your Task:** What concrete practices would you recommend so a near-miss like this can't slip through to production next time?

**Answer:** A single safeguard almost never catches everything — the value is in layering a few:

1. **Preview before you commit** — always run the equivalent `SELECT` (or wrap the statement in `BEGIN` and inspect the result, as in Q29) before trusting a `DELETE`/`UPDATE`, exactly the habit that would have shown "this affects all 3 rows, not 2" immediately.
2. **Never run destructive statements copy-pasted from chat without re-reading them in the editor** — a comment stripped or added in transit is invisible in a chat window but glaring once pasted into a SQL client with syntax highlighting.
3. **Code review for anything destructive**, exactly as happened here — a second set of eyes is precisely what caught this before it ran, which means the process already worked; the fix is making sure that review step is *mandatory*, not something a rushed engineer can skip.
4. **Prefer transactions for anything irreversible**, so even a review miss still leaves a `ROLLBACK` escape hatch before `COMMIT`.

None of these guarantee safety alone; together, they mean a single slip (a bad paste, a missed review, a forgotten preview) isn't enough on its own to cause real damage.

**Verification Query**

```sql
SELECT * FROM support_tickets WHERE status = 'Closed';
```

**Output**

```
+-----------+---------------+--------+
| ticket_id | customer_name | status |
+-----------+---------------+--------+
|         1 | Devansh Oswal | Closed |
|         3 | Yashvi Doshi  | Closed |
+-----------+---------------+--------+
```
