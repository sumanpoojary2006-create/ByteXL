## Q1. The Daily Total, on Every Row

**Topic Tag:** What is a Window Function?
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Summarize (without collapsing rows)

**Problem Statement**

An e-commerce dashboard wants each day's sales figure shown *alongside* the overall total sales for the period — every row keeps its own detail, but also carries the grand total for context, without collapsing the daily rows into one summary row the way `GROUP BY` would.

**Table: `daily_sales`**

| Column | Type | Description |
|---|---|---|
| `sale_id` | INTEGER | Unique identifier (PK) |
| `sale_date` | DATE | Date of sales |
| `amount` | DECIMAL(10,2) | Sales amount in ₹ |

Write a query that returns `sale_date`, `amount`, and `total_sales`, where `total_sales` is the sum of `amount` across every row.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE daily_sales (
    sale_id INTEGER PRIMARY KEY,
    sale_date DATE,
    amount DECIMAL(10,2)
);

INSERT INTO daily_sales (sale_id, sale_date, amount) VALUES
(1, '2026-03-01', 12000.00),
(2, '2026-03-02', 9500.00),
(3, '2026-03-03', 14200.00);
```

**Output**

```
+------------+----------+--------------+
| sale_date  |  amount  | total_sales  |
+------------+----------+--------------+
| 2026-03-01 | 12000.00 |     35700.00 |
| 2026-03-02 |  9500.00 |     35700.00 |
| 2026-03-03 | 14200.00 |     35700.00 |
+------------+----------+--------------+
```

**Solution Query**

```sql
SELECT sale_date, amount, SUM(amount) OVER () AS total_sales
FROM daily_sales
ORDER BY sale_date;
```

*This is the essential difference between a window function and `GROUP BY`: `SUM(amount) OVER ()` still returns one row per input row, each one carrying the same grand total, rather than collapsing all three days into a single summary row.*

## Q2. Average Temperature per Station, on Every Reading

**Topic Tag:** OVER, PARTITION BY, and ORDER BY
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Summarize (per group, without collapsing)

**Problem Statement**

A weather network wants each individual reading shown alongside that specific station's average temperature — not the average across all stations, and not collapsed into one row per station.

**Table: `station_readings`**

| Column | Type | Description |
|---|---|---|
| `reading_id` | INTEGER | Unique identifier (PK) |
| `station_name` | VARCHAR(40) | Station name |
| `temperature` | DECIMAL(4,1) | Temperature reading in °C |

Write a query that returns `station_name`, `temperature`, and `station_avg`, the average temperature for that specific station, rounded to 2 decimals.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE station_readings (
    reading_id INTEGER PRIMARY KEY,
    station_name VARCHAR(40),
    temperature DECIMAL(4,1)
);

INSERT INTO station_readings (reading_id, station_name, temperature) VALUES
(1, 'Ridgeview', 28.5), (2, 'Ridgeview', 31.0), (3, 'Coastal', 24.0), (4, 'Coastal', 26.0);
```

**Output**

```
+---------------+--------------+--------------+
| station_name  | temperature  | station_avg  |
+---------------+--------------+--------------+
| Coastal       |         24.0 |        25.00 |
| Coastal       |         26.0 |        25.00 |
| Ridgeview     |         28.5 |        29.75 |
| Ridgeview     |         31.0 |        29.75 |
+---------------+--------------+--------------+
```

**Solution Query**

```sql
SELECT station_name, temperature, ROUND(AVG(temperature) OVER (PARTITION BY station_name), 2) AS station_avg
FROM station_readings
ORDER BY station_name, temperature;
```

*`PARTITION BY station_name` splits the rows into separate groups for the calculation — each row's `station_avg` only ever considers rows sharing that same station, the same way `GROUP BY` would, except every original row survives instead of being collapsed.*

## Q3. Two Averages, Side by Side

**Topic Tag:** OVER, PARTITION BY, and ORDER BY
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (partitioned vs. unpartitioned)

**Problem Statement**

A portfolio tracker computes two different averages for the same stock price rows: one partitioned by stock symbol, one not partitioned at all. Before running it, predict how these two columns will differ from each other.

**Table: `stock_prices`**

| Column | Type | Description |
|---|---|---|
| `price_id` | INTEGER | Unique identifier (PK) |
| `stock_symbol` | VARCHAR(10) | Stock ticker |
| `price` | DECIMAL(10,2) | Price in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE stock_prices (
    price_id INTEGER PRIMARY KEY,
    stock_symbol VARCHAR(10),
    price DECIMAL(10,2)
);

INSERT INTO stock_prices (price_id, stock_symbol, price) VALUES
(1, 'TATA', 3200.00), (2, 'TATA', 3400.00), (3, 'INFY', 1500.00), (4, 'INFY', 1700.00);
```

**Query to Analyze**

```sql
SELECT stock_symbol, price,
    ROUND(AVG(price) OVER (PARTITION BY stock_symbol), 2) AS symbol_avg,
    ROUND(AVG(price) OVER (), 2) AS overall_avg
FROM stock_prices;
```

**Your Task:** Will `symbol_avg` be the same value on every row? Will `overall_avg`?

**Answer**

```
+---------------+---------+-------------+---------------+
| stock_symbol  |  price  | symbol_avg  |  overall_avg  |
+---------------+---------+-------------+---------------+
| INFY          | 1500.00 |     1600.00 |       2450.00 |
| INFY          | 1700.00 |     1600.00 |       2450.00 |
| TATA          | 3200.00 |     3300.00 |       2450.00 |
| TATA          | 3400.00 |     3300.00 |       2450.00 |
+---------------+---------+-------------+---------------+
```

**Why:** `overall_avg` uses `OVER ()` with no `PARTITION BY` — every row belongs to one single, unpartitioned window covering the whole table, so all four rows show the identical value, ₹2450.00. `symbol_avg` uses `OVER (PARTITION BY stock_symbol)` — each row only "sees" other rows sharing its own symbol, so INFY's two rows both show ₹1600.00 while TATA's two rows both show ₹3300.00. Omitting `PARTITION BY` doesn't mean "no grouping happens" — it means "the whole table is one partition."

## Q5. Wait Times That Aren't Really Tied

**Topic Tag:** Ranking Functions
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (ROW_NUMBER hiding a genuine tie)

**Problem Statement**

An ER triage board ranks patients by how long they've waited, longest first. Two patients have waited *exactly* the same time — the board should show that clearly, but the query currently assigns them different-looking positions, implying one has waited longer than the other when they haven't.

**Table: `er_wait_times`**

| Column | Type | Description |
|---|---|---|
| `patient_id` | INTEGER | Unique identifier (PK) |
| `patient_name` | VARCHAR(60) | Patient's name |
| `wait_minutes` | INTEGER | Minutes waited so far |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE er_wait_times (
    patient_id INTEGER PRIMARY KEY,
    patient_name VARCHAR(60),
    wait_minutes INTEGER
);

INSERT INTO er_wait_times (patient_id, patient_name, wait_minutes) VALUES
(1, 'Harish Bhandari', 45), (2, 'Ismat Fatima', 60), (3, 'Preeti Saxena', 60), (4, 'Tarun Grover', 30);
```

**Buggy Query (as submitted)**

```sql
SELECT patient_name, wait_minutes, ROW_NUMBER() OVER (ORDER BY wait_minutes DESC) AS wait_rank
FROM er_wait_times
ORDER BY wait_rank;
```

**Buggy Output**

```
+-----------------+---------------+-----------+
|  patient_name   | wait_minutes  | wait_rank |
+-----------------+---------------+-----------+
| Ismat Fatima    |            60 |         1 |
| Preeti Saxena   |            60 |         2 |
| Harish Bhandari |            45 |         3 |
| Tarun Grover    |            30 |         4 |
+-----------------+---------------+-----------+
(Ismat Fatima and Preeti Saxena waited the exact same 60 minutes, but show as rank 1 and 2)
```

**What's Wrong:** `ROW_NUMBER()` always assigns a unique, strictly increasing number to every row, breaking ties by arbitrary row order — it has no concept of "these two rows are equally ranked." For a triage board where a genuine tie should be visible, `ROW_NUMBER()` manufactures a false distinction between two patients who have waited identically long.

**Solution Query (Fixed)**

```sql
SELECT patient_name, wait_minutes, RANK() OVER (ORDER BY wait_minutes DESC) AS wait_rank
FROM er_wait_times
ORDER BY wait_rank;
```

**Fixed Output**

```
+-----------------+---------------+-----------+
|  patient_name   | wait_minutes  | wait_rank |
+-----------------+---------------+-----------+
| Ismat Fatima    |            60 |         1 |
| Preeti Saxena   |            60 |         1 |
| Harish Bhandari |            45 |         3 |
| Tarun Grover    |            30 |         4 |
+-----------------+---------------+-----------+
```

*`RANK()` gives tied rows the same rank, and correctly skips ahead afterward (rank 3, not 2) to reflect that two patients hold rank 1 — an honest representation of the tie, unlike `ROW_NUMBER()`'s forced ordering.*

## Q6. Comparing Consecutive Game Sessions

**Topic Tag:** Offset Functions: LAG and LEAD
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Compare Values (row-to-row)

**Problem Statement**

A gaming platform wants each player's score shown alongside their *previous* session's score, to compute improvement over time.

**Table: `game_sessions`**

| Column | Type | Description |
|---|---|---|
| `session_id` | INTEGER | Unique identifier (PK) |
| `player_name` | VARCHAR(40) | Player's name |
| `session_date` | DATE | Date of the session |
| `score` | INTEGER | Score achieved |

Write a query that returns `player_name`, `session_date`, `score`, and `previous_score`, the player's score from their prior session.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE game_sessions (
    session_id INTEGER PRIMARY KEY,
    player_name VARCHAR(40),
    session_date DATE,
    score INTEGER
);

INSERT INTO game_sessions (session_id, player_name, session_date, score) VALUES
(1, 'NovaBlade', '2026-03-01', 8200),
(2, 'NovaBlade', '2026-03-02', 8900),
(3, 'NovaBlade', '2026-03-03', 8600);
```

**Output**

```
+--------------+---------------+--------+-----------------+
| player_name  | session_date  | score  | previous_score  |
+--------------+---------------+--------+-----------------+
| NovaBlade    | 2026-03-01    |   8200 |          ¤NULL¤ |
| NovaBlade    | 2026-03-02    |   8900 |            8200 |
| NovaBlade    | 2026-03-03    |   8600 |            8900 |
+--------------+---------------+--------+-----------------+
```

**Solution Query**

```sql
SELECT player_name, session_date, score,
    LAG(score) OVER (PARTITION BY player_name ORDER BY session_date) AS previous_score
FROM game_sessions
ORDER BY session_date;
```

*`LAG()` reaches back one row within the ordering — the very first session for a player has nothing before it, so `previous_score` is `NULL` there, exactly like a first-row edge case anywhere else in SQL.*

## Q7. Month-over-Month Revenue

**Topic Tag:** Offset Functions: LAG and LEAD
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (LAG's first-row NULL)

**Problem Statement**

A subscription business tracks monthly revenue and wants each month shown next to the *previous* month's figure. Before running it, predict what happens for the very first month in the data.

**Table: `monthly_revenue`**

| Column | Type | Description |
|---|---|---|
| `month_start` | DATE | First day of the month (PK) |
| `revenue` | DECIMAL(10,2) | Revenue for that month in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE monthly_revenue (
    month_start DATE PRIMARY KEY,
    revenue DECIMAL(10,2)
);

INSERT INTO monthly_revenue (month_start, revenue) VALUES
('2026-01-01', 40000.00), ('2026-02-01', 45000.00), ('2026-03-01', 42000.00);
```

**Query to Analyze**

```sql
SELECT month_start, revenue, LAG(revenue) OVER (ORDER BY month_start) AS previous_month_revenue
FROM monthly_revenue
ORDER BY month_start;
```

**Your Task:** What does `previous_month_revenue` show for January, the earliest month in the data?

**Answer**

```
+--------------+----------+-------------------------+
| month_start  | revenue  | previous_month_revenue  |
+--------------+----------+-------------------------+
| 2026-01-01   | 40000.00 |                  ¤NULL¤ |
| 2026-02-01   | 45000.00 |                40000.00 |
| 2026-03-01   | 42000.00 |                45000.00 |
+--------------+----------+-------------------------+
```

**Why:** `LAG(revenue)` looks one row back in the `ORDER BY month_start` sequence. ## Q8. Running Distance per Driver

**Topic Tag:** Running Totals, Moving Averages, and Window Frames
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Summarize (running total)

**Problem Statement**

A delivery company wants each driver's cumulative distance covered so far this week, updating with every new route logged.

**Table: `driver_routes`**

| Column | Type | Description |
|---|---|---|
| `route_id` | INTEGER | Unique identifier (PK) |
| `driver_name` | VARCHAR(40) | Driver's name |
| `route_date` | DATE | Date of the route |
| `distance_km` | DECIMAL(6,1) | Distance covered in km |

Write a query that returns `driver_name`, `route_date`, `distance_km`, and `running_distance`, the cumulative distance for that driver up to and including that date.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE driver_routes (
    route_id INTEGER PRIMARY KEY,
    driver_name VARCHAR(40),
    route_date DATE,
    distance_km DECIMAL(6,1)
);

INSERT INTO driver_routes (route_id, driver_name, route_date, distance_km) VALUES
(1, 'Suresh Yadav', '2026-03-01', 40.0),
(2, 'Suresh Yadav', '2026-03-02', 35.0),
(3, 'Suresh Yadav', '2026-03-03', 50.0);
```

**Output**

```
+--------------+------------+-------------+-------------------+
| driver_name  | route_date | distance_km | running_distance  |
+--------------+------------+-------------+-------------------+
| Suresh Yadav | 2026-03-01 |        40.0 |              40.0 |
| Suresh Yadav | 2026-03-02 |        35.0 |              75.0 |
| Suresh Yadav | 2026-03-03 |        50.0 |             125.0 |
+--------------+------------+-------------+-------------------+
```

**Solution Query**

```sql
SELECT driver_name, route_date, distance_km,
    SUM(distance_km) OVER (PARTITION BY driver_name ORDER BY route_date) AS running_distance
FROM driver_routes
ORDER BY route_date;
```

*Adding `ORDER BY route_date` inside the `OVER (...)` clause is what turns a plain per-driver total (like Q2's average) into a *running* total — each row's window now only includes rows up to and including itself, in date order.*

## Q9. A Running Total with a Hidden Tie

**Topic Tag:** Running Totals, Moving Averages, and Window Frames
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Compare Values (RANGE vs. ROWS frame)

**Problem Statement**

Two employees earned the exact same commission this month. A payroll query computes a running total ordered by commission amount — one version leaves the frame unspecified (the default), another explicitly says `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. They give *different* answers for the tied employees, and you've been asked to explain why and recommend which one payroll should actually use.

**Table: `commissions`**

| Column | Type | Description |
|---|---|---|
| `emp_id` | INTEGER | Unique identifier (PK) |
| `emp_name` | VARCHAR(60) | Employee's name |
| `commission` | DECIMAL(8,2) | Commission earned in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE commissions (
    emp_id INTEGER PRIMARY KEY,
    emp_name VARCHAR(60),
    commission DECIMAL(8,2)
);

INSERT INTO commissions (emp_id, emp_name, commission) VALUES
(1, 'Ashwin Bhat', 5000.00),
(2, 'Leena Fernandes', 5000.00),
(3, 'Mohit Saxena', 7000.00);
```

**Default (RANGE) Frame**

```sql
SELECT emp_name, commission, SUM(commission) OVER (ORDER BY commission) AS running_total
FROM commissions
ORDER BY commission, emp_name;
```

```
+-----------------+-------------+----------------+
|    emp_name     | commission  | running_total  |
+-----------------+-------------+----------------+
| Ashwin Bhat     |    5000.00  |      10000.00  |
| Leena Fernandes |    5000.00  |      10000.00  |
| Mohit Saxena    |    7000.00  |      17000.00  |
+-----------------+-------------+----------------+
```

**Explicit ROWS Frame**

```sql
SELECT emp_name, commission,
    SUM(commission) OVER (ORDER BY commission ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM commissions
ORDER BY commission, emp_name;
```

```
+-----------------+-------------+----------------+
|    emp_name     | commission  | running_total  |
+-----------------+-------------+----------------+
| Ashwin Bhat     |    5000.00  |       5000.00  |
| Leena Fernandes |    5000.00  |      10000.00  |
| Mohit Saxena    |    7000.00  |      17000.00  |
+-----------------+-------------+----------------+
```

**Justification:** When `ORDER BY` is present but no frame is specified, PostgreSQL's default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — and critically, `RANGE` groups all rows with an *equal* `ORDER BY` value into the same logical position, including *all* of them in each tied row's total. That's why both ₹5000 earners show ₹10000.00 — each one's window already includes the other, since they're tied. `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` instead counts strictly by physical row position, giving Ashwin Bhat (processed first) just his own ₹5000, and Leena Fernandes ₹10000 once she's added. For a genuine "running total as of this exact row," `ROWS` is almost always what's intended — `RANGE`'s tie-grouping behavior is a frequent source of unexpected running-total values whenever the `ORDER BY` column can repeat, so payroll should standardize on the explicit `ROWS` version.

## Q10. The Two Busiest Days per Store

**Topic Tag:** Top-N Per Group
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Rank (per group)

**Problem Statement**

A retail chain wants the two busiest days (by visitor count) for each store, to staff those days more heavily next time.

**Table: `store_visits`**

| Column | Type | Description |
|---|---|---|
| `visit_id` | INTEGER | Unique identifier (PK) |
| `store_name` | VARCHAR(40) | Store name |
| `visit_date` | DATE | Date of the visit log |
| `visitor_count` | INTEGER | Visitors that day |

Write a query that returns `store_name`, `visit_date`, and `visitor_count` for each store's top 2 busiest days.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE store_visits (
    visit_id INTEGER PRIMARY KEY,
    store_name VARCHAR(40),
    visit_date DATE,
    visitor_count INTEGER
);

INSERT INTO store_visits (visit_id, store_name, visit_date, visitor_count) VALUES
(1, 'Downtown Store', '2026-03-01', 320),
(2, 'Downtown Store', '2026-03-02', 410),
(3, 'Downtown Store', '2026-03-03', 280),
(4, 'Mall Store', '2026-03-01', 500),
(5, 'Mall Store', '2026-03-02', 150);
```

**Output**

```
+------------------+---------------+----------------+
|   store_name     | visit_date    | visitor_count  |
+------------------+---------------+----------------+
| Downtown Store   | 2026-03-02    |            410 |
| Downtown Store   | 2026-03-01    |            320 |
| Mall Store       | 2026-03-01    |            500 |
| Mall Store       | 2026-03-02    |            150 |
+------------------+---------------+----------------+
```

**Solution Query**

```sql
WITH ranked_visits AS (
    SELECT store_name, visit_date, visitor_count,
        ROW_NUMBER() OVER (PARTITION BY store_name ORDER BY visitor_count DESC) AS rn
    FROM store_visits
)
SELECT store_name, visit_date, visitor_count
FROM ranked_visits
WHERE rn <= 2
ORDER BY store_name, visitor_count DESC;
```

*Window functions can't be referenced directly in a `WHERE` clause (`WHERE rn <= 2` would fail if written inline), because `WHERE` is evaluated before window functions are computed — wrapping the ranked result in a CTE and filtering the *outer* query is the standard pattern for "top-N per group."*

## Q21. Filling In the Missing Previous Price

**Topic Tag:** Offset Functions: LAG and LEAD
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values (LAG's default argument vs. COALESCE)

**Problem Statement**

A real-estate price tracker computes each listing's price change from the prior entry. For the very first price record on a listing, there's no earlier price to compare against. One approach uses `LAG`'s built-in third argument to supply a default; another wraps a plain `LAG` call in `COALESCE`. You've been asked which is the better default pattern here.

**Table: `price_history`**

| Column | Type | Description |
|---|---|---|
| `record_id` | INTEGER | Unique identifier (PK) |
| `listing_id` | INTEGER | Listing identifier |
| `price_date` | DATE | Date of this price record |
| `price` | DECIMAL(12,2) | Price in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE price_history (
    record_id INTEGER PRIMARY KEY,
    listing_id INTEGER,
    price_date DATE,
    price DECIMAL(12,2)
);

INSERT INTO price_history (record_id, listing_id, price_date, price) VALUES
(1, 101, '2026-01-01', 8500000.00),
(2, 101, '2026-02-01', 8300000.00);
```

**LAG's Built-in Default Argument**

```sql
SELECT listing_id, price_date, price,
    LAG(price, 1, price) OVER (PARTITION BY listing_id ORDER BY price_date) AS previous_price
FROM price_history
ORDER BY price_date;
```

```
+-------------+---------------+-------------+------------------+
| listing_id  |  price_date   |    price    |  previous_price  |
+-------------+---------------+-------------+------------------+
|         101 |    2026-01-01 |  8500000.00 |       8500000.00 |
|         101 |    2026-02-01 |  8300000.00 |       8500000.00 |
+-------------+---------------+-------------+------------------+
```

**Your Task:** Explain what `LAG(price, 1, price)`'s third argument accomplishes for the first row, and whether `COALESCE(LAG(price) OVER (...), price)` would behave any differently.

**Answer:** `LAG(price, 1, price)`'s third argument supplies a default value to use *specifically when there's no row to look back to* — for the very first row in a partition, instead of `NULL`, it falls back to that row's own `price`, which conveniently makes the first row show "no change" (previous price equals current price) rather than an undefined `NULL`. `COALESCE(LAG(price) OVER (...), price)` produces the *exact same result* in this case — both approaches replace a first-row `NULL` with the current row's own price. The genuine difference is readability and correctness under a subtly different scenario: `LAG`'s third argument is explicitly documented as "the default when the offset goes out of range," and reads as one self-contained expression; `COALESCE` is more general-purpose and would also silently substitute the fallback if a *real* previous price existed but happened to be a stored `NULL` (a data quality issue, not a missing-row issue) — a distinction that matters if the source data can ever have genuine `NULL` prices. For a straightforward "no earlier row" case like this one, either works, but `LAG`'s built-in default is the more precise tool for the specific problem being solved.

| `day_id` | INTEGER | Unique identifier (PK) |
| `reading_date` | DATE | Date of the reading |
| `temperature` | DECIMAL(4,1) | Temperature in °C |

Write a query that returns `reading_date`, `temperature`, and `moving_avg_2day`, the average of the current day and the day immediately before it, rounded to 2 decimals.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE temp_readings_ma (
    day_id INTEGER PRIMARY KEY,
    reading_date DATE,
    temperature DECIMAL(4,1)
);

INSERT INTO temp_readings_ma (day_id, reading_date, temperature) VALUES
(1, '2026-03-01', 28.0), (2, '2026-03-02', 30.0), (3, '2026-03-03', 26.0), (4, '2026-03-04', 32.0);
```

**Output**

```
+----------------+---------------+--------------------+
|  reading_date  |  temperature  |  moving_avg_2day   |
+----------------+---------------+--------------------+
|     2026-03-01 |          28.0 |              28.00 |
|     2026-03-02 |          30.0 |              29.00 |
|     2026-03-03 |          26.0 |              28.00 |
|     2026-03-04 |          32.0 |              29.00 |
+----------------+---------------+--------------------+
```

**Solution Query**

```sql
SELECT reading_date, temperature,
    ROUND(AVG(temperature) OVER (ORDER BY reading_date ROWS BETWEEN 1 PRECEDING AND CURRENT ROW), 2) AS moving_avg_2day
FROM temp_readings_ma
ORDER BY reading_date;
```

*`ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` explicitly caps the window at just two rows — the current one and the one right before it — which is what makes this a genuine *moving* average rather than a running total across everything seen so far. The first row has no "1 preceding" row available, so its window is just itself, averaging to its own value.*

## Q26. A Running Total That Never Changes

**Topic Tag:** Running Totals, Moving Averages, and Window Frames
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (missing ORDER BY inside OVER)

**Problem Statement**

A warehouse wants a running total of units shipped, increasing with each new order. A report is instead showing the exact same number on every single row.

**Table: `warehouse_fulfillment`**

| Column | Type | Description |
|---|---|---|
| `order_id` | INTEGER | Unique identifier (PK) |
| `order_date` | DATE | Date of the order |
| `units_shipped` | INTEGER | Units shipped for this order |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE warehouse_fulfillment (
    order_id INTEGER PRIMARY KEY,
    order_date DATE,
    units_shipped INTEGER
);

INSERT INTO warehouse_fulfillment (order_id, order_date, units_shipped) VALUES
(1, '2026-03-01', 20), (2, '2026-03-02', 15), (3, '2026-03-03', 25);
```

**Buggy Query (as submitted)**

```sql
SELECT order_date, units_shipped, SUM(units_shipped) OVER () AS running_total
FROM warehouse_fulfillment
ORDER BY order_date;
```

**Buggy Output**

```
+---------------+------------------+-----------------+
|  order_date   |  units_shipped   |  running_total  |
+---------------+------------------+-----------------+
|    2026-03-01 |               20 |              60 |
|    2026-03-02 |               15 |              60 |
|    2026-03-03 |               25 |              60 |
+---------------+------------------+-----------------+
(every row shows 60 — the grand total, not a running total)
```

**What's Wrong:** `OVER ()` with nothing inside it — no `PARTITION BY`, no `ORDER BY` — treats every row as belonging to one single, unordered window covering the whole table, exactly like Q1's grand total. Without an `ORDER BY` inside `OVER (...)`, there's no notion of "up to this point" at all — `SUM()` just adds up everything, every time, for every row alike.

**Solution Query (Fixed)**

```sql
SELECT order_date, units_shipped, SUM(units_shipped) OVER (ORDER BY order_date) AS running_total
FROM warehouse_fulfillment
ORDER BY order_date;
```

**Fixed Output**

```
+---------------+------------------+-----------------+
|  order_date   |  units_shipped   |  running_total  |
+---------------+------------------+-----------------+
|    2026-03-01 |               20 |              20 |
|    2026-03-02 |               15 |              35 |
|    2026-03-03 |               25 |              60 |
+---------------+------------------+-----------------+
```

*Adding `ORDER BY order_date` inside `OVER (...)` is what turns the window into "every row up to and including this one, in date order" — the exact same fix pattern as Q9's frame discussion, just missing the `ORDER BY` entirely rather than the wrong frame.*

**Skill Focus:** Analyse (RANGE frame with ties, reinforced)

**Problem Statement**

Two farms report the exact same crop yield this season. A running total ordered by yield uses the default frame. Before running it, predict what the running total shows for both tied farms — this is the same underlying behavior as Q9, in a fresh scenario.

**Table: `crop_yields`**

| Column | Type | Description |
|---|---|---|
| `yield_id` | INTEGER | Unique identifier (PK) |
| `farm_name` | VARCHAR(60) | Farm name |
| `yield_tons` | DECIMAL(6,1) | Yield in tons |

```sql
CREATE TABLE crop_yields (

    yield_tons DECIMAL(6,1)

(1, 'Green Valley Farm', 40.0), (2, 'Sunrise Farm', 40.0), (3, 'Hilltop Farm', 60.0);
```

**Query to Analyze**

```sql
SELECT farm_name, yield_tons, SUM(yield_tons) OVER (ORDER BY yield_tons) AS running_total

```

**Your Task:** Green Valley Farm and Sunrise Farm are tied at 40.0 tons. Do they show the same running total, or two different ones reflecting their row order?

## Q28. The Top Spender in Each Region

**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Rank (per group)

A retailer wants exactly one customer per region — the single highest spender — for a regional VIP outreach list.

**Table: `customer_spend`**

| Column | Type | Description |
|---|---|---|
| `customer_id` | INTEGER | Unique identifier (PK) |
| `region` | VARCHAR(20) | Customer's region |
| `customer_name` | VARCHAR(60) | Customer's name |
| `total_spend` | DECIMAL(10,2) | Total spend in ₹ |

Write a query that returns `region`, `customer_name`, and `total_spend` for the top spender in each region.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE customer_spend (
    customer_id INTEGER PRIMARY KEY,
    region VARCHAR(20),
    customer_name VARCHAR(60),
    total_spend DECIMAL(10,2)
);

INSERT INTO customer_spend (customer_id, region, customer_name, total_spend) VALUES
(1, 'North', 'Palak Seth', 12000.00),
```

## Q29. Top 2, but a Tie Makes It Three

**Topic Tag:** Top-N Per Group
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values (RANK vs. ROW_NUMBER for top-N)

**Problem Statement**

A gym wants its top 2 most frequent visitors this month for a small reward. Two members are tied for 2nd place. Using `RANK() <= 2` for "top 2" returns *three* names, not two, since both tied members share rank 2. You've been asked whether this is the right behavior or whether `ROW_NUMBER()` should be used instead.

**Table: `gym_checkins`**

| Column | Type | Description |
|---|---|---|
| `checkin_id` | INTEGER | Unique identifier (PK) |
| `member_name` | VARCHAR(60) | Member's name |
| `month_label` | VARCHAR(20) | Month label |
| `checkins` | INTEGER | Check-ins this month |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE gym_checkins (
    checkin_id INTEGER PRIMARY KEY,
    member_name VARCHAR(60),
    month_label VARCHAR(20),
    checkins INTEGER
);

INSERT INTO gym_checkins (checkin_id, member_name, month_label, checkins) VALUES
(1, 'Rehan Fazal', 'March', 18),
(2, 'Sneha Purandare', 'March', 22),
(3, 'Aniket Rane', 'March', 18);
```

**RANK-Based Query**

```sql
WITH ranked_members AS (
    SELECT member_name, checkins, RANK() OVER (ORDER BY checkins DESC) AS rnk
    FROM gym_checkins
)
SELECT member_name, checkins FROM ranked_members WHERE rnk <= 2;
```

```
+-------------------+------------+
|   member_name     |  checkins  |
+-------------------+------------+
| Sneha Purandare   |         22 |
| Aniket Rane       |         18 |
| Rehan Fazal       |         18 |
+-------------------+------------+
(3 rows, not 2)
```

**Your Task:** Should the gym use `RANK()` or `ROW_NUMBER()` for "top 2," and why does it matter here?

**Justification:** `RANK() <= 2` returns *everyone tied for a position within the top 2*, which is why both 18-checkin members appear — they're both genuinely rank 2, and arbitrarily excluding one of them would be unfair given they're statistically identical on the metric being ranked. `ROW_NUMBER() <= 2` would force exactly 2 rows no matter what, picking one of the tied members essentially at random (by whatever order the database happens to process them in) and silently excluding the other — which risks looking arbitrary or even unfair to the excluded member if this is genuinely a reward being handed out. For "top-N" results that need an exact fixed count no matter what (e.g. "exactly 2 seats available"), `ROW_NUMBER()` is the right tool despite its arbitrary tie-breaking; for "top-N" results where a fair, defensible list matters more than an exact count (like this reward), `RANK()`'s tie-inclusive behavior is usually the fairer choice, even if it means occasionally handing out 3 rewards instead of 2.

## Q30. Reconstruct the Top 2 per Category

**Topic Tag:** Top-N Per Group
**Difficulty:** Hard
**Type:** Reverse Engineering
**Skill Focus:** Reconstruct (top-N per group)

**Problem Statement**

A retailer's merchandising team was handed the report below: the top 2 highest-revenue products within each category. Work out the query, given the raw per-product revenue data.

**Table: `product_revenue`**

| Column | Type | Description |
|---|---|---|
| `product_id` | INTEGER | Unique identifier (PK) |
| `category` | VARCHAR(30) | Product category |
| `product_name` | VARCHAR(60) | Product name |
| `revenue` | DECIMAL(10,2) | Revenue in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE product_revenue (
    product_id INTEGER PRIMARY KEY,
    category VARCHAR(30),
    product_name VARCHAR(60),
    revenue DECIMAL(10,2)
);

INSERT INTO product_revenue (product_id, category, product_name, revenue) VALUES
(1, 'Audio', 'Wireless Earbuds', 40000.00),
(2, 'Audio', 'Bluetooth Speaker', 55000.00),
(3, 'Audio', 'Wired Headphones', 12000.00),
(4, 'Kitchen', 'Air Fryer', 60000.00);
```

**Target Output**

```
+-----------+---------------------+-----------+
| category  |    product_name     |  revenue  |
+-----------+---------------------+-----------+
| Audio     | Bluetooth Speaker   |  55000.00 |
| Audio     | Wireless Earbuds    |  40000.00 |
| Kitchen   | Air Fryer           |  60000.00 |
+-----------+---------------------+-----------+
```

**Your Task:** Write the query that produces exactly this — the top 2 products by revenue within each category. (Note that "Wired Headphones" is correctly excluded — Audio only has 2 slots, and it's 3rd by revenue there.)

**Solution Query**

```sql
WITH ranked_products AS (
    SELECT category, product_name, revenue,
        ROW_NUMBER() OVER (PARTITION BY category ORDER BY revenue DESC) AS rn
    FROM product_revenue
)
SELECT category, product_name, revenue FROM ranked_products WHERE rn <= 2 ORDER BY category, revenue DESC;
```

*Kitchen only has one product in this data, so it trivially satisfies "top 2" with just the one row it has — the pattern doesn't require each group to actually contain N rows, it just never returns more than N.*
