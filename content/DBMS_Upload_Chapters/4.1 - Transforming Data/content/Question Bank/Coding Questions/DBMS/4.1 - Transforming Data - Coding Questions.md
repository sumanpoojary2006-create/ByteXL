# Transforming Data — Coding Question Bank

Dialect: **PostgreSQL**. Every query in this bank has been executed against a live PostgreSQL 16 instance; the `Output` shown for each question is the actual result — including two questions where the "buggy" query genuinely throws a PostgreSQL error, reproduced verbatim.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the query.
- **Bug Hunt** — a query someone already wrote is shown along with its (wrong, or erroring) output; find and fix the mistake.
- **Predict the Output** — a query is already written; state exactly what it returns before checking the answer.
- **Compare & Justify** — two or more functions/approaches are plausible; pick the better one and explain why.
- **Reverse Engineering** — you're shown the data and the target result; work out the query that produces it.
- **Decision-Making** — a concrete symptom is shown; diagnose the cause and recommend a fix.

## Q1. Cleaning Up Client Names

**Topic Tag:** String Functions
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Transform

**Problem Statement**

An interior design firm's client intake form was filled out with the caps-lock key stuck on. Every name in the system now reads in all-uppercase, which looks unprofessional on client-facing proposals.

**Table: `design_clients`**

| Column | Type | Description |
|---|---|---|
| `client_id` | INTEGER | Unique identifier (PK) |
| `raw_name` | VARCHAR(60) | Client name as entered, all-uppercase |

Write a query that returns `client_id` and a calculated column `display_name`, converting `raw_name` to proper title case.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE design_clients (
    client_id INTEGER PRIMARY KEY,
    raw_name VARCHAR(60)
);

INSERT INTO design_clients (client_id, raw_name) VALUES
(1, 'PRIYA MEHTA'),
(2, 'ROHAN DESAI'),
(3, 'ANITA GHOSH');
```

**Output**

```
+-----------+--------------+
| client_id | display_name |
+-----------+--------------+
|         1 | Priya Mehta  |
|         2 | Rohan Desai  |
|         3 | Anita Ghosh  |
+-----------+--------------+
```

**Solution Query**

```sql
SELECT client_id, INITCAP(raw_name) AS display_name
FROM design_clients;
```

## Q4. Seconds Don't Divide Evenly

**Topic Tag:** Numeric Functions
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (integer division)

**Problem Statement**

A marathon's results board stores each runner's finish time in whole seconds and wants a quick "minutes estimate" column. Someone wrote `finish_seconds / 60` — before trusting it, predict whether it gives a genuinely accurate minutes figure.

**Table: `race_results`**

| Column | Type | Description |
|---|---|---|
| `runner_id` | INTEGER | Unique identifier (PK) |
| `runner_name` | VARCHAR(60) | Runner's name |
| `finish_seconds` | INTEGER | Finish time in whole seconds |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE race_results (
    runner_id INTEGER PRIMARY KEY,
    runner_name VARCHAR(60),
    finish_seconds INTEGER
);

INSERT INTO race_results (runner_id, runner_name, finish_seconds) VALUES
(1, 'Aakriti Bansal', 5430),
(2, 'Vivek Thakkar', 6205),
(3, 'Noor Fatima', 5999);
```

**Query to Analyze**

```sql
SELECT runner_name, finish_seconds, finish_seconds / 60 AS minutes_estimate
FROM race_results;
```

**Your Task:** Noor Fatima's 5999 seconds is 99 minutes and 59 seconds — almost 100 minutes. What does this query actually report for her?

**Answer**

```
+----------------+----------------+------------------+
|  runner_name   | finish_seconds | minutes_estimate |
+----------------+----------------+------------------+
| Aakriti Bansal |           5430 |               90 |
| Vivek Thakkar  |           6205 |              103 |
| Noor Fatima    |           5999 |               99 |
+----------------+----------------+------------------+
```

**Why:** `finish_seconds` is an `INTEGER`, and dividing one integer by another in SQL performs *integer division* — the fractional remainder is silently truncated, not rounded. `5999 / 60` mathematically is `99.98`, but integer division floors it straight to `99`, discarding the near-whole extra minute entirely. Getting an accurate minutes figure would require forcing decimal division first, e.g. `finish_seconds / 60.0`.

## Q6. A Month That Isn't a Number

**Topic Tag:** Date and Time Functions
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (text vs. numeric extraction)

**Problem Statement**

A vintage clothing resale shop wants every item listed in March. A volunteer's query crashes outright with a database error instead of returning results.

**Table: `vintage_listings`**

| Column | Type | Description |
|---|---|---|
| `listing_id` | INTEGER | Unique identifier (PK) |
| `item_name` | VARCHAR(60) | Item name |
| `listing_date` | DATE | Date the item was listed |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE vintage_listings (
    listing_id INTEGER PRIMARY KEY,
    item_name VARCHAR(60),
    listing_date DATE
);

INSERT INTO vintage_listings (listing_id, item_name, listing_date) VALUES
(1, '70s Denim Jacket', '2026-03-05'),
(2, 'Silk Scarf Set', '2026-04-12'),
(3, 'Leather Satchel', '2026-03-22');
```

**Buggy Query (as submitted)**

```sql
SELECT item_name
FROM vintage_listings
WHERE TO_CHAR(listing_date, 'MM') = 3;
```

**Buggy Output**

```
ERROR:  operator does not exist: text = integer
LINE 1: ...FROM vintage_listings WHERE TO_CHAR(listing_date, 'MM') = 3;
                                                                   ^
HINT:  No operator matches the given name and argument types. You might need to add explicit type casts.
```

**What's Wrong:** `TO_CHAR(listing_date, 'MM')` returns a *text* value like `'03'`, not a number — `TO_CHAR` is a formatting function, meant for display, not arithmetic. Comparing that text value to the bare integer `3` gives PostgreSQL two incompatible types with no automatic conversion between them, so it refuses to run at all rather than guess.

**Solution Query (Fixed)**

```sql
SELECT item_name
FROM vintage_listings
WHERE EXTRACT(MONTH FROM listing_date) = 3;
```

**Fixed Output**

```
+------------------+
|    item_name     |
+------------------+
| 70s Denim Jacket |
| Leather Satchel  |
+------------------+
```

*`EXTRACT(MONTH FROM ...)` returns a genuine numeric value, which compares cleanly against the integer `3` — the right tool whenever the month is going to be used in a calculation or comparison rather than just displayed.*

## Q8. Zero Doesn't Mean Zero

**Topic Tag:** NULL-Handling Functions
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Validate (sentinel values)

**Problem Statement**

An elder care facility's older monitoring devices record `0` for heart rate whenever a reading genuinely failed to register — a `0` heart rate is never a real measurement. Before averaging heart rates across patients, staff want those sentinel zeros converted to proper `NULL`s so they don't quietly drag down the average.

**Table: `vitals_log`**

| Column | Type | Description |
|---|---|---|
| `patient_id` | INTEGER | Unique identifier (PK) |
| `patient_name` | VARCHAR(60) | Patient's name |
| `heart_rate` | INTEGER | Recorded heart rate, `0` means the reading failed |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE vitals_log (
    patient_id INTEGER PRIMARY KEY,
    patient_name VARCHAR(60),
    heart_rate INTEGER
);

INSERT INTO vitals_log (patient_id, patient_name, heart_rate) VALUES
(1, 'Kamla Devi', 78),
(2, 'Ram Prasad', 0),
(3, 'Sunehri Bai', 82),
(4, 'Gopal Krishna', 0);
```

**Query to Analyze**

```sql
SELECT patient_name, NULLIF(heart_rate, 0) AS heart_rate_clean
FROM vitals_log;
```

**Your Task:** What does `NULLIF(heart_rate, 0)` return for Ram Prasad and Gopal Krishna, whose readings failed?

**Answer**

```
+---------------+------------------+
| patient_name  | heart_rate_clean |
+---------------+------------------+
| Kamla Devi    |               78 |
| Ram Prasad    |           ¤NULL¤ |
| Sunehri Bai   |               82 |
| Gopal Krishna |           ¤NULL¤ |
+---------------+------------------+
```

**Why:** `NULLIF(a, b)` returns `NULL` when `a` equals `b`, and returns `a` unchanged otherwise. Since `heart_rate` is `0` for both failed readings, `NULLIF` converts exactly those two to `NULL`, while leaving the genuine readings (78, 82) untouched — a clean, one-function way to turn a sentinel value into a proper "unknown," so it's correctly excluded from any later `AVG()`.

An archery range awards medals based on score thresholds: 90 and above is Gold, 75 up to 89 is Silver, anything below that is Bronze. Coaches want each archer's medal tier alongside their raw score.

## Q10. A Firing Type by Temperature Range

**Topic Tag:** Conditional Logic
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Compare Values (simple vs. searched CASE)

**Problem Statement**

A ceramics studio classifies each kiln booking by firing type based on temperature: below 1000°C is a bisque firing, 1000°C and above is a glaze firing. A new studio assistant tries to write this using `CASE temperature_c WHEN ... THEN ...` (the "simple" form) and gets stuck — that form only compares against exact values, not ranges.

**Table: `kiln_bookings`**

| Column | Type | Description |
|---|---|---|
| `booking_id` | INTEGER | Unique identifier (PK) |
| `potter_name` | VARCHAR(60) | Potter's name |
| `temperature_c` | INTEGER | Target firing temperature in °C |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE kiln_bookings (
    booking_id INTEGER PRIMARY KEY,
    potter_name VARCHAR(60),
    temperature_c INTEGER
);

INSERT INTO kiln_bookings (booking_id, potter_name, temperature_c) VALUES
(1, 'Ila Bhatt', 950),
(2, 'Devraj Sen', 1220),
(3, 'Nayantara Iyer', 1080);
```

**Your Task:** Write the query using whichever `CASE` form actually works for a range condition, and explain why the simple form the assistant tried can't do this.

**Solution Query**

```sql
SELECT potter_name, temperature_c,
    CASE WHEN temperature_c < 1000 THEN 'Bisque Firing' ELSE 'Glaze Firing' END AS firing_type
FROM kiln_bookings;
```

**Output**

```
+----------------+---------------+---------------+
|  potter_name   | temperature_c |  firing_type  |
+----------------+---------------+---------------+
| Ila Bhatt      |           950 | Bisque Firing |
| Devraj Sen     |          1220 | Glaze Firing  |
| Nayantara Iyer |          1080 | Glaze Firing  |
+----------------+---------------+---------------+
```

**Justification:** The "simple" `CASE column WHEN value THEN ...` form can only test *equality* against a fixed list of exact values — it has no way to express "less than 1000." The "searched" form, `CASE WHEN condition THEN ...`, allows any boolean condition in each branch, including range comparisons like `temperature_c < 1000`. Since almost no two bookings will share the exact same temperature, only the searched form can classify by range at all.

## Q13. One Character Too Many

**Type:** Bug Hunt

**Problem Statement**

An antique auction house wants just the numeric part of each lot code — `'LOT-101'` should become `'101'`. A staffer's query is leaving a stray dash at the front of every result.

**Table: `auction_lots`**

| Column | Type | Description |
|---|---|---|
| `lot_id` | INTEGER | Unique identifier (PK) |
| `lot_code` | VARCHAR(20) | Lot code, e.g. `'LOT-101'` |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE auction_lots (

);

(2, 'LOT-102'),
(3, 'LOT-103');
```

**Buggy Query (as submitted)**

```sql
SELECT lot_code, SUBSTRING(lot_code FROM 4) AS lot_number
FROM auction_lots;
```

## Q14. Two Names That Look Identical

**Topic Tag:** String Functions
**Difficulty:** Hard
**Type:** Predict the Output
**Skill Focus:** Analyse (hidden whitespace)

**Problem Statement**

A chess club's tournament software is refusing to recognize player 2's nickname as a duplicate of player 1's, even though both print as `RookMaster` on screen. Before investigating further, predict what `LENGTH()` reveals about the two.

**Table: `chess_players`**

| Column | Type | Description |
|---|---|---|
| `player_id` | INTEGER | Unique identifier (PK) |
| `nickname` | VARCHAR(40) | Player's chosen nickname |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE chess_players (
    player_id INTEGER PRIMARY KEY,
    nickname VARCHAR(40)
);

INSERT INTO chess_players (player_id, nickname) VALUES
(1, 'RookMaster'),
(2, 'RookMaster '),
(3, 'PawnStorm');
```

**Query to Analyze**

```sql
SELECT player_id, nickname, LENGTH(nickname) AS name_length
FROM chess_players;
```

**Your Task:** Players 1 and 2 both display as `RookMaster` — will their `name_length` values match?

**Answer**

```
+-----------+-------------+-------------+
| player_id |  nickname   | name_length |
+-----------+-------------+-------------+
|         1 | RookMaster  |          10 |
|         2 | RookMaster  |          11 |
|         3 | PawnStorm   |           9 |
+-----------+-------------+-------------+
```

**Why:** Player 2's nickname was saved with an invisible trailing space — `'RookMaster '`, not `'RookMaster'`. It renders identically to the eye in most interfaces, but `LENGTH()` counts every character, trailing space included, so it reports 11 instead of 10. This is exactly why a lookup like `WHERE nickname = 'RookMaster'` can mysteriously fail to match a row that *looks* correct — the data itself carries a hidden difference.

```sql
INSERT INTO royalty_tracks (track_id, track_name, play_count) VALUES
(1, 'Neon Skyline', 15400),
(2, 'Quiet Monsoon', 340),
(3, 'Unreleased Demo Mix', NULL);
```

**Query to Analyze**

```sql
SELECT track_name, play_count,
    CASE WHEN play_count > 1000 THEN 'Tier A'
         WHEN play_count > 100 THEN 'Tier B'
         ELSE 'Tier C'
    END AS royalty_tier
FROM royalty_tracks;
```

**Your Task:** Does "Unreleased Demo Mix" get some special `NULL`-aware tier, or does it fall into one of the three named tiers? Which one, and why?

**Answer**

```
+---------------------+------------+--------------+
|     track_name      | play_count | royalty_tier |
+---------------------+------------+--------------+
| Neon Skyline        |      15400 | Tier A       |
| Quiet Monsoon       |        340 | Tier B       |
| Unreleased Demo Mix |     ¤NULL¤ | Tier C       |
+---------------------+------------+--------------+
```

**Why:** `NULL > 1000` and `NULL > 100` both evaluate to `UNKNOWN`, not `TRUE` — so neither `WHEN` branch matches, exactly the same three-valued logic that makes `WHERE` clauses skip `NULL` rows. `CASE` doesn't stop and flag this as a special case; it simply keeps testing branches until one is `TRUE`, and when none ever is, it falls all the way through to `ELSE`. The track lands in `'Tier C'` — not because it genuinely has low plays, but because `CASE` has no way to distinguish "confirmed low" from "unknown" without an explicit check like `WHEN play_count IS NULL THEN 'Pending Sync'` added as its own branch.

## Q30. A Status Label, Written Two Ways

**Topic Tag:** Conditional Logic
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values (readability)

**Problem Statement**

A vintage car restoration shop wants each job labeled `'Complete'` (100%), `'In Progress'` (1-99%), or `'Not Started'` (0%). One mechanic-turned-developer is proud of a clever one-liner chaining `NULLIF` and `COALESCE` to squeeze this into a single expression without `CASE` at all. You've been asked whether that's actually a good idea for the shop's reporting scripts, which junior staff will need to maintain.

**Table: `restoration_jobs`**

| Column | Type | Description |
|---|---|---|
| `job_id` | INTEGER | Unique identifier (PK) |
| `car_model` | VARCHAR(60) | Car model being restored |
| `completion_pct` | INTEGER | Percent complete (0-100) |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE restoration_jobs (
    job_id INTEGER PRIMARY KEY,
    car_model VARCHAR(60),
    completion_pct INTEGER
);

INSERT INTO restoration_jobs (job_id, car_model, completion_pct) VALUES
(1, '1967 Ford Mustang', 100),
(2, '1972 Volkswagen Beetle', 45),
(3, '1958 MG Roadster', 0);
```

**Your Task:** Write the version you'd actually recommend for the shop's scripts, and explain your reasoning.

**Solution Query**

```sql
SELECT car_model, completion_pct,
    CASE WHEN completion_pct = 100 THEN 'Complete'
         WHEN completion_pct > 0 THEN 'In Progress'
         ELSE 'Not Started'
    END AS status
FROM restoration_jobs;
```

**Output**

```
+------------------------+----------------+-------------+
|       car_model        | completion_pct |   status    |
+------------------------+----------------+-------------+
| 1967 Ford Mustang      |            100 | Complete    |
| 1972 Volkswagen Beetle |             45 | In Progress |
| 1958 MG Roadster       |              0 | Not Started |
+------------------------+----------------+-------------+
```

**Justification:** `NULLIF`/`COALESCE` chains are built for a narrow job — substituting one specific value for another — and stretching them to express three named, ordered categories forces a reader to mentally reverse-engineer the logic instead of reading it directly. A searched `CASE` states each threshold and its label side by side, in order, with no hidden cleverness — someone unfamiliar with the codebase (a junior hire, or the same developer six months later) can read it top to bottom and know exactly what each branch means. For anything beyond a single value swap, `CASE`'s clarity is worth far more than a shorter expression that only its original author can confidently modify.
