# Aggregation — Coding Question Bank

Dialect: **PostgreSQL**. Every query in this bank has been executed against a live PostgreSQL 16 instance; the `Output` shown for each question is the actual result — including several questions where the "buggy" query genuinely throws a PostgreSQL error, reproduced verbatim.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the query.
- **Bug Hunt** — a query someone already wrote is shown along with its (wrong, or erroring) output; find and fix the mistake.
- **Predict the Output** — a query is already written; state exactly what it returns before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; write the better one and explain why.
- **Reverse Engineering** — you're shown the data and the target result; work out the query that produces it.
- **Decision-Making** — a concrete symptom is shown; diagnose the cause and recommend a fix.

## Q1. One Row, Three Summary Numbers

**Topic Tag:** Aggregate Functions
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Summarize

**Problem Statement**

An online art marketplace's dashboard needs a single summary row: how many pieces have sold, the total revenue, and the average sale price.

**Table: `art_sales`**

| Column | Type | Description |
|---|---|---|
| `sale_id` | INTEGER | Unique identifier (PK) |
| `artwork_title` | VARCHAR(60) | Title of the artwork |
| `price` | DECIMAL(10,2) | Sale price in ₹ |

Write a query that returns `total_sales` (count of sales), `total_revenue` (sum of `price`), and `avg_price` (average `price`, rounded to 2 decimals) in a single row.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE art_sales (
    sale_id INTEGER PRIMARY KEY,
    artwork_title VARCHAR(60),
    price DECIMAL(10,2)
);

INSERT INTO art_sales (sale_id, artwork_title, price) VALUES
(1, 'Monsoon Reverie', 12500.00),
(2, 'Silent Harbor', 8200.00),
(3, 'Golden Hour', 15300.00),
(4, 'Dust and Light', 6100.00);
```

**Output**

```
+-------------+---------------+-----------+
| total_sales | total_revenue | avg_price |
+-------------+---------------+-----------+
|           4 |      42100.00 |  10525.00 |
+-------------+---------------+-----------+
```

**Solution Query**

```sql
SELECT COUNT(*) AS total_sales, SUM(price) AS total_revenue, ROUND(AVG(price), 2) AS avg_price
FROM art_sales;
```

## Q3. Not Every Appointment Has Notes

**Topic Tag:** Aggregate Functions
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (`COUNT(*)` vs `COUNT(column)`)

**Problem Statement**

A telehealth platform's admin wants to know both the total number of appointments logged today, and how many of those actually have doctor's notes filled in. Two of today's four appointments are still awaiting notes.

**Table: `appointments_th`**

| Column | Type | Description |
|---|---|---|
| `appt_id` | INTEGER | Unique identifier (PK) |
| `patient_name` | VARCHAR(60) | Patient's name |
| `doctor_notes` | VARCHAR(200) | Doctor's notes, `NULL` if not yet entered |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE appointments_th (
    appt_id INTEGER PRIMARY KEY,
    patient_name VARCHAR(60),
    doctor_notes VARCHAR(200)
);

INSERT INTO appointments_th (appt_id, patient_name, doctor_notes) VALUES
(1, 'Kunal Bhide', 'Follow up in 2 weeks'),
(2, 'Sana Patel', NULL),
(3, 'Rohit Iyer', 'Prescribed antibiotics'),
(4, 'Meera Nair', NULL);
```

**Query to Analyze**

```sql
SELECT COUNT(*) AS total_rows, COUNT(doctor_notes) AS notes_filled
FROM appointments_th;
```

**Your Task:** Will `total_rows` and `notes_filled` report the same number?

**Answer**

```
+------------+--------------+
| total_rows | notes_filled |
+------------+--------------+
|          4 |            2 |
+------------+--------------+
```

**Why:** `COUNT(*)` counts every row in the result set, full stop — it doesn't look inside any particular column. `COUNT(column)` counts only the rows where that specific column is *not* `NULL`. Two appointments have `doctor_notes` still `NULL`, so `COUNT(doctor_notes)` skips them and reports 2, while `COUNT(*)` correctly reports all 4 appointments regardless of whether notes exist yet.

## Q6. A Column That Isn't Grouped

**Topic Tag:** Grouping Data
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (missing GROUP BY column)

**Problem Statement**

A tutoring center wants total fees earned per tutor, broken down by subject — a tutor who teaches two subjects should show up as two separate rows. A staffer's query fails to run at all.

**Table: `tutoring_revenue`**

| Column | Type | Description |
|---|---|---|
| `session_id` | INTEGER | Unique identifier (PK) |
| `tutor_name` | VARCHAR(60) | Tutor's name |
| `subject` | VARCHAR(40) | Subject taught |
| `fee` | DECIMAL(8,2) | Session fee in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE tutoring_revenue (
    session_id INTEGER PRIMARY KEY,
    tutor_name VARCHAR(60),
    subject VARCHAR(40),
    fee DECIMAL(8,2)
);

INSERT INTO tutoring_revenue (session_id, tutor_name, subject, fee) VALUES
(1, 'Anjali Rao', 'Math', 800.00),
(2, 'Anjali Rao', 'Physics', 900.00),
(3, 'Devendra Singh', 'Chemistry', 850.00);
```

**Buggy Query (as submitted)**

```sql
SELECT tutor_name, subject, SUM(fee)
FROM tutoring_revenue
GROUP BY tutor_name;
```

**Buggy Output**

```
ERROR:  column "tutoring_revenue.subject" must appear in the GROUP BY clause or be used in an aggregate function
LINE 1: SELECT tutor_name, subject, SUM(fee) FROM tutoring_revenue G...
                           ^
```

**What's Wrong:** Every column in the `SELECT` list that isn't wrapped in an aggregate function must appear in `GROUP BY` — otherwise, for a `tutor_name` group spanning multiple subjects, PostgreSQL has no single, unambiguous `subject` value to return for that row. Grouping only by `tutor_name` while still selecting bare `subject` leaves that ambiguity unresolved, so PostgreSQL refuses to run it.

**Solution Query (Fixed)**

```sql
SELECT tutor_name, subject, SUM(fee) AS total_fee
FROM tutoring_revenue
GROUP BY tutor_name, subject
ORDER BY tutor_name, subject;
```

**Fixed Output**

```
+----------------+-----------+-----------+
|   tutor_name   |  subject  | total_fee |
+----------------+-----------+-----------+
| Anjali Rao     | Math      |    800.00 |
| Anjali Rao     | Physics   |    900.00 |
| Devendra Singh | Chemistry |    850.00 |
+----------------+-----------+-----------+
```

*Grouping by both `tutor_name` and `subject` makes each group's `subject` unambiguous, since every row within a group now genuinely shares the same subject.*

## Q7. Households Generating Over 100 Units

**Topic Tag:** Filtering Groups
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Compare Values

**Problem Statement**

A community solar cooperative wants to recognize households whose combined generation this month exceeds 100 units, for a small rebate program.

**Table: `solar_generation`**

| Column | Type | Description |
|---|---|---|
| `reading_id` | INTEGER | Unique identifier (PK) |
| `household_name` | VARCHAR(60) | Household name |
| `units_generated` | DECIMAL(6,1) | Units generated in this reading |

Write a query that returns `household_name` and `total_units`, but only for households whose combined `units_generated` exceeds 100.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE solar_generation (
    reading_id INTEGER PRIMARY KEY,
    household_name VARCHAR(60),
    units_generated DECIMAL(6,1)
);

INSERT INTO solar_generation (reading_id, household_name, units_generated) VALUES
(1, 'Sharma Residence', 60.0),
(2, 'Sharma Residence', 55.0),
(3, 'Patel Residence', 30.0),
(4, 'Patel Residence', 25.0);
```

**Output**

```
+------------------+-------------+
|  household_name  | total_units |
+------------------+-------------+
| Sharma Residence |       115.0 |
+------------------+-------------+
```

**Solution Query**

```sql
SELECT household_name, SUM(units_generated) AS total_units
FROM solar_generation
GROUP BY household_name
HAVING SUM(units_generated) > 100
ORDER BY household_name;
```

*Patel Residence's combined 55.0 units doesn't clear the 100-unit bar, so `HAVING` correctly drops that entire group from the result — `HAVING` filters groups after aggregation, the way `WHERE` filters individual rows before it.*

## Q8. Filtering a Total Before It Exists

**Topic Tag:** Filtering Groups
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Validate (WHERE vs. HAVING)

**Problem Statement**

An esports tournament organizer wants teams whose combined prize money exceeds ₹5000. Someone tried filtering that threshold using `WHERE` directly. Before assuming it just returns the wrong teams, predict what actually happens when it runs.

**Table: `tournament_earnings`**

| Column | Type | Description |
|---|---|---|
| `player_id` | INTEGER | Unique identifier (PK) |
| `team_name` | VARCHAR(40) | Team name |
| `prize_amount` | DECIMAL(10,2) | Prize amount for this player in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE tournament_earnings (
    player_id INTEGER PRIMARY KEY,
    team_name VARCHAR(40),
    prize_amount DECIMAL(10,2)
);

INSERT INTO tournament_earnings (player_id, team_name, prize_amount) VALUES
(1, 'Team Vortex', 3000.00),
(2, 'Team Vortex', 4000.00),
(3, 'Team Falcon', 2000.00);
```

**Query to Analyze**

```sql
SELECT team_name, SUM(prize_amount)
FROM tournament_earnings
WHERE SUM(prize_amount) > 5000
GROUP BY team_name;
```

**Your Task:** Does this return only Team Vortex (whose combined prize is ₹7000), or something else entirely?

**Answer**

```
ERROR:  aggregate functions are not allowed in WHERE
LINE 1: ... SUM(prize_amount) FROM tournament_earnings WHERE SUM(prize_...
                                                             ^
```

**Why:** `WHERE` filters individual rows *before* any grouping or aggregation has happened — at the point `WHERE` runs, there's no "team total" yet for it to compare against, only single-player rows. `SUM()` genuinely doesn't exist yet in `WHERE`'s frame of reference, so PostgreSQL rejects the query outright rather than silently misinterpreting it. Filtering on an aggregated value requires `HAVING`, which runs *after* grouping: `... GROUP BY team_name HAVING SUM(prize_amount) > 5000`.

## Q10. Branches with Enough Completed Repairs

**Topic Tag:** Combining Aggregation with Sorting, Filtering, and Joins
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Compare Values (WHERE + HAVING together)

**Problem Statement**

A bicycle repair shop chain wants branches that have completed at least 2 repairs — but "completed" needs to be decided *before* counting, while "at least 2" needs to be decided *after* counting. A junior analyst isn't sure whether both conditions belong in `HAVING`, or whether they need to be split across `WHERE` and `HAVING`.

**Table: `repair_jobs`**

| Column | Type | Description |
|---|---|---|
| `job_id` | INTEGER | Unique identifier (PK) |
| `branch_name` | VARCHAR(40) | Branch name |
| `status` | VARCHAR(20) | Completed / Pending |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE repair_jobs (
    job_id INTEGER PRIMARY KEY,
    branch_name VARCHAR(40),
    status VARCHAR(20)
);

INSERT INTO repair_jobs (job_id, branch_name, status) VALUES
(1, 'Central Branch', 'Completed'),
(2, 'Central Branch', 'Completed'),
(3, 'Central Branch', 'Pending'),
(4, 'North Branch', 'Completed');
```

**Your Task:** Write the correct combined query, and explain why `status = 'Completed'` belongs in `WHERE` rather than being folded into the `HAVING` condition alongside the count.

**Solution Query**

```sql
SELECT branch_name, COUNT(*) AS completed_count
FROM repair_jobs
WHERE status = 'Completed'
GROUP BY branch_name
HAVING COUNT(*) >= 2;
```

**Output**

```
+----------------+------------------+
|  branch_name   | completed_count  |
+----------------+------------------+
| Central Branch |                2 |
+----------------+------------------+
```

**Justification:** `status = 'Completed'` is a condition about a single row's own value — exactly what `WHERE` is for, and filtering it out early means the `Pending` row never even reaches the grouping step, so it can't inflate any count. `COUNT(*) >= 2`, on the other hand, is a condition about the *group's* total after aggregation — it can only be evaluated once rows are grouped, which is `HAVING`'s job. Trying to fold `status = 'Completed'` into `HAVING` (e.g. `HAVING status = 'Completed' AND COUNT(*) >= 2`) wouldn't even run — `status` isn't an aggregate and isn't in `GROUP BY`, the same ambiguity error as Q6.

## Q14. Summing a Column That's All NULL

**Topic Tag:** Aggregate Functions
**Difficulty:** Hard
**Type:** Predict the Output
**Skill Focus:** Analyse (aggregates over all-NULL groups)

**Problem Statement**

A coworking space's room-usage tracker logs hours used per booking, but two Falcon Room bookings never had their usage hours filled in. Before trusting a "total hours used" report, predict what `SUM()` reports for a group where every single value is `NULL`.

**Table: `space_usage`**

| Column | Type | Description |
|---|---|---|
| `log_id` | INTEGER | Unique identifier (PK) |
| `room_name` | VARCHAR(40) | Room name |
| `hours_used` | DECIMAL(5,2) | Hours used, `NULL` if never logged |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE space_usage (
    log_id INTEGER PRIMARY KEY,
    room_name VARCHAR(40),
    hours_used DECIMAL(5,2)
);

INSERT INTO space_usage (log_id, room_name, hours_used) VALUES
(1, 'Falcon Room', NULL),
(2, 'Falcon Room', NULL);
```

**Query to Analyze**

```sql
SELECT room_name, SUM(hours_used) AS total_hours, COUNT(hours_used) AS logged_count
FROM space_usage
GROUP BY room_name;
```

**Your Task:** Does `SUM(hours_used)` report `0` for the Falcon Room, since there's genuinely no usage recorded?

**Answer**

```
+-------------+-------------+--------------+
|  room_name  | total_hours | logged_count |
+-------------+-------------+--------------+
| Falcon Room |      ¤NULL¤ |            0 |
+-------------+-------------+--------------+
```

**Why:** `SUM()` (like every aggregate function except `COUNT(*)`) simply ignores `NULL` values while summing — but when *every* value in a group is `NULL`, there's nothing left to sum at all, and `SUM()` reports `NULL`, not `0`. Reporting `0` would falsely claim "we know this room was used zero hours"; reporting `NULL` correctly says "we have no usage data for this room at all" — a meaningfully different, and more honest, statement. `COUNT(hours_used)` reporting `0` confirms exactly that: zero *logged* readings, not zero usage.

## Q15. Reconstruct the Quiz Summary

**Type:** Reverse Engineering
**Skill Focus:** Reconstruct

(1, '2026-03-01', 'Paid', 300.00),
(2, '2026-03-01', 'Free', 0.00),
(3, '2026-03-01', 'Paid', 350.00),
(4, '2026-03-02', 'Paid', 200.00);
```

FROM aquarium_tickets

```

**Why:** Site Beta's only pickup (10kg) survives the `WHERE weight_kg > 5` row filter, but once grouped, its total (10kg) never clears the `HAVING SUM(weight_kg) > 50` group filter, so it's dropped before `ORDER BY` ever sees it. The two survivors, Site Gamma (115kg) and Site Alpha (75kg), are then sorted by their summed weight, heaviest first — `ORDER BY` here sorts on the aggregated `total_weight`, computed *after* every earlier clause has already run. The fixed pipeline is always: filter rows (`WHERE`) → group (`GROUP BY`) → filter groups (`HAVING`) → sort (`ORDER BY`).

## Q29. Busy Branches, Highest Revenue First

**Topic Tag:** Combining Aggregation with Sorting, Filtering, and Joins
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values

**Problem Statement**

A co-working cafe chain wants its busiest branches — more than 5 orders — ranked by total revenue, top 3 only. One developer's draft query groups and filters correctly but sorts by `order_count` instead of `total_amount`, so a branch with lots of small orders could outrank a branch with fewer, larger ones. You've been asked to fix the sort key and confirm the query still behaves correctly.

**Table: `cafe_orders`**

| Column | Type | Description |
|---|---|---|
| `order_id` | INTEGER | Unique identifier (PK) |
| `branch_name` | VARCHAR(40) | Branch name |
| `amount` | DECIMAL(8,2) | Order amount in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE cafe_orders (
    order_id INTEGER PRIMARY KEY,
    branch_name VARCHAR(40),
    amount DECIMAL(8,2)
);

INSERT INTO cafe_orders (order_id, branch_name, amount) VALUES
(1, 'Branch A', 200.00),
(2, 'Branch A', 250.00),
(3, 'Branch A', 300.00),
(4, 'Branch A', 100.00),
(5, 'Branch A', 150.00),
(6, 'Branch A', 400.00),
(7, 'Branch B', 500.00),
(8, 'Branch B', 600.00);
```

**Your Task:** Write the query ranked by revenue as intended, and explain what would have gone wrong sorting by `order_count` instead.

**Solution Query**

```sql
SELECT branch_name, COUNT(*) AS order_count, SUM(amount) AS total_amount
FROM cafe_orders
GROUP BY branch_name
HAVING COUNT(*) > 5
ORDER BY total_amount DESC
LIMIT 3;
```

**Output**

```
+-------------+-------------+--------------+
| branch_name | order_count | total_amount |
+-------------+-------------+--------------+
| Branch A    |           6 |      1400.00 |
+-------------+-------------+--------------+
```

**Justification:** In this data, Branch B only has 2 orders, so it never even clears the `HAVING COUNT(*) > 5` bar, regardless of which column the final `ORDER BY` uses — meaning both the buggy and fixed versions happen to produce the same single-row result here. But the bug is real and would surface with more data: a branch handling 20 tiny ₹50 orders (`order_count` = 20) could out-rank a branch with 6 orders averaging ₹500 each (`order_count` = 6) if sorted by count, even though the second branch brought in far more revenue. Since the question asks for branches ranked by *revenue*, `ORDER BY total_amount DESC` is the only sort key that actually answers it — `order_count` measures something related but different (volume of orders, not money earned).

## Q30. Reconstruct the Genre Leaderboard

**Topic Tag:** Combining Aggregation with Sorting, Filtering, and Joins
**Difficulty:** Hard
**Type:** Reverse Engineering
**Skill Focus:** Reconstruct

**Problem Statement**

A vintage vinyl record shop's owner has already pulled the single best-selling genre among genres that sold more than ₹500 total. Work out the full query — filtering, grouping, sorting, and limiting — that produces this one-row result from the raw sales data.

**Table: `vinyl_sales`**

| Column | Type | Description |
|---|---|---|
| `sale_id` | INTEGER | Unique identifier (PK) |
| `genre` | VARCHAR(30) | Music genre |
| `amount` | DECIMAL(8,2) | Sale amount in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE vinyl_sales (
    sale_id INTEGER PRIMARY KEY,
    genre VARCHAR(30),
    amount DECIMAL(8,2)
);

INSERT INTO vinyl_sales (sale_id, genre, amount) VALUES
(1, 'Jazz', 1200.00),
(2, 'Jazz', 1100.00),
(3, 'Rock', 900.00),
(4, 'Rock', 850.00),
(5, 'Funk', 200.00);
```

**Target Output**

```
+-------+-------------+
| genre | total_sales |
+-------+-------------+
| Jazz  |     2300.00 |
+-------+-------------+
```

**Your Task:** Write the single query — filtering out genres under ₹500 total, and keeping only the single top genre by sales — that produces exactly this result.

**Solution Query**

```sql
SELECT genre, SUM(amount) AS total_sales
FROM vinyl_sales
GROUP BY genre
HAVING SUM(amount) > 500
ORDER BY total_sales DESC
LIMIT 1;
```

*'Funk', at ₹200 total, is excluded by `HAVING` before `ORDER BY`/`LIMIT` ever run — otherwise a low-selling genre could never accidentally end up "on top" just because of how the pipeline order works.*
