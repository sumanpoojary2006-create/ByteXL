# Joins — Coding Question Bank

Dialect: **PostgreSQL**. Every query in this bank has been executed against a live PostgreSQL 16 instance; the `Output` shown for each question is the actual result, not a hand-typed guess.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the query.
- **Bug Hunt** — a query someone already wrote is shown along with its (wrong) output; find and fix the mistake.
- **Predict the Output** — a query is already written; state exactly what it returns before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; write the better one and explain why.
- **Reverse Engineering** — you're shown the data and the target result; work out the query that produces it.
- **Decision-Making** — a concrete symptom is shown; diagnose the cause and recommend a fix.

## Q1. One Table Can't Hold Both

**Topic Tag:** Why Joins Exist?
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A veterinary clinic chain keeps pet owners in one table and their pets in another, since one owner can have several pets. The front desk needs a combined view showing each owner alongside their pet's name.

**Table: `pet_owners`**

| Column | Type | Description |
|---|---|---|
| `owner_id` | INTEGER | Unique identifier (PK) |
| `owner_name` | VARCHAR(60) | Owner's name |

**Table: `pets`**

| Column | Type | Description |
|---|---|---|
| `pet_id` | INTEGER | Unique identifier (PK) |
| `pet_name` | VARCHAR(40) | Pet's name |
| `owner_id` | INTEGER | References `pet_owners.owner_id` |

Write a query that returns `owner_name` and `pet_name` for every pet, matched to its owner.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE pet_owners (
    owner_id INTEGER PRIMARY KEY,
    owner_name VARCHAR(60)
);

CREATE TABLE pets (
    pet_id INTEGER PRIMARY KEY,
    pet_name VARCHAR(40),
    owner_id INTEGER
);

INSERT INTO pet_owners (owner_id, owner_name) VALUES
(1, 'Kavya Nair'), (2, 'Rohit Sinha'), (3, 'Divya Rao');

INSERT INTO pets (pet_id, pet_name, owner_id) VALUES
(1, 'Bruno', 1), (2, 'Whiskers', 2), (3, 'Coco', 3);
```

**Output**

```
+-------------+----------+
| owner_name  | pet_name |
+-------------+----------+
| Divya Rao   | Coco     |
| Kavya Nair  | Bruno    |
| Rohit Sinha | Whiskers |
+-------------+----------+
```

**Solution Query**

```sql
SELECT o.owner_name, p.pet_name
FROM pet_owners o
INNER JOIN pets p ON o.owner_id = p.owner_id
ORDER BY o.owner_name;
```

## Q3. Products from Indian Suppliers

**Topic Tag:** INNER JOIN
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (join + filter)

**Problem Statement**

A warehouse wants to audit which products come specifically from suppliers based in India, to check compliance with a new domestic-sourcing target.

**Table: `suppliers`**

| Column | Type | Description |
|---|---|---|
| `supplier_id` | INTEGER | Unique identifier (PK) |
| `supplier_name` | VARCHAR(60) | Supplier's name |
| `country` | VARCHAR(40) | Supplier's country |

**Table: `products_wh`**

| Column | Type | Description |
|---|---|---|
| `product_id` | INTEGER | Unique identifier (PK) |
| `product_name` | VARCHAR(60) | Product name |
| `supplier_id` | INTEGER | References `suppliers.supplier_id` |
| `unit_price` | DECIMAL(8,2) | Unit price in ₹ |

Write a query that returns `product_name` and `supplier_name` for products whose supplier is based in `'India'`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE suppliers (
    supplier_id INTEGER PRIMARY KEY,
    supplier_name VARCHAR(60),
    country VARCHAR(40)
);

CREATE TABLE products_wh (
    product_id INTEGER PRIMARY KEY,
    product_name VARCHAR(60),
    supplier_id INTEGER,
    unit_price DECIMAL(8,2)
);

INSERT INTO suppliers (supplier_id, supplier_name, country) VALUES
(1, 'Bharat Components', 'India'), (2, 'Meridian Traders', 'UAE'), (3, 'Ganges Industrial', 'India');

INSERT INTO products_wh (product_id, product_name, supplier_id, unit_price) VALUES
(1, 'Steel Bracket', 1, 45.00), (2, 'Copper Wire Roll', 2, 220.00), (3, 'Rubber Gasket', 3, 12.00);
```

**Output**

```
+---------------+-------------------+
| product_name  |   supplier_name   |
+---------------+-------------------+
| Rubber Gasket | Ganges Industrial |
| Steel Bracket | Bharat Components |
+---------------+-------------------+
```

**Solution Query**

```sql
SELECT p.product_name, s.supplier_name
FROM products_wh p
INNER JOIN suppliers s ON p.supplier_id = s.supplier_id
WHERE s.country = 'India'
ORDER BY p.product_name;
```

*Copper Wire Roll never appears, since `INNER JOIN` only keeps rows with a match on both sides, and the `WHERE` filter removes the UAE supplier's row entirely — `INNER JOIN` only shows what genuinely exists in both tables and satisfies every condition.*

## Q4. Every Member, Loan or Not

A library wants a membership report listing every registered member, showing their currently borrowed book if they have one — but members with no active loan should still appear on the list, not disappear from it.

**Table: `library_members`**

| Column | Type | Description |
|---|---|---|
| `member_id` | INTEGER | Unique identifier (PK) |
| `member_name` | VARCHAR(60) | Member's name |

**Table: `active_loans`**

| Column | Type | Description |
|---|---|---|
| `loan_id` | INTEGER | Unique identifier (PK) |
| `member_id` | INTEGER | References `library_members.member_id` |
| `book_title` | VARCHAR(80) | Title of the borrowed book |

Write a query that returns `member_name` and `book_title` for every member, including those with no active loan.

```sql
CREATE TABLE library_members (
    member_id INTEGER PRIMARY KEY,
    member_name VARCHAR(60)
);

CREATE TABLE active_loans (
    loan_id INTEGER PRIMARY KEY,
    member_id INTEGER,
    book_title VARCHAR(80)
);

INSERT INTO library_members (member_id, member_name) VALUES
(1, 'Ankit Sardana'), (2, 'Bhavya Chandran'), (3, 'Chirag Vora');

INSERT INTO active_loans (loan_id, member_id, book_title) VALUES
(1, 1, 'Principles of Economics'), (2, 3, 'World History Atlas');
```

**Output**

```
+-----------------+-------------------------+
|   member_name   |       book_title        |
+-----------------+-------------------------+
| Ankit Sardana   | Principles of Economics |
| Bhavya Chandran | ¤NULL¤                  |
| Chirag Vora     | World History Atlas     |
+-----------------+-------------------------+
```

**Solution Query**

```sql
SELECT m.member_name, l.book_title
FROM library_members m
LEFT JOIN active_loans l ON m.member_id = l.member_id
ORDER BY m.member_name;
```

*Bhavya Chandran has no matching row in `active_loans`, so `LEFT JOIN` still keeps her row from `library_members` and simply fills `book_title` with `NULL` — an `INNER JOIN` here would have dropped her entirely.*

## Q5. One Member, Two Bookings

**Topic Tag:** LEFT JOIN
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (row multiplication and NULL rows)

**Problem Statement**

A coworking space's usage report joins members to their room bookings. Zoya Ahmed has booked two different rooms, Aditya Menon has booked one, and Simran Kaur hasn't booked any room yet. Before running the report, predict exactly how many rows come back, and what happens to Simran's row.

**Table: `coworking_members`**

| Column | Type | Description |
|---|---|---|
| `member_id` | INTEGER | Unique identifier (PK) |
| `member_name` | VARCHAR(60) | Member's name |

**Table: `room_bookings`**

| Column | Type | Description |
|---|---|---|
| `booking_id` | INTEGER | Unique identifier (PK) |
| `member_id` | INTEGER | References `coworking_members.member_id` |
| `room_name` | VARCHAR(40) | Room booked |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE coworking_members (
    member_id INTEGER PRIMARY KEY,
    member_name VARCHAR(60)
);

CREATE TABLE room_bookings (
    booking_id INTEGER PRIMARY KEY,
    member_id INTEGER,
    room_name VARCHAR(40)
);

INSERT INTO coworking_members (member_id, member_name) VALUES
(1, 'Zoya Ahmed'), (2, 'Aditya Menon'), (3, 'Simran Kaur');

INSERT INTO room_bookings (booking_id, member_id, room_name) VALUES
(1, 1, 'Falcon Room'), (2, 1, 'Eagle Room'), (3, 2, 'Falcon Room');
```

**Query to Analyze**

```sql
SELECT m.member_name, b.room_name
FROM coworking_members m
LEFT JOIN room_bookings b ON m.member_id = b.member_id
ORDER BY m.member_name, b.room_name;
```

**Your Task:** How many total rows come back, and does Zoya Ahmed appear once or twice?

**Answer**

```
+--------------+-------------+
| member_name  |  room_name  |
+--------------+-------------+
| Aditya Menon | Falcon Room |
| Simran Kaur  | ¤NULL¤      |
| Zoya Ahmed   | Eagle Room  |
| Zoya Ahmed   | Falcon Room |
+--------------+-------------+
(4 rows)
```

**Why:** `LEFT JOIN` produces one output row for *every match* — since Zoya has two bookings, she appears twice, once per matching booking row, each with her name repeated. Simran has zero matching bookings, so she appears exactly once with `room_name` as `NULL`, the "keep the left row anyway" guarantee `LEFT JOIN` makes. The total row count isn't the number of members (3) — it's the number of members-with-no-match, plus the number of actual booking matches: 1 (Simran) + 1 (Aditya) + 2 (Zoya) = 4.

## Q6. Vacant Units Gone Missing

**Topic Tag:** RIGHT JOIN and FULL OUTER JOIN
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (wrong LEFT JOIN direction)

**Problem Statement**

An apartment complex has 4 units, 2 of them vacant. The property manager wants a report of every unit with its tenant's name if occupied — but a leasing agent's query only ever shows the 2 occupied units, never the vacant ones the manager actually needs to see.

**Table: `units`**

| Column | Type | Description |
|---|---|---|
| `unit_id` | INTEGER | Unique identifier (PK) |
| `unit_number` | VARCHAR(10) | Unit number |

**Table: `tenants`**

| Column | Type | Description |
|---|---|---|
| `tenant_id` | INTEGER | Unique identifier (PK) |
| `tenant_name` | VARCHAR(60) | Tenant's name |
| `unit_id` | INTEGER | References `units.unit_id` |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE units (
    unit_id INTEGER PRIMARY KEY,
    unit_number VARCHAR(10)
);

CREATE TABLE tenants (
    tenant_id INTEGER PRIMARY KEY,
    tenant_name VARCHAR(60),
    unit_id INTEGER
);

INSERT INTO units (unit_id, unit_number) VALUES
(1, '101'), (2, '102'), (3, '103'), (4, '104');

INSERT INTO tenants (tenant_id, tenant_name, unit_id) VALUES
(1, 'Rohan Mehta', 1), (2, 'Sana Iqbal', 3);
```

**Buggy Query (as submitted)**

```sql
SELECT u.unit_number, t.tenant_name
FROM tenants t
LEFT JOIN units u ON t.unit_id = u.unit_id
ORDER BY u.unit_number;
```

**Buggy Output**

```
+-------------+-------------+
| unit_number | tenant_name |
+-------------+-------------+
| 101         | Rohan Mehta |
| 103         | Sana Iqbal  |
+-------------+-------------+
(only 2 rows — units 102 and 104 never appear)
```

**What's Wrong:** `LEFT JOIN` guarantees every row from the table on the *left* survives — but the query put `tenants` on the left, and `tenants` never had rows for the vacant units in the first place. A `LEFT JOIN` can only preserve rows that exist; it can't invent tenant-less rows for units that were never in `tenants` to begin with.

**Solution Query (Fixed)**

```sql
SELECT u.unit_number, t.tenant_name
FROM units u
LEFT JOIN tenants t ON u.unit_id = t.unit_id
ORDER BY u.unit_number;
```

**Fixed Output**

```
+-------------+-------------+
| unit_number | tenant_name |
+-------------+-------------+
| 101         | Rohan Mehta |
| 102         | ¤NULL¤      |
| 103         | Sana Iqbal  |
| 104         | ¤NULL¤      |
+-------------+-------------+
```

*Putting `units` on the left guarantees every unit shows up, tenant or not — the fix isn't a different join type at all, just which table is on which side of it.*

## Q7. Who Reports to Whom

**Topic Tag:** Self Joins
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (self-referencing)

**Problem Statement**

A company stores every employee in one table, with a `manager_id` pointing back to another row in that same table. HR wants a simple report pairing each employee with their manager's name.

**Table: `employees_org`**

| Column | Type | Description |
|---|---|---|
| `employee_id` | INTEGER | Unique identifier (PK) |
| `employee_name` | VARCHAR(60) | Employee's name |
| `manager_id` | INTEGER | References `employees_org.employee_id`, `NULL` for the top of the chain |

Write a query that returns `employee` and `manager`, joining the table to itself.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE employees_org (
    employee_id INTEGER PRIMARY KEY,
    employee_name VARCHAR(60),
    manager_id INTEGER
);

INSERT INTO employees_org (employee_id, employee_name, manager_id) VALUES
(1, 'Farhan Ali', NULL),
(2, 'Neha Kulkarni', 1),
(3, 'Arjun Reddy', 1),
(4, 'Devika Pillai', 2);
```

**Output**

```
+---------------+---------------+
|   employee    |    manager    |
+---------------+---------------+
| Arjun Reddy   | Farhan Ali    |
| Devika Pillai | Neha Kulkarni |
| Farhan Ali    | ¤NULL¤        |
| Neha Kulkarni | Farhan Ali    |
+---------------+---------------+
```

**Solution Query**

```sql
SELECT e.employee_name AS employee, m.employee_name AS manager
FROM employees_org e
LEFT JOIN employees_org m ON e.manager_id = m.employee_id
ORDER BY e.employee_name;
```

*The same table plays two different roles at once — `e` for "the employee row" and `m` for "that employee's manager row" — connected by matching `e.manager_id` to `m.employee_id`. `LEFT JOIN` (rather than `INNER JOIN`) keeps Farhan Ali visible even though he has no manager of his own.*

## Q8. Which Students Are in Which Courses

**Topic Tag:** Multi-Table Joins
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (three tables)

**Problem Statement**

An e-learning platform stores students, courses, and enrollments (which link the two) in three separate tables. The registrar wants a simple report of which student is enrolled in which course, by name — not by ID.

**Table: `students`**

| Column | Type | Description |
|---|---|---|
| `student_id` | INTEGER | Unique identifier (PK) |
| `student_name` | VARCHAR(60) | Student's name |

**Table: `courses`**

| Column | Type | Description |
|---|---|---|
| `course_id` | INTEGER | Unique identifier (PK) |
| `course_name` | VARCHAR(60) | Course name |

**Table: `enrollments`**

| Column | Type | Description |

| `enrollment_id` | INTEGER | Unique identifier (PK) |
| `student_id` | INTEGER | References `students.student_id` |
| `course_id` | INTEGER | References `courses.course_id` |

Write a query that returns `student_name` and `course_name` for every enrollment, joining all three tables.

```sql
CREATE TABLE courses (
    course_id INTEGER PRIMARY KEY,
    course_name VARCHAR(60)
);

    enrollment_id INTEGER PRIMARY KEY,

INSERT INTO students (student_id, student_name) VALUES
(1, 'Kabir Anand'), (2, 'Ira Chatterjee');

INSERT INTO courses (course_id, course_name) VALUES
(1, 'Intro to Python'), (2, 'Data Structures');

```
```
+----------------+-----------------+
```

## Q9. One Actor, Several Roles

**Topic Tag:** Multi-Table Joins
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (fan-out)

**Problem Statement**

A talent agency joins actors to the productions they've been cast in. Meher Kohli has landed two roles this season; Devraj Sen has landed one. Before running the report, predict how many rows come back, and whether Meher Kohli's name appears once or more than once.

**Table: `actors`**

| Column | Type | Description |
|---|---|---|
| `actor_id` | INTEGER | Unique identifier (PK) |
| `actor_name` | VARCHAR(60) | Actor's name |

**Table: `roles`**

| Column | Type | Description |
|---|---|---|
| `role_id` | INTEGER | Unique identifier (PK) |
| `actor_id` | INTEGER | References `actors.actor_id` |
| `production_name` | VARCHAR(60) | Production the role is in |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE actors (
    actor_id INTEGER PRIMARY KEY,
    actor_name VARCHAR(60)
);

CREATE TABLE roles (
    role_id INTEGER PRIMARY KEY,
    actor_id INTEGER,
    production_name VARCHAR(60)
);

INSERT INTO actors (actor_id, actor_name) VALUES
(1, 'Meher Kohli'), (2, 'Devraj Sen');

INSERT INTO roles (role_id, actor_id, production_name) VALUES
(1, 1, 'Monsoon Nights'), (2, 1, 'City Lights'), (3, 2, 'Silent Harbor');
```

**Query to Analyze**

```sql
SELECT a.actor_name, r.production_name
FROM actors a
INNER JOIN roles r ON a.actor_id = r.actor_id
ORDER BY a.actor_name, r.production_name;
```

**Your Task:** How many total rows, and how many times does "Meher Kohli" appear?

**Answer**

```
+-------------+------------------+
| actor_name  | production_name |
+-------------+------------------+
| Devraj Sen  | Silent Harbor    |
| Meher Kohli | City Lights      |
| Meher Kohli | Monsoon Nights   |
+-------------+------------------+
(3 rows)
```

**Why:** The result has one row per *role*, not per actor — joining always produces one output row for each matching pair. Since Meher Kohli has two rows in `roles`, her name is duplicated across two output rows, once per production. This "fan-out" is normal and expected whenever the joined table has multiple matches for one row on the other side; it only becomes a bug if something downstream (like `SUM()` or `COUNT(DISTINCT actor_id)`) isn't written to account for it.

## Q10. Policyholders with at Least One Claim

**Topic Tag:** Semi Joins and Anti Joins
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Compare Values (JOIN+DISTINCT vs. EXISTS)

**Problem Statement**

An insurance company wants a list of policyholders who have filed at least one claim — just their names, once each, regardless of how many claims they've filed. One developer plans to `INNER JOIN` policyholders to claims and add `DISTINCT`; another suggests `WHERE EXISTS (...)` instead. You've been asked which is the better default and why.

**Table: `policyholders`**

| Column | Type | Description |
|---|---|---|
| `policyholder_id` | INTEGER | Unique identifier (PK) |
| `name` | VARCHAR(60) | Policyholder's name |

**Table: `claims`**

| Column | Type | Description |
|---|---|---|
| `claim_id` | INTEGER | Unique identifier (PK) |
| `policyholder_id` | INTEGER | References `policyholders.policyholder_id` |
| `claim_amount` | DECIMAL(10,2) | Claim amount in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE policyholders (
    policyholder_id INTEGER PRIMARY KEY,
    name VARCHAR(60)
);

CREATE TABLE claims (
    claim_id INTEGER PRIMARY KEY,
    policyholder_id INTEGER,
    claim_amount DECIMAL(10,2)
);

INSERT INTO policyholders (policyholder_id, name) VALUES
(1, 'Suhas Kelkar'), (2, 'Ritika Anand'), (3, 'Gopal Krishnan');

INSERT INTO claims (claim_id, policyholder_id, claim_amount) VALUES
(1, 1, 15000.00), (2, 1, 8000.00), (3, 3, 22000.00);
```

**Your Task:** Write the query you'd recommend, and explain what goes wrong with a plain `INNER JOIN` (no `DISTINCT`) here — Suhas Kelkar has filed two claims.

**Solution Query (recommended)**

```sql
SELECT p.name
FROM policyholders p
WHERE EXISTS (SELECT 1 FROM claims c WHERE c.policyholder_id = p.policyholder_id)
ORDER BY p.name;
```

**Output**

```
+----------------+
|      name      |
+----------------+
| Gopal Krishnan |
| Suhas Kelkar   |
+----------------+
```

**Justification:** A plain `INNER JOIN` without `DISTINCT` — `SELECT p.name FROM policyholders p INNER JOIN claims c ON p.policyholder_id = c.policyholder_id` — actually returns Suhas Kelkar *twice*, once per claim, exactly the fan-out from Q9. Adding `DISTINCT` papers over it, but it's solving a problem the query created for itself: it joins in claim data it never needed, purely to check "does at least one exist," then has to deduplicate the mess afterward. `WHERE EXISTS` states the actual intent directly — "does a matching claim exist for this policyholder" — and structurally can never produce duplicate rows in the first place, since it only checks for existence and never actually pulls in claim rows to multiply against. It's also typically the more efficient plan, since the database can stop searching the moment it finds one matching claim, rather than needing to find and later discard every matching row.

## Q12. Which Engineer Owns Which Bug

**Topic Tag:** Why Joins Exist?
**Difficulty:** Medium

| `exhibit_name` | VARCHAR(60) | Exhibit name |
| `curator_id` | INTEGER | References `curators.curator_id`, `NULL` if not yet assigned a curator |

```sql

FROM curators c
RIGHT JOIN exhibits_cur e ON c.curator_id = e.curator_id
ORDER BY e.exhibit_name;
```

```sql
CREATE TABLE curators (
    curator_id INTEGER PRIMARY KEY,

INSERT INTO exhibits_cur (exhibit_id, exhibit_name, curator_id) VALUES
```

```sql
FROM exhibits_cur e
```

```
+---------------+---------------------+
```

```sql
(1, 'Vasant Rao', NULL),
(2, 'Aditi Rao', 1),
(3, 'Nikhil Rao', 1);
```

**Output**

```
+------------+------------+
|   child    |   parent   |
+------------+------------+
| Aditi Rao  | Vasant Rao |
| Nikhil Rao | Vasant Rao |
+------------+------------+
```

**Solution Query**


*Vasant Rao himself never appears as a "child" in this result — `INNER JOIN` here means only people who actually have a recorded parent show up at all, which is correct for this specific report, but worth noticing: an `INNER` self-join silently drops root-level records with a `NULL` reference column.*

## Q29. The Anti-Join That Excluded Everyone

**Topic Tag:** Semi Joins and Anti Joins
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (`NOT IN` with a NULL-containing subquery)

**Problem Statement**

An employee referral program wants a list of employees who have never referred anyone, to nudge them about the referral bonus. Not every hire came through a referral — one hire has `referred_by` as `NULL`. A query using `NOT IN` is coming back completely empty, even though two employees clearly haven't referred anyone.

**Table: `employees_ref`**

| Column | Type | Description |
|---|---|---|
| `employee_id` | INTEGER | Unique identifier (PK) |
| `employee_name` | VARCHAR(60) | Employee's name |

**Table: `referral_hires`**

| Column | Type | Description |
|---|---|---|
| `hire_id` | INTEGER | Unique identifier (PK) |
| `referred_by` | INTEGER | References `employees_ref.employee_id`, `NULL` if not a referral hire |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE employees_ref (
    employee_id INTEGER PRIMARY KEY,
    employee_name VARCHAR(60)
);

CREATE TABLE referral_hires (
    hire_id INTEGER PRIMARY KEY,
    referred_by INTEGER
);

INSERT INTO employees_ref (employee_id, employee_name) VALUES
(1, 'Rakesh Iyer'), (2, 'Simran Kaur'), (3, 'Aditya Menon');

INSERT INTO referral_hires (hire_id, referred_by) VALUES
(1, 1), (2, NULL);
```

**Buggy Query (as submitted)**

```sql
SELECT employee_name
FROM employees_ref
WHERE employee_id NOT IN (SELECT referred_by FROM referral_hires);
```

**Buggy Output**

```
+----------------+
| employee_name  |
+----------------+
+----------------+
(0 rows — every employee was excluded, including Simran Kaur and Aditya Menon who have clearly never referred anyone)
```

**What's Wrong:** This is the `NOT IN` + `NULL` trap from the filtering chapter, resurfacing in a join-shaped query: the subquery `(SELECT referred_by FROM referral_hires)` includes a genuine `NULL` (from the hire with no referrer). The moment any `NULL` is present in a `NOT IN` list, the entire comparison collapses to `UNKNOWN` for every row, emptying the result completely — not just excluding the row tied to the `NULL`.

**Solution Query (Fixed)**

```sql
SELECT e.employee_name
FROM employees_ref e
WHERE NOT EXISTS (SELECT 1 FROM referral_hires r WHERE r.referred_by = e.employee_id)
ORDER BY e.employee_name;
```

**Fixed Output**

```
+---------------+
| employee_name |
+---------------+
| Aditya Menon  |
| Simran Kaur   |
+---------------+
```

*`NOT EXISTS` (an anti-join) never falls into this trap — it asks "does a matching row exist," a question that a `NULL` in the other table simply answers "no" to, rather than "unknown" for the whole list.*

## Q30. Tickets That Were Never Escalated

**Topic Tag:** Semi Joins and Anti Joins
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values (LEFT JOIN + IS NULL vs. NOT EXISTS)

**Problem Statement**

A call center wants tickets that have never been escalated, for a "resolved without escalation" success metric. Two patterns are both commonly used for this: `LEFT JOIN ... WHERE right_table.key IS NULL`, and `WHERE NOT EXISTS (...)`. You've been asked to write both and explain which one to standardize on going forward.

**Table: `tickets_cc`**

| Column | Type | Description |
|---|---|---|
| `ticket_id` | INTEGER | Unique identifier (PK) |
| `subject` | VARCHAR(80) | Ticket subject |

**Table: `escalations`**

| Column | Type | Description |
|---|---|---|
| `escalation_id` | INTEGER | Unique identifier (PK) |
| `ticket_id` | INTEGER | References `tickets_cc.ticket_id` |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE tickets_cc (
    ticket_id INTEGER PRIMARY KEY,
    subject VARCHAR(80)
);

CREATE TABLE escalations (
    escalation_id INTEGER PRIMARY KEY,
    ticket_id INTEGER
);

INSERT INTO tickets_cc (ticket_id, subject) VALUES
(1, 'Billing discrepancy'), (2, 'Password reset'), (3, 'Service outage');

INSERT INTO escalations (escalation_id, ticket_id) VALUES
(1, 3);
```

**LEFT JOIN + IS NULL version**

```sql
SELECT t.subject
FROM tickets_cc t
LEFT JOIN escalations e ON t.ticket_id = e.ticket_id
WHERE e.ticket_id IS NULL
ORDER BY t.subject;
```

**NOT EXISTS version**

```sql
SELECT t.subject
FROM tickets_cc t
WHERE NOT EXISTS (SELECT 1 FROM escalations e WHERE e.ticket_id = t.ticket_id)
ORDER BY t.subject;
```

**Output (identical for both)**

```
+----------------------+
|       subject        |
+----------------------+
| Billing discrepancy  |
| Password reset       |
+----------------------+
```

**Justification:** Both produce identical results here and are widely used interchangeably — the deciding factors are safety and intent, not correctness. `NOT EXISTS` reads as a direct statement of intent ("no matching escalation exists") and is immune to a subtle trap the `LEFT JOIN` version carries if written slightly differently: filtering on `e.escalation_id IS NULL` would still work, but filtering on the *wrong* column from the right-hand table (or forgetting the `IS NULL` filter entirely and getting a plain `LEFT JOIN`) is an easy, silent mistake — and reaching for `NOT IN` instead of either pattern reintroduces Q29's `NULL` trap. `NOT EXISTS` is generally the recommended default for anti-joins for exactly this reason: it says what's meant, and it structurally can't fall into the `NOT IN` + `NULL` trap the way a careless rewrite of either alternative can.
