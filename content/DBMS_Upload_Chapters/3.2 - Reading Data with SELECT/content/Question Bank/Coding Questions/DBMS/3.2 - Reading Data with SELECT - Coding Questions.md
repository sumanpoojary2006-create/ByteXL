# Reading Data with SELECT — Coding Question Bank

Dialect: **PostgreSQL**. Every query in this bank has been executed against a live PostgreSQL 16 instance; the `Output` shown for each question is the actual result, not a hand-typed guess.

**Question Types used in this bank:**
- **Write the Query** — the classic format: a problem statement, a schema, and you write the query.
- **Bug Hunt** — a query someone already wrote is shown along with its (wrong) output; find and fix the mistake.
- **Predict the Output** — a query is already written; state exactly what it returns before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; write the better one and explain why.
- **Reverse Engineering** — you're shown the data and the target result; work out the query that produces it.
- **Decision-Making** — a concrete symptom is shown; diagnose the cause and recommend a fix.

## Q1. Boarding Pass Kiosk

**Topic Tag:** The SELECT Statement
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A regional airline is setting up self-service boarding kiosks. To keep the kiosk screen uncluttered, it should show only the passenger's name and their assigned seat — nothing about fares or flight numbers.

| `fare_class` | VARCHAR(20) | Economy / Premium Economy / Business |

## Q4. The Three Ashas

**Topic Tag:** DISTINCT: Removing Duplicate Rows
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Validate (case sensitivity)

**Problem Statement**

An ed-tech platform's admin console lets staff pull a distinct list of student emails before sending a batch notification. One staff member notices the same student, Asha Rao, appears to have signed up three times with slightly different-looking emails, and wants to know whether `DISTINCT` will quietly collapse them into one.

**Table: `students`**

| Column | Type | Description |
|---|---|---|
| `student_id` | INTEGER | Unique identifier (PK) |
| `full_name` | VARCHAR(60) | Student's name |
| `email` | VARCHAR(80) | Student's registered email |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE students (
    student_id INTEGER PRIMARY KEY,
    full_name VARCHAR(60),
    email VARCHAR(80)
);

INSERT INTO students (student_id, full_name, email) VALUES
(1, 'Asha Rao', 'asha.rao@mailbox.com'),
(2, 'Asha Rao', 'Asha.Rao@mailbox.com'),
(3, 'Karthik Iyer', 'karthik.i@mailbox.com'),
(4, 'Asha Rao', 'ASHA.RAO@MAILBOX.COM'),
(5, 'Meena Pillai', 'meena.p@mailbox.com');
```

**Query to Analyze**

```sql
SELECT DISTINCT email
FROM students
ORDER BY email;
```

**Your Task:** Before running it, decide — how many rows will this return, and will the three "Asha Rao" emails collapse into one?

**Answer**

```
+------------------------+
|         email          |
+------------------------+
| ASHA.RAO@MAILBOX.COM   |
| Asha.Rao@mailbox.com   |
| asha.rao@mailbox.com   |
| karthik.i@mailbox.com  |
| meena.p@mailbox.com    |
+------------------------+
(5 rows)
```

**Why:** `DISTINCT` compares text byte-for-byte in PostgreSQL — it does not normalize case. `asha.rao@`, `Asha.Rao@`, and `ASHA.RAO@` are three different strings as far as SQL is concerned, so all three survive. Collapsing them would require an explicit `LOWER(email)` in the query, not plain `DISTINCT`.

## Q6. The Vanishing Discount

**Topic Tag:** Expressions and Calculated Columns
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (NULL propagation)

**Problem Statement**

A boutique hotel's front office wrote a query to show each guest's total payable amount after their negotiated discount. Guests who didn't negotiate a discount have `discount_pct` left as `NULL` — but the front office is confused: those guests' totals are showing up blank instead of the full price.

**Table: `hotel_bookings`**

| Column | Type | Description |
|---|---|---|
| `booking_id` | INTEGER | Unique identifier (PK) |
| `guest_name` | VARCHAR(60) | Guest's name |
| `nightly_rate` | DECIMAL(8,2) | Rate per night in ₹ |
| `nights` | INTEGER | Number of nights booked |
| `discount_pct` | DECIMAL(5,2) | Negotiated discount, `NULL` if none |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE hotel_bookings (
    booking_id INTEGER PRIMARY KEY,
    guest_name VARCHAR(60),
    nightly_rate DECIMAL(8,2),
    nights INTEGER,
    discount_pct DECIMAL(5,2)
);

INSERT INTO hotel_bookings (booking_id, guest_name, nightly_rate, nights, discount_pct) VALUES
(1, 'Aditi Kapoor', 4200.00, 3, 10.00),
(2, 'Vikram Shetty', 3600.00, 2, NULL),
(3, 'Neha Bhatt', 5000.00, 4, 15.00),
(4, 'Rajeev Nambiar', 3900.00, 1, NULL);
```

**Buggy Query (as submitted by the front office)**

```sql
SELECT guest_name,
       ROUND(nightly_rate * nights * (1 - discount_pct / 100), 2) AS total_payable
FROM hotel_bookings;
```

**Buggy Output**

```
+----------------+---------------+
|   guest_name   | total_payable |
+----------------+---------------+
| Aditi Kapoor   |      11340.00 |
| Vikram Shetty  |        ¤NULL¤ |
| Neha Bhatt     |      17000.00 |
| Rajeev Nambiar |        ¤NULL¤ |
+----------------+---------------+
```

**What's Wrong:** Any arithmetic expression involving a `NULL` value evaluates to `NULL` in SQL. Since `discount_pct` is `NULL` for guests with no negotiated discount, `1 - discount_pct / 100` becomes `NULL`, and the whole `total_payable` calculation collapses to `NULL` — instead of falling back to the full, undiscounted price.

**Solution Query (Fixed)**

```sql
SELECT guest_name,
       ROUND(nightly_rate * nights * (1 - COALESCE(discount_pct, 0) / 100), 2) AS total_payable
FROM hotel_bookings;
```

**Correct Output**

```
+----------------+---------------+
|   guest_name   | total_payable |
+----------------+---------------+
| Aditi Kapoor   |      11340.00 |
| Vikram Shetty  |       7200.00 |
| Neha Bhatt     |      17000.00 |
| Rajeev Nambiar |       3900.00 |
+----------------+---------------+
```

(3, 'Mughal Miniatures', 'Heritage', 2100),

## Q8. Price on Request

**Topic Tag:** Sorting Results
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (NULL ordering)

**Problem Statement**

A real-estate portal lists properties by price, cheapest first. Two of the listings have no `price` yet because the sellers want buyers to enquire directly. An intern is about to run the standard "sort by price" query and isn't sure where those two listings will land in the results.

**Table: `listings`**

| Column | Type | Description |
|---|---|---|
| `listing_id` | INTEGER | Unique identifier (PK) |
| `address` | VARCHAR(80) | Property address |
| `price` | DECIMAL(12,2) | Asking price in ₹, `NULL` if "price on request" |
| `bedrooms` | INTEGER | Number of bedrooms |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE listings (
    listing_id INTEGER PRIMARY KEY,
    address VARCHAR(80),
    price DECIMAL(12,2),
    bedrooms INTEGER
);

INSERT INTO listings (listing_id, address, price, bedrooms) VALUES
(1, '12 Lake View Road', 8500000.00, 3),
(2, '45 Palm Grove Street', NULL, 4),
(3, '9 Hill Crest Avenue', 6200000.00, 2),
(4, '78 Garden City Lane', NULL, 3),
(5, '3 Riverside Colony', 7300000.00, 3);
```

**Query to Analyze**

```sql
SELECT address, price
FROM listings
ORDER BY price;
```

**Your Task:** Predict the row order, specifically — do the two `NULL`-priced listings appear first, last, or somewhere in between?

**Answer**

```
+----------------------+------------+
|       address        |   price    |
+----------------------+------------+
| 9 Hill Crest Avenue  | 6200000.00 |
| 3 Riverside Colony   | 7300000.00 |
| 12 Lake View Road    | 8500000.00 |
| 45 Palm Grove Street |     ¤NULL¤ |
| 78 Garden City Lane  |     ¤NULL¤ |
+----------------------+------------+
(5 rows)
```

**Why:** PostgreSQL treats `NULL` as "unknown," and by default `ORDER BY ... ASC` places `NULL`s **last**, after every known value — never first and never mixed in by numeric value. To force `NULL`s first instead, the query would need an explicit `ORDER BY price NULLS FIRST`.

## Q26. Sorting by Clinical Priority, Not the Alphabet

**Topic Tag:** Sorting Results
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values

**Problem Statement**

A hospital's triage queue labels each waiting patient `'High'`, `'Medium'`, or `'Low'` severity. A junior staffer sorted the queue with a plain `ORDER BY severity_label` and was alarmed to see a `'Low'`-severity patient placed ahead of every `'Medium'`-severity one.

**Table: `patients_queue`**

| Column | Type | Description |
|---|---|---|
| `patient_id` | INTEGER | Unique identifier (PK) |
| `patient_name` | VARCHAR(60) | Patient's name |
| `severity_label` | VARCHAR(10) | 'High', 'Medium', or 'Low' |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE patients_queue (
    patient_id INTEGER PRIMARY KEY,
    patient_name VARCHAR(60),
    severity_label VARCHAR(10)
);

INSERT INTO patients_queue (patient_id, patient_name, severity_label) VALUES
(1, 'Harish Bhandari', 'Low'),
(2, 'Ismat Fatima', 'High'),
(3, 'Colin D''Souza', 'Medium'),
(4, 'Preeti Saxena', 'High'),
(5, 'Tarun Grover', 'Low');
```

**Naive Query (alphabetical — what the junior staffer ran)**

```sql
SELECT patient_name, severity_label
FROM patients_queue
ORDER BY severity_label;
```

**Naive Output**

```
+-----------------+----------------+
|  patient_name   | severity_label |
+-----------------+----------------+
| Ismat Fatima    | High           |
| Preeti Saxena   | High           |
| Harish Bhandari | Low            |
| Tarun Grover    | Low            |
| Colin D'Souza   | Medium         |
+-----------------+----------------+
```

**Your Task:** Plain alphabetical order puts `'High'` first only by coincidence — `'Low'` still lands ahead of `'Medium'`, which is clinically backwards. Write a query that sorts strictly by true priority (High, then Medium, then Low), and explain why a plain `ORDER BY severity_label` can't be trusted for this.

**Solution Query**

```sql
SELECT patient_name, severity_label
FROM patients_queue
ORDER BY CASE severity_label
             WHEN 'High' THEN 1
             WHEN 'Medium' THEN 2
             WHEN 'Low' THEN 3
         END;
```

**Output**

```
+-----------------+----------------+
|  patient_name   | severity_label |
+-----------------+----------------+
| Ismat Fatima    | High           |
| Preeti Saxena   | High           |
| Colin D'Souza   | Medium         |
| Harish Bhandari | Low            |
| Tarun Grover    | Low            |
+-----------------+----------------+
```

**Justification:** `ORDER BY severity_label` sorts the *text* alphabetically, and there's no reason a text label's alphabetical order has to match its real-world priority — here it happens to work for `'High'` but breaks between `'Low'` and `'Medium'`. A `CASE` expression inside `ORDER BY` maps each label to an explicit priority number, so the sort follows the business meaning of the label instead of its spelling.

## Q28. The Runner-Up Offer

**Topic Tag:** Limiting Results
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values

**Problem Statement**

A hiring manager wants to know the second-highest salary offer extended for a role, to use as a benchmark for the next negotiation. One recruiter suggests `ORDER BY offer_amount DESC LIMIT 2` and just reading off the last row; another suggests `ORDER BY offer_amount DESC LIMIT 1 OFFSET 1`. You need to pick the one that reliably returns *only* the second-highest offer as a single-row result, and explain the difference.

**Table: `job_offers`**

| Column | Type | Description |
|---|---|---|
| `offer_id` | INTEGER | Unique identifier (PK) |
| `candidate_name` | VARCHAR(60) | Candidate's name |
| `offer_amount` | DECIMAL(10,2) | Offer amount in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE job_offers (
    offer_id INTEGER PRIMARY KEY,
    candidate_name VARCHAR(60),
    offer_amount DECIMAL(10,2)
);

INSERT INTO job_offers (offer_id, candidate_name, offer_amount) VALUES
(1, 'Nitin Kapoor', 1450000.00),
(2, 'Sarita Menon', 1620000.00),
(3, 'Waseem Akhtar', 1580000.00),
(4, 'Bhavna Iyer', 1390000.00);
```

**Your Task:** Write the query that returns exactly one row — the second-highest offer — and explain why `LIMIT 2` alone isn't the right tool for that.

**Solution Query**

```sql
SELECT candidate_name, offer_amount
FROM job_offers
ORDER BY offer_amount DESC
LIMIT 1 OFFSET 1;
```

**Output**

```
+----------------+--------------+
| candidate_name | offer_amount |
+----------------+--------------+
| Waseem Akhtar  |   1580000.00 |
+----------------+--------------+
```

**Justification:** `ORDER BY offer_amount DESC LIMIT 2` returns the *top two* rows as a two-row result — getting the second-highest out of that still requires the application code to discard the first row and read the second, which is extra work and easy to get backwards. `LIMIT 1 OFFSET 1` asks the database to skip the single highest row and hand back exactly one row — the second-highest — directly, with nothing further to trim on the client side.

## Q29. A Tie at the Top

**Topic Tag:** Limiting Results
**Difficulty:** Hard
**Type:** Predict the Output
**Skill Focus:** Analyse (ties, determinism)

**Problem Statement**

A parking garage's operator dashboard shows the single longest-parked vehicle currently on site, to flag it for a courtesy call. Tonight, two vehicles happen to have parked for exactly the same duration. The on-call engineer wants to know whether the dashboard's `LIMIT 1` query will reliably show the *same* one of those two vehicles every time it refreshes.

**Table: `parking_sessions`**

| Column | Type | Description |
|---|---|---|
| `session_id` | INTEGER | Unique identifier (PK) |
| `vehicle_plate` | VARCHAR(15) | Vehicle's plate number |
| `duration_minutes` | INTEGER | Minutes parked so far |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE parking_sessions (
    session_id INTEGER PRIMARY KEY,
    vehicle_plate VARCHAR(15),
    duration_minutes INTEGER
);

INSERT INTO parking_sessions (session_id, vehicle_plate, duration_minutes) VALUES
(1, 'KA01AB1234', 340),
(2, 'MH12CD5678', 480),
(3, 'DL08EF9012', 480),
(4, 'TN09GH3456', 210);
```

**Query to Analyze**

```sql
SELECT vehicle_plate, duration_minutes
FROM parking_sessions
ORDER BY duration_minutes DESC
LIMIT 1;
```

**Your Task:** `MH12CD5678` and `DL08EF9012` are tied at 480 minutes. Is this query guaranteed to always return the same one of the two, refresh after refresh?

**Answer**

```
+---------------+------------------+
| vehicle_plate | duration_minutes |
+---------------+------------------+
| MH12CD5678    |              480 |
+---------------+------------------+
```

**Why:** On this exact table right now, PostgreSQL happens to return `MH12CD5678`, but the query gives the database no instruction about how to break the tie — `ORDER BY duration_minutes DESC` alone doesn't say which of two equal values should come first. Either `MH12CD5678` or `DL08EF9012` is a defensible answer, and which one actually comes back is not guaranteed by the SQL itself; it can change after the table is updated, reindexed, or rewritten. A dashboard that must be reliably reproducible needs a tiebreaker column added, e.g. `ORDER BY duration_minutes DESC, session_id`.
