# Filtering Data — Coding Question Bank

Dialect: **PostgreSQL**. Every query in this bank has been executed against a live PostgreSQL 16 instance; the `Output` shown for each question is the actual result, not a hand-typed guess.

**Question Types used in this bank:**
- **Write the Query** — the classic format: a problem statement, a schema, and you write the query.
- **Bug Hunt** — a query someone already wrote is shown along with its (wrong) output; find and fix the mistake.
- **Predict the Output** — a query is already written; state exactly what it returns before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; write the better one and explain why.
- **Reverse Engineering** — you're shown the data and the target result; work out the query that produces it.
- **Decision-Making** — a concrete symptom is shown; diagnose the cause and recommend a fix.

## Q1. Above the Five Hundred Mark

**Topic Tag:** The WHERE Clause
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

An independent bookstore is curating a "Premium Picks" shelf display and wants a quick list of every title priced above ₹500.

| Column | Type | Description |
|---|---|---|
| `book_id` | INTEGER | Unique identifier (PK) |
| `title` | VARCHAR(80) | Book title |
| `author` | VARCHAR(60) | Author's name |
| `price` | DECIMAL(8,2) | Price in ₹ |

Write a query that returns the `title` and `author` of every book priced above ₹500.

| 1 | The Silent Orchard | Meher Kapadia | 620.00 |

**Sample Output**

| title | author |
|---|---|
| The Silent Orchard | Meher Kapadia |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE books_catalog (
    book_id INTEGER PRIMARY KEY,
    title VARCHAR(80),
```

```
+--------------------------+-----------------+

+--------------------------+-----------------+

| Monsoon Ledger           | Anita Fernandes |
| The Cartographer's Error | Leela Iyengar   |
```

```sql
SELECT title, author
FROM books_catalog
```

## Q4. The Expiry Boundary

**Topic Tag:** Comparison Operators
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Validate (strict boundary)

**Problem Statement**

An online pharmacy pulls a "must clear soon" list of medicines expiring before 1 June 2026. One of the medicines expires on *exactly* that date, and the pharmacist wants to know whether it will show up on the list.

**Table: `medicines`**

| Column | Type | Description |
|---|---|---|
| `medicine_id` | INTEGER | Unique identifier (PK) |
| `medicine_name` | VARCHAR(60) | Medicine name |
| `expiry_date` | DATE | Expiry date |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE medicines (
    medicine_id INTEGER PRIMARY KEY,
    medicine_name VARCHAR(60),
    expiry_date DATE
);

INSERT INTO medicines (medicine_id, medicine_name, expiry_date) VALUES
(1, 'Amoxiclav 625', '2026-05-15'),
(2, 'Paracetamol 650', '2026-06-01'),
(3, 'Cetrizine 10mg', '2026-07-20'),
(4, 'Metformin 500', '2026-04-10');
```

**Query to Analyze**

```sql
SELECT medicine_name, expiry_date
FROM medicines
WHERE expiry_date < '2026-06-01';
```

**Your Task:** Does "Paracetamol 650" (expiring exactly `2026-06-01`) appear in the result?

**Answer**

```
+---------------+-------------+
| medicine_name | expiry_date |
+---------------+-------------+
| Amoxiclav 625 | 2026-05-15  |
| Metformin 500 | 2026-04-10  |
+---------------+-------------+
(2 rows)
```

**Why:** `<` is a *strict* less-than comparison. A row whose `expiry_date` is exactly `2026-06-01` is neither before nor after the boundary — it's equal to it — so it's excluded. Only `<=` would have included it.

## Q8. One Character, Not Zero

**Topic Tag:** Pattern Matching
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Validate (underscore wildcard)

**Problem Statement**

A neighbourhood print shop's job queue is being filtered with the pattern `report_v1.pdf`, using `_` as a single-character wildcard. Before running it, the shop owner wants to know exactly which of today's four file names will match.

**Table: `print_jobs`**

| Column | Type | Description |
|---|---|---|
| `job_id` | INTEGER | Unique identifier (PK) |
| `file_name` | VARCHAR(60) | Submitted file name |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE print_jobs (
    job_id INTEGER PRIMARY KEY,
    file_name VARCHAR(60)
);

INSERT INTO print_jobs (job_id, file_name) VALUES
(1, 'report_v1.pdf'),
(2, 'reportAv1.pdf'),
(3, 'reportv1.pdf'),
(4, 'report_v10.pdf');
```

**Query to Analyze**

```sql
SELECT file_name
FROM print_jobs
WHERE file_name LIKE 'report_v1.pdf';
```

**Your Task:** Which file names match, and which don't? Pay attention to what `_` does and doesn't stand in for.

**Answer**

```
+---------------+
|   file_name   |
+---------------+
| report_v1.pdf |
| reportAv1.pdf |
+---------------+
(2 rows)
```

**Why:** `_` matches *exactly one* character, no more and no fewer. `report_v1.pdf` (the literal underscore) and `reportAv1.pdf` both have exactly one character in that slot, so both match — the underscore wildcard matches a literal underscore just as happily as any other single character. `reportv1.pdf` has *zero* characters there, so it fails to match. `report_v10.pdf` has an extra digit that throws off the fixed-length pattern entirely, so it also fails.

## Q10. The Comparison That Never Matches

**Topic Tag:** Working with NULL
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Compare Values

**Problem Statement**

A physiotherapy clinic wants a list of patients who haven't yet been assigned a therapist. One clinic assistant writes `WHERE therapist_name = NULL` and gets an empty list back, even though two patients clearly have no therapist assigned. You've been asked to fix the query and explain why the assistant's version can never work, no matter what data is in the table.

**Table: `physio_patients`**

| Column | Type | Description |
|---|---|---|
| `patient_id` | INTEGER | Unique identifier (PK) |
| `patient_name` | VARCHAR(60) | Patient's name |
| `therapist_name` | VARCHAR(60) | Assigned therapist, `NULL` if unassigned |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE physio_patients (
    patient_id INTEGER PRIMARY KEY,
    patient_name VARCHAR(60),
    therapist_name VARCHAR(60)
);

INSERT INTO physio_patients (patient_id, patient_name, therapist_name) VALUES
(1, 'Geeta Iyer', 'Dr. Nalini Rao'),
(2, 'Suresh Nair', NULL),
(3, 'Farida Sheikh', 'Dr. Ashok Bhide'),
(4, 'Pankaj Sood', NULL);
```

**Assistant's Query**

```sql
SELECT patient_name FROM physio_patients WHERE therapist_name = NULL;
```

**Assistant's Output**

```
+--------------+
| patient_name |
+--------------+
+--------------+
(0 rows)
```

**Your Task:** Write the query that actually returns the two unassigned patients, and explain why `= NULL` can never succeed.

**Solution Query**

```sql
SELECT patient_name
FROM physio_patients
WHERE therapist_name IS NULL;
```

**Output**

```
+--------------+
| patient_name |
+--------------+
| Suresh Nair  |
| Pankaj Sood  |
+--------------+
```

**Justification:** `NULL` represents "unknown," not a value that can equal or not equal anything — including itself. `therapist_name = NULL` doesn't evaluate to true or false; it evaluates to `UNKNOWN` for every row, and `WHERE` only keeps rows where the condition is `TRUE`, so an all-`UNKNOWN` comparison always yields zero rows. `IS NULL` is a dedicated test built specifically to check for "unknown," which `=` was never designed to do.

## Q30. The List That Poisoned Itself

**Topic Tag:** Working with NULL
**Difficulty:** Hard
**Type:** Predict the Output
**Skill Focus:** Analyse (`NOT IN` with `NULL`)

**Problem Statement**

An aquarium's tank-management tool filters out tanks whose `species_id` is in an exclusion list. One tank has never had its species identified, so its `species_id` is `NULL`. Someone assembled the exclusion list as `(3, 7, NULL)`, since a `NULL` naturally ended up in the list from unrelated code. Before running it, predict how many tanks this query returns.

**Table: `aquarium_tanks`**

| Column | Type | Description |
|---|---|---|
| `tank_id` | INTEGER | Unique identifier (PK) |
| `tank_name` | VARCHAR(40) | Tank name |
| `species_id` | INTEGER | Species identifier, `NULL` if not yet identified |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE aquarium_tanks (
    tank_id INTEGER PRIMARY KEY,
    tank_name VARCHAR(40),
    species_id INTEGER
);

INSERT INTO aquarium_tanks (tank_id, tank_name, species_id) VALUES
(1, 'Reef Tank A', 3),
(2, 'Reef Tank B', 7),
(3, 'Deep Tank C', 12),
(4, 'Quarantine Tank D', 5);
```

**Query to Analyze**

```sql
SELECT tank_name
FROM aquarium_tanks
WHERE species_id NOT IN (3, 7, NULL);
```

**Your Task:** "Deep Tank C" (species 12) and "Quarantine Tank D" (species 5) are both clearly not 3 or 7 — do they appear in the result?

**Answer**

```
+-----------+
| tank_name |
+-----------+
+-----------+
(0 rows)
```

**Why:** This is one of SQL's sharpest traps. `NOT IN (3, 7, NULL)` is really `<> 3 AND <> 7 AND <> NULL` under the hood. `species_id <> NULL` is `UNKNOWN` for every single row, no matter what `species_id` actually is — and `UNKNOWN AND anything` is never `TRUE`. So the *entire* `NOT IN` expression collapses to "never true" for every row the moment even one `NULL` sneaks into the list, silently emptying the whole result — not just excluding the row that's actually unidentified. The safe fix is either scrubbing `NULL`s out of the list before comparing, or using `NOT EXISTS` instead of `NOT IN`.
