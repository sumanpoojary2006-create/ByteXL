# Query Optimization — Coding Question Bank

Dialect: **PostgreSQL**. Every statement in this bank has been executed against a live PostgreSQL 16 instance — including `EXPLAIN` and `EXPLAIN ANALYZE` output, reproduced verbatim from real runs.

**A note on what's graded in this chapter:** `EXPLAIN` cost estimates and timings shift slightly across machines, PostgreSQL versions, and even repeated runs on the same machine — they're shown here exactly as the lessons show them, as real illustrative evidence of what a plan looks like, but they are never the graded answer. What's graded is always the deterministic, row-level result of a verification query. Several datasets in this bank use `generate_series` to build hundreds or thousands of rows, matching how the lessons themselves demonstrate plan behavior — a 3-row table rarely shows the difference between a sequential scan and an index scan in any meaningful way.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the statement (often a query plus supporting index).
- **Bug Hunt** — a statement or conclusion someone drew is shown to be wrong; find and fix the mistake.
- **Predict the Output** — a query or plan is already given; state exactly what happens before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; pick the better one and explain why.
- **Reverse Engineering** — you're shown a plan or a target result; work out the query or index behind it.
- **Decision-Making** — a concrete symptom or scenario is shown; diagnose it and recommend an approach.

# Set 1

## Q1. A Filter with No Index to Use

**Topic Tag:** Inside the Query Optimizer
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A bookstore's inventory table has 2,000 rows and no index on `price`. The optimizer has exactly one way to find rows matching a price filter: check every row. Write the query, and see what the optimizer's only available option looks like.

**Table: `bookstore_inventory_opt`**

| Column | Type | Description |
|---|---|---|
| `book_id` | INTEGER | Unique identifier (PK) |
| `title` | TEXT | Book title |
| `price` | NUMERIC(8,2) | Price in ₹ |

Write a query returning `title` and `price` for books priced at exactly ₹245.00, sorted by title.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE bookstore_inventory_opt (
    book_id INTEGER PRIMARY KEY,
    title TEXT,
    price NUMERIC(8,2)
);

INSERT INTO bookstore_inventory_opt (book_id, title, price)
SELECT i, 'Book Title ' || i, (10 + (i % 500))::NUMERIC(8,2)
FROM generate_series(1, 2000) AS i;
```

**Output**

```
+------------------+---------+
|      title       |  price  |
+------------------+---------+
| Book Title 1235  |  245.00 |
| Book Title 1735  |  245.00 |
| Book Title 235   |  245.00 |
| Book Title 735   |  245.00 |
+------------------+---------+
```

**Solution Query**

```sql
SELECT title, price
FROM bookstore_inventory_opt
WHERE price = 245.00
ORDER BY title;
```

**EXPLAIN (illustrative — no index exists on `price`)**

```
Seq Scan on bookstore_inventory_opt  (cost=0.00..39.00 rows=4 width=20)
  Filter: (price = 245.00)
```

*With no index on `price`, `Seq Scan` is the optimizer's only available strategy — it isn't a "bad" choice here, it's the *only* choice, since there's nothing sorted or structured to jump through. The row output above is correct regardless; the plan only describes how the database got there.*

## Q2. The Same Filter, with an Index

**Topic Tag:** Reading EXPLAIN
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

An orders table has 3,000 rows. Unlike Q1, this one has an index on `customer_id`. Create it, then look up one customer's order and read what strategy the optimizer picked this time.

**Table: `orders_opt`**

| Column | Type | Description |
|---|---|---|
| `order_id` | INTEGER | Unique identifier (PK) |
| `customer_id` | INTEGER | Customer identifier |
| `amount` | NUMERIC(10,2) | Order amount in ₹ |

Write a statement that creates an index on `customer_id`, then a query returning `amount` for `customer_id = 1500`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE orders_opt (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER,
    amount NUMERIC(10,2)
);

INSERT INTO orders_opt (order_id, customer_id, amount)
SELECT i, (i % 3000) + 1, (100 + (i % 900))::NUMERIC(10,2)
FROM generate_series(1, 3000) AS i;
```

**Output**

```
+---------+
| amount  |
+---------+
| 699.00  |
+---------+
```

**Solution Query**

```sql
CREATE INDEX idx_orders_customer ON orders_opt (customer_id);

SELECT amount FROM orders_opt WHERE customer_id = 1500;
```

**EXPLAIN (illustrative)**

```
Index Scan using idx_orders_customer on orders_opt  (cost=0.28..8.30 rows=1 width=5)
  Index Cond: (customer_id = 1500)
```

*Compare the cost range here (`0.28..8.30`) against Q1's (`0.00..39.00`) — not as an exact benchmark, but as a rough sense of scale: an index narrowing a search to one row is typically far cheaper than scanning every row in the table, especially as the table grows.*

## Q3. When the Index Gets Ignored

**Topic Tag:** Reading EXPLAIN
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (selectivity)

**Problem Statement**

An employees table has an index on `status`. 900 of 1,000 employees are `'Active'`; only 100 are `'Inactive'`. Before checking, predict whether the optimizer uses the index for *both* filters, or only one of them.

**Table: `employees_opt`**

| Column | Type | Description |
|---|---|---|
| `emp_id` | INTEGER | Unique identifier (PK) |
| `status` | TEXT | Active / Inactive |
| `salary` | NUMERIC(10,2) | Salary in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE employees_opt (
    emp_id INTEGER PRIMARY KEY,
    status TEXT,
    salary NUMERIC(10,2)
);

INSERT INTO employees_opt (emp_id, status, salary)
SELECT i, CASE WHEN i <= 900 THEN 'Active' ELSE 'Inactive' END, (40000 + (i % 50) * 1000)::NUMERIC(10,2)
FROM generate_series(1, 1000) AS i;

CREATE INDEX idx_emp_status ON employees_opt (status);
```

**Query to Analyze**

```sql
SELECT emp_id FROM employees_opt WHERE status = 'Inactive';  -- 10% of rows
SELECT emp_id FROM employees_opt WHERE status = 'Active';    -- 90% of rows
```

**Your Task:** Both queries have `idx_emp_status` available. Does the optimizer use it for both?

**Answer**

```
+-----------+-----+
|  status   | cnt |
+-----------+-----+
| Active    | 900 |
| Inactive  | 100 |
+-----------+-----+
```

**EXPLAIN — `status = 'Inactive'` (illustrative)**

```
Index Scan using idx_emp_status on employees_opt  (cost=0.15..9.90 rows=100 width=4)
  Index Cond: (status = 'Inactive'::text)
```

**EXPLAIN — `status = 'Active'` (illustrative)**

```
Seq Scan on employees_opt  (cost=0.00..19.50 rows=900 width=4)
  Filter: (status = 'Active'::text)
```

**Why:** The optimizer only picks the index for `'Inactive'`, even though the exact same index exists for both queries. Fetching 900 out of 1,000 rows *through* an index means bouncing between the index structure and the table for nearly every single row — often more expensive overall than simply reading the table straight through once. This is why "having an index" doesn't guarantee it gets used: the optimizer weighs the *estimated* cost of every available strategy for this specific query and picks the cheapest one, and a low-selectivity filter frequently makes the plain sequential scan the actual winner.

## Q4. Reading the Real Timing

**Topic Tag:** Reading EXPLAIN ANALYZE
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

`EXPLAIN` alone only estimates. `EXPLAIN ANALYZE` actually runs the query and reports genuine elapsed time and genuine row counts alongside the plan. Run it for a `SELECT` (always safe, since nothing is being modified) and separately confirm the result with a plain query.

**Table:** `employees_opt` *(same table as Q3)*

Write a query counting inactive employees, and separately run `EXPLAIN ANALYZE` on the underlying filter to see the real numbers.

**Output**

```
+-----------------+
| inactive_count  |
+-----------------+
|             100 |
+-----------------+
```

**Solution Query**

```sql
SELECT COUNT(*) AS inactive_count FROM employees_opt WHERE status = 'Inactive';
```

**EXPLAIN ANALYZE (illustrative)**

```
Index Scan using idx_emp_status on employees_opt  (cost=0.15..9.90 rows=100 width=4) (actual time=0.012..0.020 rows=100 loops=1)
  Index Cond: (status = 'Inactive'::text)
Planning Time: 0.009 ms
Execution Time: 0.025 ms
```

*Notice `rows=100` appears twice — once as the planner's estimate (before the `actual time=...` parenthetical) and once as the genuinely observed `rows=100` inside it. Here they match closely; Q19 later in this bank shows a case where they don't.*

## Q5. EXPLAIN ANALYZE Actually Ran That DELETE

**Topic Tag:** Reading EXPLAIN ANALYZE
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (EXPLAIN ANALYZE executes writes for real)

**Problem Statement**

An engineer wanted to preview how a cleanup `DELETE` would perform before running it "for real," and reached for `EXPLAIN ANALYZE` assuming it was a safe, read-only preview — the same instinct as running plain `EXPLAIN`. It wasn't safe at all.

**Table: `temp_cleanup_opt`**

| Column | Type | Description |
|---|---|---|
| `row_id` | INTEGER | Unique identifier (PK) |
| `status` | TEXT | Row status |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE temp_cleanup_opt (
    row_id INTEGER PRIMARY KEY,
    status TEXT
);

INSERT INTO temp_cleanup_opt (row_id, status) VALUES
(1, 'stale'), (2, 'stale'), (3, 'keep');
```

**Before**

```
+---------+---------+
| row_id  | status  |
+---------+---------+
|       1 | stale   |
|       2 | stale   |
|       3 | keep    |
+---------+---------+
```

**Buggy Statement (as run "just to preview it")**

```sql
EXPLAIN ANALYZE DELETE FROM temp_cleanup_opt WHERE status = 'stale';
```

**Buggy Output**

```
Delete on temp_cleanup_opt  (cost=0.00..25.88 rows=0 width=0) (actual time=0.006..0.006 rows=0 loops=1)
  ->  Seq Scan on temp_cleanup_opt  (cost=0.00..25.88 rows=6 width=6) (actual time=0.002..0.003 rows=2 loops=1)
        Filter: (status = 'stale'::text)
        Rows Removed by Filter: 1
Planning Time: 0.011 ms
Execution Time: 0.249 ms
```

**What's Wrong:** `EXPLAIN ANALYZE` doesn't simulate a query — the "ANALYZE" part specifically means "actually execute this and measure the real thing." For a `SELECT`, that's harmless: running it and throwing away the result changes nothing. For a `DELETE` (or `UPDATE`, or `INSERT`), "actually execute this" means the rows genuinely get deleted, exactly as if `EXPLAIN ANALYZE` weren't there at all — the plan output is just extra information layered on top of a real write.

**After (the rows are genuinely gone — this can't be undone by re-reading)**

```
+---------+---------+
| row_id  | status  |
+---------+---------+
|       3 | keep    |
+---------+---------+
```

**Recommended Practice:** To preview a destructive statement's plan without the side effect, either use plain `EXPLAIN` (no `ANALYZE`, estimate-only, always safe) or wrap the real thing in a transaction that gets rolled back: `BEGIN; EXPLAIN ANALYZE DELETE ...; ROLLBACK;` — the same transaction-as-safety-net pattern from the Modifying Data chapter's discipline lesson, applied here to protect against a genuinely destructive diagnostic tool.

## Q6. Joining a Small Table to a Larger One

**Topic Tag:** Join Algorithms
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A 3-row region lookup table is joined to a 1,500-row sales table, filtered down to one specific sale. With so few rows to match against, expect the optimizer to reach for a simple, direct strategy rather than anything elaborate.

**Table: `regions_opt`**

| Column | Type | Description |
|---|---|---|
| `region_id` | INTEGER | Unique identifier (PK) |
| `region_name` | TEXT | Region name |

**Table: `sales_opt`**

| Column | Type | Description |
|---|---|---|
| `sale_id` | INTEGER | Unique identifier (PK) |
| `region_id` | INTEGER | References `regions_opt.region_id` |
| `amount` | NUMERIC(10,2) | Sale amount in ₹ |

Write a query joining the two tables for `sale_id = 100`, returning `region_name` and `amount`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE regions_opt (
    region_id INTEGER PRIMARY KEY,
    region_name TEXT
);

CREATE TABLE sales_opt (
    sale_id INTEGER PRIMARY KEY,
    region_id INTEGER,
    amount NUMERIC(10,2)
);

INSERT INTO regions_opt (region_id, region_name) VALUES (1, 'North'), (2, 'South'), (3, 'East');

INSERT INTO sales_opt (sale_id, region_id, amount)
SELECT i, (i % 3) + 1, (500 + (i % 200))::NUMERIC(10,2)
FROM generate_series(1, 1500) AS i;
```

**Output**

```
+--------------+---------+
| region_name  | amount  |
+--------------+---------+
| South        | 600.00  |
+--------------+---------+
```

**Solution Query**

```sql
SELECT r.region_name, s.amount
FROM regions_opt r
JOIN sales_opt s ON r.region_id = s.region_id
WHERE s.sale_id = 100;
```

**EXPLAIN (illustrative)**

```
Nested Loop  (cost=0.28..9.36 rows=1 width=10)
  Join Filter: (r.region_id = s.region_id)
  ->  Index Scan using sales_opt_pkey on sales_opt s  (cost=0.28..8.29 rows=1 width=9)
        Index Cond: (sale_id = 100)
  ->  Seq Scan on regions_opt r  (cost=0.00..1.03 rows=3 width=9)
```

*A `Nested Loop` finds the one matching sale first (via its primary key), then checks all 3 regions to find the match — with so few rows on one side, looping is cheap and direct, no elaborate hashing or sorting needed.*

## Q7. Joining Two Sizeable Tables with No Filter

**Topic Tag:** Join Algorithms
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (Hash Join)

**Problem Statement**

The same two tables from Q6, but this time joined with *no* filtering `WHERE` clause at all — every row on both sides genuinely needs to be matched up. Before running it, predict whether the optimizer sticks with the same nested-loop strategy or switches approaches.

**Tables:** `regions_opt`, `sales_opt` *(same as Q6)*

**Query to Analyze**

```sql
SELECT COUNT(*) FROM regions_opt r JOIN sales_opt s ON r.region_id = s.region_id;
```

**Your Task:** Predict the count, and predict whether this uses the same `Nested Loop` strategy as Q6.

**Answer**

```
+--------+
| count  |
+--------+
|  1500  |
+--------+
```

**EXPLAIN (illustrative)**

```
Aggregate  (cost=38.32..38.33 rows=1 width=8)
  ->  Hash Join  (cost=1.07..34.57 rows=1500 width=0)
        Hash Cond: (s.region_id = r.region_id)
        ->  Seq Scan on sales_opt s  (cost=0.00..24.00 rows=1500 width=4)
        ->  Hash  (cost=1.03..1.03 rows=3 width=4)
              ->  Seq Scan on regions_opt r  (cost=0.00..1.03 rows=3 width=4)
```

**Why:** All 1,500 sales rows genuinely match a region (every `region_id` in `sales_opt` exists in `regions_opt`), so the count is 1500. The plan switches to a `Hash Join`: with no filter narrowing either side down, a nested loop re-scanning `regions_opt` up to 1,500 times would be wasteful. Instead, the tiny `regions_opt` table is built once into an in-memory hash table (`Hash`), and `sales_opt` is scanned exactly once, probing the hash table for each row — one pass per table total, rather than one pass per matching attempt.

## Q8. Replacing a Query-per-Author Loop

**Topic Tag:** Common Bottlenecks: Missing Indexes, N+1 Queries, Large Scans
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Compare Values (N+1 elimination)

**Problem Statement**

An application loop fetches each author's books with a separate query per author — fine for 2 authors, but the same pattern run against 10,000 authors means 10,000 round trips to the database. Replace the loop with one query.

**Table: `authors_opt`**

| Column | Type | Description |
|---|---|---|
| `author_id` | INTEGER | Unique identifier (PK) |
| `author_name` | TEXT | Author's name |

**Table: `books_opt`**

| Column | Type | Description |
|---|---|---|
| `book_id` | INTEGER | Unique identifier (PK) |
| `author_id` | INTEGER | References `authors_opt.author_id` |
| `title` | TEXT | Book title |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE authors_opt (
    author_id INTEGER PRIMARY KEY,
    author_name TEXT
);

CREATE TABLE books_opt (
    book_id INTEGER PRIMARY KEY,
    author_id INTEGER,
    title TEXT
);

INSERT INTO authors_opt VALUES (1, 'Meher Kapadia'), (2, 'Devraj Sen');
INSERT INTO books_opt VALUES (1, 1, 'The Silent Orchard'), (2, 1, 'Monsoon Ledger'), (3, 2, 'Paper Boats');
```

**N+1 Pattern (the loop being replaced — one query per author)**

```sql
SELECT title FROM books_opt WHERE author_id = 1;
SELECT title FROM books_opt WHERE author_id = 2;
```

**Output**

```
+-----------------+--------------------+
|  author_name    |       title        |
+-----------------+--------------------+
| Devraj Sen      | Paper Boats        |
| Meher Kapadia   | Monsoon Ledger     |
| Meher Kapadia   | The Silent Orchard |
+-----------------+--------------------+
```

**Solution Query**

```sql
SELECT a.author_name, b.title
FROM authors_opt a
JOIN books_opt b ON a.author_id = b.author_id
ORDER BY a.author_name, b.title;
```

*This "N+1" pattern — 1 query to get the list, then N more queries, one per item — is one of the most common real-world performance bugs, and it's invisible in application code that just looks like an innocent loop. Replacing it with a single join isn't a micro-optimization; it turns N+1 round trips to the database into exactly 1.*

## Q9. Add an Index, or Live with the Scan

**Topic Tag:** Common Bottlenecks: Missing Indexes, N+1 Queries, Large Scans
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Decision-making

**Problem Statement**

A 5,000-row events table is regularly queried by `event_code`, with no index on it — every such query currently scans all 5,000 rows. You've been asked whether adding an index is worth it here, and to show the before/after.

**Table: `large_events_opt`**

| Column | Type | Description |
|---|---|---|
| `event_id` | INTEGER | Unique identifier (PK) |
| `event_code` | TEXT | Event code |
| `event_time` | TIMESTAMP | Timestamp of the event |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE large_events_opt (
    event_id INTEGER PRIMARY KEY,
    event_code TEXT,
    event_time TIMESTAMP
);

INSERT INTO large_events_opt (event_id, event_code, event_time)
SELECT i, 'EVT-' || (i % 5000), TIMESTAMP '2026-01-01' + (i || ' seconds')::INTERVAL
FROM generate_series(1, 5000) AS i;
```

**Your Task:** Show the plan before and after adding an index on `event_code`, and justify the decision.

**Before (illustrative)**

```
Seq Scan on large_events_opt  (cost=0.00..94.50 rows=1 width=8)
  Filter: (event_code = 'EVT-42'::text)
```

**Solution Query**

```sql
CREATE INDEX idx_event_code ON large_events_opt (event_code);

SELECT event_time FROM large_events_opt WHERE event_code = 'EVT-42';
```

**Output**

```
+-----------------------+
|     event_time        |
+-----------------------+
| 2026-01-01 00:00:42   |
+-----------------------+
```

**After (illustrative)**

```
Index Scan using idx_event_code on large_events_opt  (cost=0.28..8.30 rows=1 width=8)
  Index Cond: (event_code = 'EVT-42'::text)
```

**Justification:** `event_code` here is essentially unique per row (5,000 distinct codes across 5,000 rows) — exactly the high-selectivity scenario from Q3 and the earlier Indexes chapter where an index pays off decisively, unlike a boolean or a mostly-one-value column. Add the index: it turns a "check every row" query into a "jump straight there" one, and every future lookup by `event_code` benefits identically, for a write-side cost (updating one index entry per insert) that's negligible for a column this selective.

## Q10. Same Answer, Fewer Round Trips per Row

**Topic Tag:** Iterative Performance Tuning: Measure, Change, Re-measure
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Compare Values (correlated subquery → grouped join)

**Problem Statement**

A report computes each customer's total payments using a correlated subquery evaluated once per customer row — functionally correct, but re-scanning `payments_opt` from scratch for every customer. Rewrite it to compute every customer's total in a single grouped pass, and confirm the output is identical.

**Table: `customers_opt`**

| Column | Type | Description |
|---|---|---|
| `customer_id` | INTEGER | Unique identifier (PK) |
| `customer_name` | TEXT | Customer's name |

**Table: `payments_opt`**

| Column | Type | Description |
|---|---|---|
| `payment_id` | INTEGER | Unique identifier (PK) |
| `customer_id` | INTEGER | References `customers_opt.customer_id` |
| `amount` | NUMERIC(8,2) | Payment amount in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE customers_opt (
    customer_id INTEGER PRIMARY KEY,
    customer_name TEXT
);

CREATE TABLE payments_opt (
    payment_id INTEGER PRIMARY KEY,
    customer_id INTEGER,
    amount NUMERIC(8,2)
);

INSERT INTO customers_opt VALUES (1, 'Suhas Kelkar'), (2, 'Ritika Anand');
INSERT INTO payments_opt VALUES (1, 1, 500.00), (2, 1, 700.00), (3, 2, 300.00);
```

**Naive Version (measure: one correlated subquery per customer row)**

```sql
SELECT c.customer_name,
    (SELECT SUM(p.amount) FROM payments_opt p WHERE p.customer_id = c.customer_id) AS total_paid
FROM customers_opt c
ORDER BY c.customer_name;
```

**Output**

```
+----------------+-------------+
| customer_name  | total_paid  |
+----------------+-------------+
| Ritika Anand   |     300.00  |
| Suhas Kelkar   |    1200.00  |
+----------------+-------------+
```

**Solution Query (change: single grouped aggregation, joined back once)**

```sql
SELECT c.customer_name, COALESCE(t.total_paid, 0) AS total_paid
FROM customers_opt c
LEFT JOIN (
    SELECT customer_id, SUM(amount) AS total_paid FROM payments_opt GROUP BY customer_id
) t ON c.customer_id = t.customer_id
ORDER BY c.customer_name;
```

*Both versions return the identical result — the "iterate" part of this chapter is exactly this cycle: measure the naive version's plan (one subquery execution per outer row, the same cost-scaling risk as a correlated subquery flagged in the Subqueries chapter), change it to a shape that computes the aggregate once, and re-measure to confirm the rewrite is both correct and cheaper. `LEFT JOIN` (rather than `INNER JOIN`) also correctly preserves a customer who has made zero payments, showing `0` via `COALESCE` instead of silently disappearing.*

## Q11. Does Clause Order in WHERE Matter

**Topic Tag:** Inside the Query Optimizer
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Compare Values

**Problem Statement**

A warehouse system's two engineers wrote what they insist are "differently optimized" versions of the same filter, one listing `warehouse_code` first and one listing `status` first. Confirm whether the order actually changes anything.

**Table: `shipments_opt`**

| Column | Type | Description |
|---|---|---|
| `shipment_id` | INTEGER | Unique identifier (PK) |
| `warehouse_code` | TEXT | Warehouse code |
| `status` | TEXT | Shipment status |

Write both versions of the query and compare their results.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE shipments_opt (
    shipment_id INTEGER PRIMARY KEY,
    warehouse_code TEXT,
    status TEXT
);

INSERT INTO shipments_opt (shipment_id, warehouse_code, status) VALUES
(1, 'WH-A', 'Dispatched'), (2, 'WH-B', 'Pending'), (3, 'WH-A', 'Pending');
```

**Query A (warehouse_code first)**

```sql
SELECT shipment_id FROM shipments_opt WHERE warehouse_code = 'WH-A' AND status = 'Pending';
```

**Query B (status first)**

```sql
SELECT shipment_id FROM shipments_opt WHERE status = 'Pending' AND warehouse_code = 'WH-A';
```

**Output (identical for both)**

```
+---------------+
| shipment_id   |
+---------------+
|             3 |
+---------------+
```

**Why this matters:** The order conditions are written in a `WHERE` clause never affects the result, and the optimizer doesn't even necessarily evaluate them in the order written — it's free to check whichever condition it estimates will eliminate more rows first, regardless of which one a human typed first. Writing `WHERE` conditions "in the right order" for performance is a myth left over from much older, simpler database engines; a modern optimizer already reorders its own work based on actual cost estimates.

## Q12. Why the Same Query's Plan Can Change Over Time

**Topic Tag:** Inside the Query Optimizer
**Difficulty:** Hard
**Type:** Decision-Making
**Skill Focus:** Decision-making (statistics drive planning)

**Problem Statement**

A table starts with 50 rows and an index on `category`. A colleague is confused that the exact same query — unchanged — sometimes gets a different-looking `EXPLAIN` output after a bulk load, without anyone touching the SQL. Diagnose why.

**Table: `growing_table_opt`**

| Column | Type | Description |
|---|---|---|
| `row_id` | INTEGER | Unique identifier (PK) |
| `category` | TEXT | Category label |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE growing_table_opt (
    row_id INTEGER PRIMARY KEY,
    category TEXT
);

INSERT INTO growing_table_opt (row_id, category)
SELECT i, 'CAT-' || (i % 10) FROM generate_series(1, 50) AS i;

CREATE INDEX idx_growing_category ON growing_table_opt (category);
```

**EXPLAIN Before Statistics Are Refreshed (illustrative)**

```
Seq Scan on growing_table_opt  (cost=0.00..1.62 rows=1 width=4)
  Filter: (category = 'CAT-5'::text)
```

**EXPLAIN After `ANALYZE` (illustrative)**

```
Seq Scan on growing_table_opt  (cost=0.00..1.62 rows=5 width=4)
  Filter: (category = 'CAT-5'::text)
```

**Your Task:** Both plans still choose `Seq Scan` here (the table is tiny either way), but the *row estimate* changes from 1 to 5. Explain why, and what this implies for larger tables where the estimate could change which strategy gets picked entirely.

**Answer:** The query optimizer doesn't inspect live data every time it plans a query — it relies on cached statistics (row counts, value distributions, how common each distinct value is) that PostgreSQL maintains separately and refreshes via `ANALYZE`, either run manually or automatically in the background. Right after a bulk insert, those statistics can be stale or entirely default/guessed, which is why the estimate before `ANALYZE` (`rows=1`) doesn't match the true distribution (10 categories evenly split across 50 rows genuinely means 5 rows per category, confirmed after `ANALYZE` catches up). On a small table this mismatch is harmless — `Seq Scan` wins either way. On a much larger table, though, a stale row estimate is exactly the kind of thing that can push the optimizer toward the *wrong* strategy (e.g., picking a nested loop expecting 1 row when there are actually thousands), which is precisely why running `ANALYZE` after a significant bulk load — or trusting PostgreSQL's autovacuum/autoanalyze process to catch up — is a genuine performance practice, not just a formality.

## Q15. A Cost Number Isn't a Millisecond

**Topic Tag:** Reading EXPLAIN
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (misreading `cost` as real time)

**Problem Statement**

A teammate looked at `EXPLAIN`'s `cost=0.28..8.29` on a query and reported in stand-up that "this query takes about 8 milliseconds." Diagnose the mistake.

**Table:** `pos_transactions_opt` *(same as Q13)*

**The Claim Being Checked**

```sql
EXPLAIN SELECT amount FROM pos_transactions_opt WHERE transaction_id = 750;
```

```
Index Scan using pos_transactions_opt_pkey on pos_transactions_opt  (cost=0.28..8.29 rows=1 width=5)
  Index Cond: (transaction_id = 750)
```

**What's Wrong:** `cost=0.28..8.29` is not a time measurement at all — it's expressed in an internal, arbitrary planner unit (roughly calibrated to "how expensive is fetching one sequential disk page," a value that isn't even the same across different hardware). **Solution: Get Genuine Timing with EXPLAIN ANALYZE**

```sql

```

```
Index Scan using pos_transactions_opt_pkey on pos_transactions_opt  (cost=0.28..8.29 rows=1 width=5) (actual time=0.004..0.004 rows=1 loops=1)
  Index Cond: (transaction_id = 750)
Planning Time: 0.018 ms
Execution Time: 0.009 ms
```

*The real elapsed time — `Execution Time: 0.009 ms` — is nowhere close to "8 milliseconds," and it only shows up at all once `ANALYZE` is added to actually run the query. The fix isn't a different query; it's reading the right number from the right tool: `cost` for comparing plans, `actual time` / `Execution Time` (only available from `EXPLAIN ANALYZE`) for genuine wall-clock performance.*

## Q18. EXPLAIN vs. EXPLAIN ANALYZE, Side by Side

**Topic Tag:** Reading EXPLAIN ANALYZE
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Decision-making (when to use which)

**Problem Statement**

For the same query, one teammate always reaches for plain `EXPLAIN`; another always reaches for `EXPLAIN ANALYZE`. You've been asked to explain when each is actually the right call, using this query as the example.

**Table:** `call_records_opt` *(same as Q14)*

**EXPLAIN (illustrative)**

```sql
EXPLAIN SELECT call_id FROM call_records_opt WHERE call_type = 'Video';
```

```
Bitmap Heap Scan on call_records_opt  (cost=4.54..11.16 rows=50 width=4)
  Recheck Cond: (call_type = 'Video'::text)
  ->  Bitmap Index Scan on idx_call_type  (cost=0.00..4.53 rows=50 width=0)
        Index Cond: (call_type = 'Video'::text)
```

**EXPLAIN ANALYZE (illustrative)**

```sql
EXPLAIN ANALYZE SELECT call_id FROM call_records_opt WHERE call_type = 'Video';
```

```
Bitmap Heap Scan on call_records_opt  (cost=4.54..11.16 rows=50 width=4) (actual time=0.004..0.007 rows=50 loops=1)
  Recheck Cond: (call_type = 'Video'::text)
  Heap Blocks: exact=1
  ->  Bitmap Index Scan on idx_call_type  (cost=0.00..4.53 rows=50 width=0) (actual time=0.003..0.003 rows=50 loops=1)
        Index Cond: (call_type = 'Video'::text)
```

**Your Task:** Recommend a rule of thumb for when to use each.

**Justification:** Plain `EXPLAIN` is unconditionally safe on any statement, including a `DELETE`/`UPDATE`, because it only ever *estimates* — it never runs the query. That makes it the right default when the goal is understanding which strategy the optimizer *plans* to use, or when previewing anything destructive (as Q5 painfully illustrates, `EXPLAIN ANALYZE` is the wrong tool for that specific job). `EXPLAIN ANALYZE` earns its cost — genuinely running the statement — when the goal is confirming real-world timing or catching a case where the *estimate* is wrong (an `actual rows` wildly different from the estimated `rows=`, a strong signal of stale statistics, as explored in Q12 and Q19). The practical rule: reach for plain `EXPLAIN` first, always; only step up to `EXPLAIN ANALYZE` for read-only statements when real timing specifically matters, or wrap anything destructive in a rolled-back transaction first.

```
| post_id  |     comment_text       |
+----------+------------------------+
|        1 | Try the DBMS course!   |
|        1 | Agreed                 |
|        2 | Count me in            |
+----------+------------------------+
```

*One query, using `IN (...)` with every post ID the page needs, replaces the entire loop — the application groups the results by `post_id` in memory afterward, work that's essentially free compared to N extra database round trips.*

## Q26. Indexing Just the Rare, Always-Queried Slice

**Topic Tag:** Common Bottlenecks: Missing Indexes, N+1 Queries, Large Scans
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Decision-making (partial index for a bottleneck)

**Problem Statement**

A 4,000-row analytics events table logs both `'pageview'` (95%) and `'purchase'` (5%) events. Purchase-analysis queries always filter `event_type = 'purchase'` combined with a `user_id`. Design the index that best serves this specific bottleneck, and justify it over a plain full-column index.

**Table: `analytics_events_opt`**

| Column | Type | Description |
|---|---|---|
| `event_id` | INTEGER | Unique identifier (PK) |
| `user_id` | INTEGER | User identifier |
| `event_type` | TEXT | pageview / purchase |
| `event_date` | DATE | Event date |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE analytics_events_opt (
    event_id INTEGER PRIMARY KEY,
    user_id INTEGER,
    event_type TEXT,
    event_date DATE
);

INSERT INTO analytics_events_opt (event_id, user_id, event_type, event_date)
SELECT i, (i % 200) + 1, CASE WHEN i % 20 = 0 THEN 'purchase' ELSE 'pageview' END, DATE '2026-01-01' + (i % 60)
FROM generate_series(1, 4000) AS i;
```

**Your Task:** Write the index you'd recommend, and justify it over `CREATE INDEX ... ON analytics_events_opt (user_id)` covering every row regardless of `event_type`.

**Solution Query**

```sql
CREATE INDEX idx_purchases_only ON analytics_events_opt (user_id) WHERE event_type = 'purchase';

SELECT user_id FROM analytics_events_opt WHERE event_type = 'purchase' AND user_id = 21;
```

**Output**

```
+----------+
| user_id  |
+----------+
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
|      21  |
+----------+
```

**EXPLAIN (illustrative)**

```
Index Only Scan using idx_purchases_only on analytics_events_opt  (cost=0.14..8.16 rows=1 width=4)
  Index Cond: (user_id = 21)
```

**Justification:** This combines two ideas from the Indexes chapter directly: a partial index (indexing only the 5% of rows that are `'purchase'`, since `'pageview'` rows are never part of this specific query pattern) and an index-only scan (the query only needs `user_id`, which the index carries entirely on its own — `Index Only Scan` in the plan confirms it never has to touch the underlying table row at all). A full-column index on `user_id` would index all 4,000 rows, 95% of which this particular bottleneck query never cares about — the partial index stays a fraction of the size, is cheaper to maintain on every `pageview` insert (since those rows never touch it), and is exactly as fast for the one query pattern it was built for.

## Q28. Measure, Change, Re-measure — the Full Cycle

**Topic Tag:** Iterative Performance Tuning: Measure, Change, Re-measure
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (the full tuning cycle)

**Problem Statement**

Q27 already went through "measure" (the `Seq Scan` baseline) and "change" (adding `idx_status_code`). The cycle isn't complete until the change is re-measured to confirm it actually helped — with `EXPLAIN ANALYZE` this time, for genuine timing, not just an estimate.

**Table:** `api_logs_opt` *(already indexed by Q27)*

Write a query returning the first 3 error log IDs in order, and re-measure the indexed query with `EXPLAIN ANALYZE`.

**Output**

```
+----------+
| log_id   |
+----------+
|      100 |
|      200 |
|      300 |
+----------+
```

**Solution Query**

```sql
SELECT log_id FROM api_logs_opt WHERE status_code = 500 ORDER BY log_id LIMIT 3;
```

**Re-measure: EXPLAIN ANALYZE (illustrative)**

```
Index Scan using idx_status_code on api_logs_opt  (cost=0.28..11.49 rows=30 width=4) (actual time=0.001..0.006 rows=30 loops=1)
  Index Cond: (status_code = 500)
Planning Time: 0.007 ms
Execution Time: 0.008 ms
```

*This is the complete loop the lesson is named for: **measure** (Q27's `Seq Scan` baseline), **change** (add the index), **re-measure** (this `EXPLAIN ANALYZE`, now genuinely confirming a real, executed improvement — not just trusting that adding an index "should" help). Tuning that stops after "change" without re-measuring is only half-finished — the whole point is confirming the change actually delivered what was predicted.*

## Q29. Reconstruct the Optimized Department Report

**Topic Tag:** Iterative Performance Tuning: Measure, Change, Re-measure
**Difficulty:** Hard
**Type:** Reverse Engineering
**Skill Focus:** Reconstruct (correlated subquery → grouped join)

**Problem Statement**

A naive report computes each department's average salary with a correlated subquery, evaluated once per department row — the same pattern flagged as a scaling risk in the Subqueries chapter and Q10 of this bank. Someone already produced the optimized rewrite's output below — work out the query, using a single grouped join instead.

**Table: `departments_opt3`**

| Column | Type | Description |
|---|---|---|
| `dept_id` | INTEGER | Unique identifier (PK) |
| `dept_name` | TEXT | Department name |

**Table: `staff_opt3`**

| Column | Type | Description |
|---|---|---|
| `staff_id` | INTEGER | Unique identifier (PK) |
| `dept_id` | INTEGER | References `departments_opt3.dept_id` |
| `salary` | NUMERIC(10,2) | Salary in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE departments_opt3 (
    dept_id INTEGER PRIMARY KEY,
    dept_name TEXT
);

CREATE TABLE staff_opt3 (
    staff_id INTEGER PRIMARY KEY,
    dept_id INTEGER,
    salary NUMERIC(10,2)
);

INSERT INTO departments_opt3 VALUES (1, 'Engineering'), (2, 'Sales');
INSERT INTO staff_opt3 VALUES (1, 1, 90000.00), (2, 1, 85000.00), (3, 2, 60000.00);
```

**Naive Version (the one being replaced)**

```sql
SELECT d.dept_name,
    (SELECT AVG(s.salary) FROM staff_opt3 s WHERE s.dept_id = d.dept_id) AS avg_salary
FROM departments_opt3 d
ORDER BY d.dept_name;
```

**Target Output**

```
+---------------+---------------------+
|   dept_name   |     avg_salary      |
+---------------+---------------------+
| Engineering   | 87500.000000000000  |
| Sales         | 60000.000000000000  |
+---------------+---------------------+
```

**Your Task:** Write the single-pass, grouped-join version that produces this identical result.

**Solution Query**

```sql
SELECT d.dept_name, AVG(s.salary) AS avg_salary
FROM departments_opt3 d
JOIN staff_opt3 s ON d.dept_id = s.dept_id
GROUP BY d.dept_name
ORDER BY d.dept_name;
```

*Both versions return the exact same averages — the naive version simply recomputes an average once per department via a fresh subquery each time, while this version joins once and groups once, scaling to one pass over the data regardless of how many departments exist.*

## Q30. A Fix That Didn't Actually Fix Anything

**Topic Tag:** Iterative Performance Tuning: Measure, Change, Re-measure
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (indexed the wrong column, skipped re-measuring)

**Problem Statement**

A support ticket lookup by `status` was running slow. An engineer added an index — and moved on without re-measuring, assuming the fix worked. It didn't.

**Table: `tickets_opt3`**

| Column | Type | Description |
|---|---|---|
| `ticket_id` | INTEGER | Unique identifier (PK) |
| `subject` | TEXT | Ticket subject |
| `status` | TEXT | Ticket status |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE tickets_opt3 (
    ticket_id INTEGER PRIMARY KEY,
    subject TEXT,
    status TEXT
);

INSERT INTO tickets_opt3 (ticket_id, subject, status)
SELECT i, 'Ticket ' || i, CASE WHEN i = 500 THEN 'Escalated' ELSE 'Normal' END
FROM generate_series(1, 1000) AS i;
```

**"Fix" as Applied (indexed `subject`, not `status`)**

```sql
CREATE INDEX idx_ticket_subject ON tickets_opt3 (subject);
```

**Query Still Being Run**

```sql
EXPLAIN SELECT ticket_id FROM tickets_opt3 WHERE status = 'Escalated';
```

**Buggy Output**

```
Seq Scan on tickets_opt3  (cost=0.00..19.50 rows=1 width=4)
  Filter: (status = 'Escalated'::text)
(still a Seq Scan — the "fix" changed nothing about this query)
```

**What's Wrong:** The query filters on `status`, but the index that got created is on `subject` — a column this query never touches at all. `idx_ticket_subject` is a perfectly valid index; it's simply indexing the wrong thing for this specific bottleneck. Because the engineer skipped the "re-measure" step, the mistake shipped unnoticed — the fix "felt done" the moment `CREATE INDEX` succeeded, but success at creating an index is not the same as success at fixing the query it was meant to help.

**Solution Query (Fixed)**

```sql
CREATE INDEX idx_ticket_status ON tickets_opt3 (status);
```

**Fixed EXPLAIN (illustrative)**

```
Index Scan using idx_ticket_status on tickets_opt3  (cost=0.15..8.17 rows=1 width=4)
  Index Cond: (status = 'Escalated'::text)
```

**Fixed Output**

```
+------------+
| ticket_id  |
+------------+
|        500 |
+------------+
```

*This is precisely why "measure, change, re-measure" is a three-step cycle, not two: skipping the final re-measure is how a confidently-applied, syntactically-correct fix ships without anyone noticing it solved the wrong problem.*
