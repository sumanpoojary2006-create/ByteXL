# Subqueries and CTEs — Coding Question Bank

Dialect: **PostgreSQL**. Every query in this bank has been executed against a live PostgreSQL 16 instance; the `Output` shown for each question is the actual result — including several questions where the "buggy" query genuinely throws a PostgreSQL error, reproduced verbatim.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the query.
- **Bug Hunt** — a query someone already wrote is shown along with its (wrong, or erroring) output; find and fix the mistake.
- **Predict the Output** — a query is already written; state exactly what it returns before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; write the better one and explain why.
- **Reverse Engineering** — you're shown the data and the target result; work out the query that produces it.
- **Decision-Making** — a concrete symptom is shown; diagnose the cause and recommend a fix.

## Q1. The Highest-Value Invoices

**Topic Tag:** What is a Subquery?
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Compare Values

**Problem Statement**

A freelancer's invoice tracker needs to flag invoices priced above the average, to see which clients are the biggest earners. There's no fixed number to compare against — "average" has to be computed from the data itself, inside the same query.

**Table: `invoices_fl`**

| Column | Type | Description |
|---|---|---|
| `invoice_id` | INTEGER | Unique identifier (PK) |
| `client_name` | VARCHAR(60) | Client's name |
| `amount` | DECIMAL(10,2) | Invoice amount in ₹ |

Write a query that returns `client_name` and `amount` for invoices priced above the average invoice amount.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE invoices_fl (
    invoice_id INTEGER PRIMARY KEY,
    client_name VARCHAR(60),
    amount DECIMAL(10,2)
);

INSERT INTO invoices_fl (invoice_id, client_name, amount) VALUES
(1, 'Northwind Traders', 25000.00),
(2, 'Bluepeak Media', 8000.00),
(3, 'Crimson Studio', 15000.00),
(4, 'Larkspur Co', 6000.00);
```

**Output**

```
+-------------------+----------+
|    client_name    |  amount  |
+-------------------+----------+
| Crimson Studio    | 15000.00 |
| Northwind Traders | 25000.00 |
+-------------------+----------+
```

**Solution Query**

```sql
SELECT client_name, amount
FROM invoices_fl
WHERE amount > (SELECT AVG(amount) FROM invoices_fl);
```

*The inner `SELECT AVG(amount) FROM invoices_fl` is a **subquery** — a complete query nested inside another, evaluated first so its single result (the average, ₹13,500) becomes a value the outer query can compare against, exactly the way a literal number would be used.*

## Q2. Employees in Western Departments

**Topic Tag:** Subqueries in WHERE
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A company wants a list of employees who work in any department based in the West region — but the region is recorded on the department, not the employee, so the employee table has to be filtered against a list of department IDs computed from a different table.

**Table: `departments_reg`**

| Column | Type | Description |
|---|---|---|
| `dept_id` | INTEGER | Unique identifier (PK) |
| `dept_name` | VARCHAR(40) | Department name |
| `region` | VARCHAR(20) | Region the department operates in |

**Table: `employees_dept`**

| Column | Type | Description |
|---|---|---|
| `emp_id` | INTEGER | Unique identifier (PK) |
| `emp_name` | VARCHAR(60) | Employee's name |
| `dept_id` | INTEGER | References `departments_reg.dept_id` |

Write a query that returns `emp_name` for employees whose department is in the `'West'` region, using a subquery in `WHERE`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE departments_reg (
    dept_id INTEGER PRIMARY KEY,
    dept_name VARCHAR(40),
    region VARCHAR(20)
);

CREATE TABLE employees_dept (
    emp_id INTEGER PRIMARY KEY,
    emp_name VARCHAR(60),
    dept_id INTEGER
);

INSERT INTO departments_reg (dept_id, dept_name, region) VALUES
(1, 'Sales West', 'West'), (2, 'Sales East', 'East'), (3, 'Marketing West', 'West');

INSERT INTO employees_dept (emp_id, emp_name, dept_id) VALUES
(1, 'Aarav Sethi', 1), (2, 'Ishaani Roy', 2), (3, 'Yuvraj Malik', 3);
```

**Output**

```
+---------------+
|   emp_name    |
+---------------+
| Aarav Sethi   |
| Yuvraj Malik  |
+---------------+
```

**Solution Query**

```sql
SELECT emp_name
FROM employees_dept
WHERE dept_id IN (SELECT dept_id FROM departments_reg WHERE region = 'West')
ORDER BY emp_name;
```

*This could also be written as a `JOIN`, but the subquery form reads naturally as "employees whose department is one of these" — a list-membership question `IN` is built specifically for.*

## Q3. Movies Nobody Has Rated

**Topic Tag:** Subqueries in WHERE
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Validate (`NOT IN` with a NULL)

**Problem Statement**

A streaming platform wants movies that have never received a single rating. One rating row exists with `movie_id` left as `NULL` — a data-entry glitch where a rating was submitted but the movie link failed to save. Before running it, predict whether that glitch affects the result.

**Table: `movies_str`**

| Column | Type | Description |
|---|---|---|
| `movie_id` | INTEGER | Unique identifier (PK) |
| `movie_title` | VARCHAR(60) | Movie title |

**Table: `ratings_str`**

| Column | Type | Description |
|---|---|---|
| `rating_id` | INTEGER | Unique identifier (PK) |
| `movie_id` | INTEGER | References `movies_str.movie_id`, `NULL` if the link failed to save |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE movies_str (
    movie_id INTEGER PRIMARY KEY,
    movie_title VARCHAR(60)
);

CREATE TABLE ratings_str (
    rating_id INTEGER PRIMARY KEY,
    movie_id INTEGER
);

INSERT INTO movies_str (movie_id, movie_title) VALUES
(1, 'Monsoon Nights'), (2, 'Neon Alley'), (3, 'Dust and Gold');

INSERT INTO ratings_str (rating_id, movie_id) VALUES
(1, 1), (2, NULL);
```

**Query to Analyze**

```sql
SELECT movie_title
FROM movies_str
WHERE movie_id NOT IN (SELECT movie_id FROM ratings_str);
```

**Your Task:** Movies 2 and 3 have genuinely never been rated. Does this query find them?

**Answer**

```
+-------------+
| movie_title |
+-------------+
+-------------+
(0 rows)
```

**Why:** This is the `NOT IN` + `NULL` trap resurfacing from the filtering chapter, now hiding inside a subquery. The subquery `(SELECT movie_id FROM ratings_str)` returns `(1, NULL)` — and the moment a `NULL` sits anywhere in a `NOT IN` list, the entire comparison collapses to `UNKNOWN` for every row, emptying the whole result rather than just mishandling the one row tied to the `NULL`. Even "Dust and Gold," which has no rating at all, silently disappears. The safe fix is `NOT EXISTS (SELECT 1 FROM ratings_str r WHERE r.movie_id = movies_str.movie_id)`, which never falls into this trap.

## Q4. Buildings with More Than One Open Request

**Topic Tag:** Subqueries in FROM
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Summarize (derived table)

**Problem Statement**

A property manager wants buildings with more than one maintenance request logged, computed by first summarizing request counts per building, then filtering that summary.

**Table: `maintenance_requests`**

| Column | Type | Description |
|---|---|---|
| `request_id` | INTEGER | Unique identifier (PK) |
| `building_name` | VARCHAR(40) | Building name |
| `status` | VARCHAR(20) | Request status |

Write a query that returns `building_name` and `request_count`, using a subquery in `FROM` to first compute the per-building count, then filtering for buildings with more than 1.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE maintenance_requests (
    request_id INTEGER PRIMARY KEY,
    building_name VARCHAR(40),
    status VARCHAR(20)
);

INSERT INTO maintenance_requests (request_id, building_name, status) VALUES
(1, 'Sunrise Towers', 'Open'), (2, 'Sunrise Towers', 'Closed'), (3, 'Palm Residency', 'Open');
```

**Output**

```
+-----------------+----------------+
|  building_name  | request_count  |
+-----------------+----------------+
| Sunrise Towers  |              2 |
+-----------------+----------------+
```

**Solution Query**

```sql
SELECT building_name, request_count
FROM (
    SELECT building_name, COUNT(*) AS request_count
    FROM maintenance_requests
    GROUP BY building_name
) AS building_summary
WHERE request_count > 1;
```

*This could be written with `HAVING` directly, but a subquery in `FROM` — a "derived table" — treats the summarized result as if it were its own ordinary table, which becomes essential once the filtering logic gets more complex than a single `HAVING` clause can cleanly express.*

## Q5. A Derived Table's Missing Grouping

**Topic Tag:** Subqueries in FROM
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (missing GROUP BY inside a derived table)

**Problem Statement**

A national park network wants total visitor counts per park, computed inside a derived table. A ranger's query fails to run.

**Table: `park_visits`**

| Column | Type | Description |
|---|---|---|
| `visit_id` | INTEGER | Unique identifier (PK) |
| `park_name` | VARCHAR(60) | Park name |
| `visitor_count` | INTEGER | Visitors on this log entry |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE park_visits (
    visit_id INTEGER PRIMARY KEY,
    park_name VARCHAR(60),
    visitor_count INTEGER
);

INSERT INTO park_visits (visit_id, park_name, visitor_count) VALUES
(1, 'Sundarbans', 120), (2, 'Sundarbans', 95), (3, 'Kaziranga', 200);
```

**Buggy Query (as submitted)**

```sql
SELECT park_name, total_visitors
FROM (SELECT park_name, SUM(visitor_count) AS total_visitors FROM park_visits) AS park_totals;
```

**Buggy Output**

```
ERROR:  column "park_visits.park_name" must appear in the GROUP BY clause or be used in an aggregate function
LINE 1: SELECT park_name, total_visitors FROM (SELECT park_name, SUM...
                                                      ^
```

**What's Wrong:** The error happens *inside* the derived table's own inner query, not the outer one — a subquery in `FROM` is still a complete, self-contained query with all the same rules. Selecting `park_name` alongside `SUM(visitor_count)` without a `GROUP BY park_name` is exactly the same ungrouped-column error covered in the Aggregation chapter; wrapping the query in `FROM (...)` doesn't exempt it from that rule.

**Solution Query (Fixed)**

```sql
SELECT park_name, total_visitors
FROM (
    SELECT park_name, SUM(visitor_count) AS total_visitors
    FROM park_visits
    GROUP BY park_name
) AS park_totals
ORDER BY park_name;
```

**Fixed Output**

```
+-------------+-----------------+
|  park_name  | total_visitors  |
+-------------+-----------------+
| Kaziranga   |             200 |
| Sundarbans  |             215 |
+-------------+-----------------+
```

## Q6. Batches Longer Than Their Roaster's Average

**Topic Tag:** Correlated Subqueries
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Compare Values (per-row comparison)

**Problem Statement**

A coffee roastery wants batches that took longer to roast than *that specific roaster's own* average roast time — not the average across every roaster, since different roasters specialize in different roast profiles.

**Table: `roast_batches`**

| Column | Type | Description |
|---|---|---|
| `batch_id` | INTEGER | Unique identifier (PK) |
| `roaster_name` | VARCHAR(60) | Roaster's name |
| `roast_minutes` | DECIMAL(5,1) | Roast duration in minutes |

Write a query that returns `batch_id`, `roaster_name`, and `roast_minutes` for batches longer than that roaster's own average roast time.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE roast_batches (
    batch_id INTEGER PRIMARY KEY,
    roaster_name VARCHAR(60),
    roast_minutes DECIMAL(5,1)
);

INSERT INTO roast_batches (batch_id, roaster_name, roast_minutes) VALUES
(1, 'Imran Sheikh', 12.0), (2, 'Imran Sheikh', 16.0), (3, 'Vijay Kumar', 14.0), (4, 'Vijay Kumar', 10.0);
```

**Output**

```
+----------+---------------+----------------+
| batch_id | roaster_name  | roast_minutes  |
+----------+---------------+----------------+
|        2 | Imran Sheikh  |           16.0 |
|        3 | Vijay Kumar   |           14.0 |
+----------+---------------+----------------+
```

**Solution Query**

```sql
SELECT b1.batch_id, b1.roaster_name, b1.roast_minutes
FROM roast_batches b1
WHERE b1.roast_minutes > (
    SELECT AVG(b2.roast_minutes)
    FROM roast_batches b2
    WHERE b2.roaster_name = b1.roaster_name
)
ORDER BY b1.batch_id;
```

*The inner query can't run just once and be reused for every row — it references `b1.roaster_name`, a value from the *current* outer row, so it has to re-execute once per outer row, recomputing a different average each time. That's what makes this a **correlated** subquery, unlike Q1's subquery, which only ever needed to compute one number, total.*

## Q7. Speakers with More Than One Proposal

**Topic Tag:** Correlated Subqueries
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse

**Problem Statement**

A tech conference's review committee wants speakers who submitted more than one proposal, so they can be asked to pick their strongest one. Dr. Kavita Menon submitted two; Arvind Chatterjee submitted one. Before running a correlated-subquery version of this check, predict who shows up.

**Table: `cfp_speakers`**

| Column | Type | Description |
|---|---|---|
| `speaker_id` | INTEGER | Unique identifier (PK) |
| `speaker_name` | VARCHAR(60) | Speaker's name |

**Table: `cfp_proposals`**

| Column | Type | Description |
|---|---|---|
| `proposal_id` | INTEGER | Unique identifier (PK) |
| `speaker_id` | INTEGER | References `cfp_speakers.speaker_id` |
| `title` | VARCHAR(80) | Proposal title |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE cfp_speakers (
    speaker_id INTEGER PRIMARY KEY,
    speaker_name VARCHAR(60)
);

CREATE TABLE cfp_proposals (
    proposal_id INTEGER PRIMARY KEY,
    speaker_id INTEGER,
    title VARCHAR(80)
);

INSERT INTO cfp_speakers (speaker_id, speaker_name) VALUES
(1, 'Dr. Kavita Menon'), (2, 'Arvind Chatterjee');

INSERT INTO cfp_proposals (proposal_id, speaker_id, title) VALUES
(1, 1, 'Scaling Systems'), (2, 1, 'Career Panel'), (3, 2, 'Intro to Rust');
```

**Query to Analyze**

```sql
SELECT sp.speaker_name
FROM cfp_speakers sp
WHERE (SELECT COUNT(*) FROM cfp_proposals p WHERE p.speaker_id = sp.speaker_id) > 1;
```

**Your Task:** Which speaker(s) appear in the result?

**Answer**

```
+--------------------+
|   speaker_name     |
+--------------------+
| Dr. Kavita Menon   |
+--------------------+
(1 row)
```

**Why:** For each row of `cfp_speakers`, the correlated subquery recomputes `COUNT(*)` specifically over that speaker's own proposals — Dr. Kavita Menon's count evaluates to 2 (`> 1`, included), Arvind Chatterjee's evaluates to 1 (not `> 1`, excluded). This is functionally identical to a `GROUP BY speaker_id HAVING COUNT(*) > 1` on the joined data, just expressed as a per-row check instead of a grouped one — a useful alternative shape when the count needs to sit inside a `WHERE` condition on the speaker table directly, rather than reshaping the whole query around a `GROUP BY`.

## Q8. Naming a Filtered Set

**Topic Tag:** Common Table Expressions (CTEs)
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A telemedicine platform wants a readable query for patients who still have refills remaining on their prescription — readable enough that a non-SQL-fluent pharmacist reviewing it could follow the logic.

**Table: `prescriptions_tm`**

| Column | Type | Description |
|---|---|---|
| `prescription_id` | INTEGER | Unique identifier (PK) |
| `patient_name` | VARCHAR(60) | Patient's name |
| `medicine_name` | VARCHAR(60) | Prescribed medicine |
| `refill_count` | INTEGER | Refills remaining |

Write a query using a `WITH` clause named `active_refills` that selects `patient_name` and `medicine_name` for prescriptions with `refill_count > 0`, then selects from it.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE prescriptions_tm (
    prescription_id INTEGER PRIMARY KEY,
    patient_name VARCHAR(60),
    medicine_name VARCHAR(60),
    refill_count INTEGER
);

INSERT INTO prescriptions_tm (prescription_id, patient_name, medicine_name, refill_count) VALUES
(1, 'Kavya Nair', 'Metformin 500', 3), (2, 'Rohit Sinha', 'Atorvastatin 10', 0), (3, 'Divya Rao', 'Amlodipine 5', 2);
```

**Output**

```
+---------------+----------------+
| patient_name  | medicine_name  |
+---------------+----------------+
| Divya Rao     | Amlodipine 5   |
| Kavya Nair    | Metformin 500  |
+---------------+----------------+
```

**Solution Query**

```sql
WITH active_refills AS (
    SELECT patient_name, medicine_name
    FROM prescriptions_tm
    WHERE refill_count > 0
)
SELECT * FROM active_refills
ORDER BY patient_name;
```

*A CTE (`WITH ... AS (...)`) computes the same kind of intermediate result a subquery-in-`FROM` does, but gives it a name declared up front — a reader sees `active_refills` and immediately knows what the block below computes, before even reading its body.*

## Q9. Naming the Same Filter Twice

**Topic Tag:** Common Table Expressions (CTEs)
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Compare Values (subquery-in-FROM vs. CTE)

**Problem Statement**

An organic farm's CSA (community-supported agriculture) coordinator wants boxes priced above ₹850. One version of the query nests the filter as a subquery in `FROM`; another names it with `WITH`. Both return identical results — you've been asked which to standardize on for the farm's internal reporting scripts.

**Table: `csa_boxes`**

| Column | Type | Description |
|---|---|---|
| `box_id` | INTEGER | Unique identifier (PK) |
| `member_name` | VARCHAR(60) | CSA member's name |
| `box_value` | DECIMAL(8,2) | Box value in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE csa_boxes (
    box_id INTEGER PRIMARY KEY,
    member_name VARCHAR(60),
    box_value DECIMAL(8,2)
);

INSERT INTO csa_boxes (box_id, member_name, box_value) VALUES
(1, 'Harshita Rane', 800.00), (2, 'Om Bhosale', 1200.00), (3, 'Kavita Save', 950.00);
```

**Subquery-in-FROM Version**

```sql
SELECT member_name, box_value
FROM (SELECT member_name, box_value FROM csa_boxes WHERE box_value > 850) AS pricier_boxes
ORDER BY member_name;
```

**CTE Version**

```sql
WITH pricier_boxes AS (
    SELECT member_name, box_value FROM csa_boxes WHERE box_value > 850
)
SELECT member_name, box_value FROM pricier_boxes
ORDER BY member_name;
```

**Output (identical for both)**

```
+----------------+------------+
|  member_name   | box_value  |
+----------------+------------+
| Kavita Save    |     950.00 |
| Om Bhosale     |    1200.00 |
+----------------+------------+
```

**Justification:** For a query this simple, the two are functionally and even readability-wise nearly a wash. The CTE earns its keep as queries grow: naming `pricier_boxes` up front documents *intent* before a reader parses the filter logic, and if the farm's next report needs to reference that same filtered set a second time (say, once to list the boxes and once to count them), a CTE can be referenced by name multiple times in the same query, while a subquery-in-`FROM` would have to be copy-pasted again or wrapped in yet another nested layer. Standardizing on CTEs for named intermediate steps costs nothing on simple queries and pays off directly as soon as a query has more than one logical step.

## Q10. Everyone Under Farhan Ali

**Topic Tag:** Recursive CTEs: Querying Hierarchies and Graphs
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (recursive traversal)

**Problem Statement**

A company's org chart is stored as a self-referencing table. HR wants every employee who reports to Farhan Ali, directly *or indirectly* — not just his immediate reports, but their reports too, however many levels deep the chain goes.

**Table: `employees_hier`**

| Column | Type | Description |
|---|---|---|
| `employee_id` | INTEGER | Unique identifier (PK) |
| `employee_name` | VARCHAR(60) | Employee's name |
| `manager_id` | INTEGER | References `employees_hier.employee_id`, `NULL` for the top of the chain |

Write a `WITH RECURSIVE` query that returns every employee under Farhan Ali (`employee_id = 1`), at any depth.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE employees_hier (
    employee_id INTEGER PRIMARY KEY,
    employee_name VARCHAR(60),
    manager_id INTEGER
);

INSERT INTO employees_hier (employee_id, employee_name, manager_id) VALUES
(1, 'Farhan Ali', NULL),
(2, 'Neha Kulkarni', 1),
(3, 'Arjun Reddy', 1),
(4, 'Devika Pillai', 2),
(5, 'Sameer Khan', 4);
```

**Output**

```
+-----------------+
|  employee_name  |
+-----------------+
| Arjun Reddy     |
| Devika Pillai   |
| Neha Kulkarni   |
| Sameer Khan     |
+-----------------+
```

**Solution Query**

```sql
WITH RECURSIVE reports_chain AS (
    SELECT employee_id, employee_name, manager_id
    FROM employees_hier
    WHERE employee_id = 1

    UNION ALL

    SELECT e.employee_id, e.employee_name, e.manager_id
    FROM employees_hier e
    INNER JOIN reports_chain rc ON e.manager_id = rc.employee_id
)
SELECT employee_name FROM reports_chain WHERE employee_id <> 1 ORDER BY employee_name;
```

*The first `SELECT` (the "base case") starts at Farhan Ali. The second `SELECT` (the "recursive case") joins `employees_hier` back to `reports_chain` itself, pulling in one more level of reports each pass — Neha and Arjun in the first pass, then Devika (Neha's report) in the next, then Sameer (Devika's report) in the pass after that — until a pass finds no new matches and the recursion stops on its own. Sameer Khan, three levels down, would be invisible to a plain non-recursive query without knowing the chain's exact depth in advance.*

## Q11. The Single Costliest Repair

**Topic Tag:** What is a Subquery?
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Compare Values

**Problem Statement**

A property manager wants to know which maintenance request is the most expensive one on record, to flag it for board approval.

| Column | Type | Description |
|---|---|---|
| `request_id` | INTEGER | Unique identifier (PK) |
| `description` | VARCHAR(80) | Request description |
| `est_cost` | DECIMAL(8,2) | Estimated cost in ₹ |

Write a query that returns `description` and `est_cost` for the request whose cost equals the maximum cost.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE maintenance_costs (
    request_id INTEGER PRIMARY KEY,
    description VARCHAR(80),
    est_cost DECIMAL(8,2)
);

INSERT INTO maintenance_costs (request_id, description, est_cost) VALUES
```

```
+-------------------+-----------+
```

## Q13. Products in the Electronics Category

**Topic Tag:** Subqueries in WHERE
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A product catalog needs every product in the "Electronics" category, but the query only has the category name to go on — the products table only stores a `category_id`.

**Table: `categories_pc`**

| Column | Type | Description |
|---|---|---|
| `category_id` | INTEGER | Unique identifier (PK) |
| `category_name` | VARCHAR(40) | Category name |

**Table: `products_pc`**

| Column | Type | Description |
|---|---|---|
| `product_id` | INTEGER | Unique identifier (PK) |
| `product_name` | VARCHAR(60) | Product name |
| `category_id` | INTEGER | References `categories_pc.category_id` |

Write a query that returns `product_name` for products in the `'Electronics'` category, using a subquery.

**Dataset Creation Query (Backend)**

## Q21. A Subquery That Isn't Actually Correlated

**Topic Tag:** Correlated Subqueries
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (forgetting the correlation)

**Problem Statement**

A school wants each student's subjects where they scored above *their own* average across all their subjects. A teacher's query was meant to correlate per student, but a typo left it referencing the wrong alias entirely — and it doesn't even run.

**Table: `students_grades`**

| Column | Type | Description |
|---|---|---|
| `student_id` | INTEGER | Unique identifier (PK) |
| `student_name` | VARCHAR(60) | Student's name |
| `subject` | VARCHAR(30) | Subject name |
| `score` | INTEGER | Score achieved |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE students_grades (student_id INTEGER PRIMARY KEY, student_name VARCHAR(60), subject VARCHAR(30), score INTEGER);

INSERT INTO students_grades VALUES
(1, 'Kabir Anand', 'Math', 85), (2, 'Kabir Anand', 'Science', 90), (3, 'Ira Chatterjee', 'Math', 70);
```

**Buggy Query (as submitted)**

```sql
SELECT s1.student_name, s1.subject, s1.score
FROM students_grades s1
WHERE s1.score > (SELECT AVG(s1.score) FROM students_grades s2);
```

**Buggy Output**

```
ERROR:  aggregate functions are not allowed in WHERE
LINE 3: WHERE s1.score > (SELECT AVG(s1.score) FROM students_grades ...
                                 ^
```

**What's Wrong:** The subquery's `FROM` clause introduces alias `s2`, but the `AVG(...)` inside mistakenly wraps `s1.score` — a column from the *outer* query — instead of `s2.score`, the column the subquery was actually supposed to aggregate over.
```
+----------------+----------+--------+
| student_name   | subject  | score  |
+----------------+----------+--------+
| Kabir Anand    | Science  |     90 |
+----------------+----------+--------+
```

*The fix does two things at once: aggregates the *subquery's own* column (`s2.score`), and correlates it back to the outer row via `WHERE s2.student_name = s1.student_name` — without that `WHERE`, the average would just be the overall average across every student, not "this student's own average."*

## Q23. Fastest Runner per Category, Two Ways

**Topic Tag:** Correlated Subqueries
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Compare Values (correlated subquery vs. join-on-derived-table)

**Problem Statement**

A race's results board wants the fastest runner in each category. One approach uses a correlated subquery comparing each runner's time to their category's minimum; another computes per-category minimums as a derived table and joins back to find the matching runner. Both are shown below — you've been asked to say when each is the more natural choice.

**Table: `race_times`**

| Column | Type | Description |
|---|---|---|
| `runner_id` | INTEGER | Unique identifier (PK) |
| `runner_name` | VARCHAR(60) | Runner's name |
| `category` | VARCHAR(20) | Age category |
| `finish_seconds` | INTEGER | Finish time in seconds |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE race_times (runner_id INTEGER PRIMARY KEY, runner_name VARCHAR(60), category VARCHAR(20), finish_seconds INTEGER);

INSERT INTO race_times VALUES
(1, 'Aakriti Bansal', 'Senior', 5430), (2, 'Vivek Thakkar', 'Senior', 5200), (3, 'Noor Fatima', 'Junior', 6100);
```

**Correlated Subquery Version**

```sql
SELECT r1.runner_name, r1.category, r1.finish_seconds
FROM race_times r1
WHERE r1.finish_seconds = (SELECT MIN(r2.finish_seconds) FROM race_times r2 WHERE r2.category = r1.category)
ORDER BY r1.category;
```

**Join-on-Derived-Table Version**

```sql
SELECT r1.runner_name, r1.category, r1.finish_seconds
FROM race_times r1
INNER JOIN (
    SELECT category, MIN(finish_seconds) AS min_time FROM race_times GROUP BY category
) AS grp ON r1.category = grp.category AND r1.finish_seconds = grp.min_time
ORDER BY r1.category;
```

```
+----------------+-----------+------------------+
|  runner_name   | category  |  finish_seconds  |
+----------------+-----------+------------------+
| Noor Fatima    | Junior    |             6100 |
| Vivek Thakkar  | Senior    |             5200 |
+----------------+-----------+------------------+
```

**Justification:** Both are correct and, on typical query planners, often perform comparably for small-to-medium data — this is more a matter of clarity than a hard performance rule. The correlated subquery reads almost like a sentence — "this runner's time equals the minimum time for their category" — which is easy to follow for a single condition like this. The join-on-derived-table version pre-computes each category's minimum exactly once as its own named result, then matches it back — a shape that scales better in *readability* once more than one derived aggregate needs joining back, or once the same per-group aggregate needs to be reused in multiple places in the query. For a single, one-off comparison like this one, the correlated subquery is usually the more direct choice; the derived-table join earns its complexity once the query needs to do more with that aggregate than compare it once.

## Q24. When a Correlated Subquery Gets Expensive

**Topic Tag:** Correlated Subqueries
**Difficulty:** Hard
**Type:** Decision-Making
**Skill Focus:** Decision-making (correlated subquery cost)

**Problem Statement**

Revisiting Q20's "highest-paid employee per department" query: it currently runs fine on a handful of employees, but the payroll table is about to grow to 200,000 rows across many departments. A colleague asks whether the correlated-subquery approach will still be a good idea at that scale, and if not, what to reach for instead.

```sql
SELECT e1.emp_name, e1.dept_name, e1.salary
FROM employees_pay e1
WHERE e1.salary = (SELECT MAX(e2.salary) FROM employees_pay e2 WHERE e2.dept_name = e1.dept_name);
```

**Your Task:** Explain what happens to this query's cost as the table grows, and what alternative approach avoids the problem.

**Answer:** A correlated subquery conceptually re-runs once *per outer row* — for 200,000 employees, that's 200,000 separate scans (in the worst case) each re-scanning the department to find its max salary, rather than one pass over the data. In practice, a good query planner can sometimes optimize this into something cheaper depending on indexes, but it's not guaranteed, and correlated subqueries are a common source of surprise slowdowns exactly because they *look* deceptively simple while implying repeated work under the hood. The safer default at scale is to compute the per-department maximum *once*, as its own grouped result, and join back to it — the same "join-on-derived-table" shape from Q23:

```sql
SELECT e1.emp_name, e1.dept_name, e1.salary
FROM employees_pay e1
INNER JOIN (
    SELECT dept_name, MAX(salary) AS max_salary FROM employees_pay GROUP BY dept_name
) AS dept_max ON e1.dept_name = dept_max.dept_name AND e1.salary = dept_max.max_salary;
```

This computes each department's maximum exactly once, in a single grouped pass, then joins it back — the same guaranteed-single-pass cost regardless of how many departments or employees exist, instead of cost that grows with the number of outer rows.

```
HINT:  Use WITH RECURSIVE, or re-order the WITH items to remove forward references.
```

**What's Wrong:** In a plain (non-recursive) `WITH`, each CTE can only reference CTEs defined *earlier* in the same `WITH` clause — not ones that come later. `top_payers` is defined first here, but tries to select from `customer_totals`, which isn't defined until the block after it. PostgreSQL's own error message even names the fix directly.

**Solution Query (Fixed)**

```sql
WITH customer_totals AS (
    SELECT customer_name, SUM(amount) AS total_paid FROM payments_cte GROUP BY customer_name
),
top_payers AS (
    SELECT * FROM customer_totals WHERE total_paid > 400
)
SELECT * FROM top_payers ORDER BY total_paid DESC;
```

**Fixed Output**

```
+----------------+-------------+
| customer_name  | total_paid  |
+----------------+-------------+
| Devika Rane    |    1200.00  |
+----------------+-------------+
```

## Q28. Every Subcategory Under Electronics

**Topic Tag:** Recursive CTEs: Querying Hierarchies and Graphs
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve (recursive traversal)

**Problem Statement**

A product catalog organizes categories in a tree — "Laptops" sits under "Computers," which sits under "Electronics." The catalog page for "Electronics" needs every category nested underneath it, at any depth.

**Table: `category_tree`**

| Column | Type | Description |
|---|---|---|
| `category_id` | INTEGER | Unique identifier (PK) |
| `category_name` | VARCHAR(60) | Category name |
| `parent_id` | INTEGER | References `category_tree.category_id`, `NULL` for top-level categories |

Write a `WITH RECURSIVE` query that returns every category nested under "Electronics" (`category_id = 1`).

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE category_tree (category_id INTEGER PRIMARY KEY, category_name VARCHAR(60), parent_id INTEGER);

INSERT INTO category_tree VALUES
(1, 'Electronics', NULL),
(2, 'Computers', 1),
(3, 'Laptops', 2),
(4, 'Furniture', NULL);
```

**Output**

```
+------------------+
|  category_name   |
+------------------+
| Computers        |
| Laptops          |
+------------------+
```

**Solution Query**

```sql
WITH RECURSIVE subcats AS (
    SELECT category_id, category_name, parent_id FROM category_tree WHERE category_id = 1

    UNION ALL

    SELECT c.category_id, c.category_name, c.parent_id
    FROM category_tree c
    INNER JOIN subcats s ON c.parent_id = s.category_id
)
SELECT category_name FROM subcats WHERE category_id <> 1 ORDER BY category_name;
```

*"Laptops" is two levels below "Electronics," not one — the recursion has to run twice (once to reach "Computers," once more to reach "Laptops") before it finds no further matches and stops. "Furniture," a sibling top-level category, never enters the recursion at all, since nothing in the chain ever points back to it.*

## Q29. A Route That Loops Back on Itself

**Topic Tag:** Recursive CTEs: Querying Hierarchies and Graphs
**Difficulty:** Hard
**Type:** Predict the Output
**Skill Focus:** Analyse (cycles in recursive CTEs)

**Problem Statement**

A flight network has routes DEL→BOM, BOM→BLR, and BLR→DEL — a loop. A recursive CTE traces every airport reachable from DEL, capped at 5 hops as a safety guard. Before running it, predict whether it actually terminates, and whether DEL reappears in the reachable set.

**Table: `flight_routes`**

| Column | Type | Description |
|---|---|---|
| `origin` | VARCHAR(10) | Departure airport |
| `destination` | VARCHAR(10) | Arrival airport |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE flight_routes (origin VARCHAR(10), destination VARCHAR(10));

INSERT INTO flight_routes VALUES ('DEL', 'BOM'), ('BOM', 'BLR'), ('BLR', 'DEL');
```

**Query to Analyze**

```sql
WITH RECURSIVE reachable AS (
    SELECT origin, destination, 1 AS hop FROM flight_routes WHERE origin = 'DEL'

    UNION ALL

    SELECT r.origin, r.destination, rc.hop + 1
    FROM flight_routes r
    INNER JOIN reachable rc ON r.origin = rc.destination
    WHERE rc.hop < 5
)
SELECT DISTINCT destination, MIN(hop) AS first_seen_hop FROM reachable GROUP BY destination ORDER BY destination;
```

**Your Task:** Without the `WHERE rc.hop < 5` guard, would this query ever finish running? With the guard in place, does DEL show up as a reachable destination?

**Answer**

```
+--------------+-----------------+
| destination  | first_seen_hop  |
+--------------+-----------------+
| BLR          |               2 |
| BOM          |               1 |
| DEL          |               3 |
+--------------+-----------------+
```

**Why:** Without any guard, this recursion would never terminate on its own — DEL→BOM→BLR→DEL→BOM→BLR→... loops forever, since nothing in a plain recursive CTE automatically detects "I've already visited this node." The `WHERE rc.hop < 5` condition is a manually-added safety cap that stops the recursive branch from generating any more rows once `hop` reaches 5, which is exactly why the query finishes at all. DEL genuinely does reappear as reachable (at hop 3, having looped all the way around), showing the loop is real, not a mistake in the data — a production version of this query would typically also track the full path visited so far and explicitly exclude revisiting a node, rather than relying on a hop-count cap alone.

## Q30. Reconstruct the Full Parts List

**Topic Tag:** Recursive CTEs: Querying Hierarchies and Graphs
**Difficulty:** Medium
**Type:** Reverse Engineering
**Skill Focus:** Reconstruct (recursive traversal)

**Problem Statement**

A bicycle manufacturer's bill of materials nests sub-parts under parent parts — a "Wheel" is part of a "Bicycle," and a "Spoke" is part of a "Wheel." Someone has already pulled the full parts explosion under "Bicycle" — every part at any depth, not just the direct children. Work out the recursive query.

**Table: `bom_parts`**

| Column | Type | Description |
|---|---|---|
| `part_id` | INTEGER | Unique identifier (PK) |
| `part_name` | VARCHAR(60) | Part name |
| `parent_part_id` | INTEGER | References `bom_parts.part_id`, `NULL` for the top-level assembly |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE bom_parts (part_id INTEGER PRIMARY KEY, part_name VARCHAR(60), parent_part_id INTEGER);

INSERT INTO bom_parts VALUES
(1, 'Bicycle', NULL),
(2, 'Frame', 1),
(3, 'Wheel', 1),
(4, 'Spoke', 3);
```

**Target Output**

```
+------------+
| part_name  |
+------------+
| Frame      |
| Spoke      |
| Wheel      |
+------------+
```

**Your Task:** Write the `WITH RECURSIVE` query that produces this full parts explosion under "Bicycle" (`part_id = 1`).

**Solution Query**

```sql
WITH RECURSIVE parts_explosion AS (
    SELECT part_id, part_name, parent_part_id FROM bom_parts WHERE part_id = 1

    UNION ALL

    SELECT b.part_id, b.part_name, b.parent_part_id
    FROM bom_parts b
    INNER JOIN parts_explosion pe ON b.parent_part_id = pe.part_id
)
SELECT part_name FROM parts_explosion WHERE part_id <> 1 ORDER BY part_name;
```

*"Spoke" is nested two levels deep (Bicycle → Wheel → Spoke), the same shape as Q28's category tree — a fixed-depth `JOIN` chain could only ever reach a hardcoded number of levels, while this recursive structure reaches "Spoke" or a part nested ten levels deeper with the exact same query, unchanged.*
