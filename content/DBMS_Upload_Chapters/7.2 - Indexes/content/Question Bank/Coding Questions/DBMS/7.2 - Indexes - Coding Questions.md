# Indexes — Coding Question Bank

Dialect: **PostgreSQL**. Every statement in this bank has been executed against a live PostgreSQL 16 instance — including several questions where the "buggy" statement genuinely throws a PostgreSQL error, reproduced verbatim.

**A note on what's graded in this chapter:** an index can never change what a query returns — only how fast it returns it. So unlike earlier chapters, the graded `Output` here is always the correct, deterministic row-level result of a verification query, never `EXPLAIN` cost numbers (those shift slightly across machines and Postgres versions even for the identical query). Where `EXPLAIN` output would help explain *why* an index matters, it appears as narrative context only, exactly the way the Indexes lessons themselves use it.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the `CREATE INDEX` (and often a verification query).
- **Bug Hunt** — a statement someone already wrote is shown along with its (genuinely erroring) output; find and fix the mistake.
- **Predict the Output** — a query is already written; state exactly what it returns before checking the answer.
- **Compare & Justify** — two or more indexing approaches are plausible; pick the better one and explain why.
- **Reverse Engineering** — you're shown an index definition and a goal; work out the query it's meant to serve.
- **Decision-Making** — a concrete symptom or design question is shown; diagnose it and recommend an approach.

## Q1. Finding a Guest by Email

**Topic Tag:** What is an Index?
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve (indexed lookup)

**Problem Statement**

A hotel booking system's front desk looks up guests by email dozens of times a day. Without help, the database would have to check every single row to find a match — an index lets it jump straight there.

**Table: `hotel_bookings_idx`**

| Column | Type | Description |
|---|---|---|
| `booking_id` | INTEGER | Unique identifier (PK) |
| `guest_email` | VARCHAR(80) | Guest's email |
| `room_number` | VARCHAR(10) | Assigned room |
| `checkin_date` | DATE | Check-in date |

Write a statement that creates an index on `guest_email`, then a query that returns `room_number` and `checkin_date` for the guest `'vikram.shetty@mail.com'`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE hotel_bookings_idx (
    booking_id INTEGER PRIMARY KEY,
    guest_email VARCHAR(80),
    room_number VARCHAR(10),
    checkin_date DATE
);

INSERT INTO hotel_bookings_idx (booking_id, guest_email, room_number, checkin_date) VALUES
(1, 'aditi.kapoor@mail.com', '204', '2026-04-10'),
(2, 'vikram.shetty@mail.com', '310', '2026-04-11'),
(3, 'neha.bhatt@mail.com', '105', '2026-04-12');
```

**Output**

```
+--------------+---------------+
| room_number  | checkin_date  |
+--------------+---------------+
| 310          |    2026-04-11 |
+--------------+---------------+
```

**Solution Query**

```sql
CREATE INDEX idx_guest_email ON hotel_bookings_idx (guest_email);

SELECT room_number, checkin_date
FROM hotel_bookings_idx
WHERE guest_email = 'vikram.shetty@mail.com';
```

*The `CREATE INDEX` statement doesn't change what the `SELECT` returns at all — run this same query without the index, and the result is identical. The index only affects how the database finds that result, which is why this chapter's grading always focuses on the row output, not on plan internals.*

## Q3. A Range Query on ISBN

**Topic Tag:** B-Tree Indexes
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Compare Values (range scan)

**Problem Statement**

A library's catalog system wants every book whose ISBN falls within a given range — the default B-tree index type keeps its entries sorted, so it naturally supports range lookups, not just exact matches.

**Table: `library_catalog_idx`**

| Column | Type | Description |
|---|---|---|
| `book_id` | INTEGER | Unique identifier (PK) |
| `isbn` | VARCHAR(20) | ISBN |
| `title` | VARCHAR(80) | Book title |
| `published_year` | INTEGER | Year published |

Write a statement that creates an index on `isbn`, then a query returning `title` and `isbn` for books with ISBN between `'978-0132350884'` and `'978-0134685991'`, sorted by ISBN.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE library_catalog_idx (
    book_id INTEGER PRIMARY KEY,
    isbn VARCHAR(20),
    title VARCHAR(80),
    published_year INTEGER
);

INSERT INTO library_catalog_idx (book_id, isbn, title, published_year) VALUES
(1, '978-0134685991', 'Effective Java', 2018),
(2, '978-0132350884', 'Clean Code', 2008),
(3, '978-0201633610', 'Design Patterns', 1994),
(4, '978-1491950357', 'Building Microservices', 2015);
```

**Output**

```
+-----------------+-----------------+
|      title      |       isbn      |
+-----------------+-----------------+
| Clean Code      | 978-0132350884  |
| Effective Java  | 978-0134685991  |
+-----------------+-----------------+
```

**Solution Query**

```sql
CREATE INDEX idx_isbn ON library_catalog_idx (isbn);

SELECT title, isbn
FROM library_catalog_idx
WHERE isbn BETWEEN '978-0132350884' AND '978-0134685991'
ORDER BY isbn;
```

*A hash index (covered in the next lesson) could only ever support `isbn = 'exact value'` — B-tree's sorted structure is what makes a `BETWEEN` range like this possible to serve efficiently at all.*

## Q4. Does the Index Help the Sort Too

**Topic Tag:** B-Tree Indexes
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (B-tree's sorted leaves)

**Problem Statement**

A support desk wants tickets listed oldest first. A B-tree index already exists on `created_at`. Before running the query, predict whether the results actually come back in the correct chronological order — a B-tree's leaf level is already sorted, which the previous lesson noted can serve `ORDER BY` "for free."

**Table: `support_tickets_idx`**

| Column | Type | Description |
|---|---|---|
| `ticket_id` | INTEGER | Unique identifier (PK) |
| `subject` | VARCHAR(80) | Ticket subject |
| `created_at` | TIMESTAMP | Creation timestamp |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE support_tickets_idx (
    ticket_id INTEGER PRIMARY KEY,
    subject VARCHAR(80),
    created_at TIMESTAMP
);

INSERT INTO support_tickets_idx (ticket_id, subject, created_at) VALUES
(1, 'Billing discrepancy', '2026-03-05 10:00'),
(2, 'Login failure', '2026-03-03 09:15'),
(3, 'Feature request', '2026-03-04 14:30');

CREATE INDEX idx_created_at ON support_tickets_idx (created_at);
```

**Query to Analyze**

```sql
SELECT subject, created_at FROM support_tickets_idx ORDER BY created_at;
```

**Your Task:** Predict the row order. Does it come back oldest-first, matching `created_at`, even though the rows were inserted in a different order?

**Answer**

```
+-----------------------+----------------------+
|        subject        |      created_at      |
+-----------------------+----------------------+
| Login failure         |  2026-03-03 09:15:00 |
| Feature request       |  2026-03-04 14:30:00 |
| Billing discrepancy   |  2026-03-05 10:00:00 |
+-----------------------+----------------------+
```

**Why:** Yes — correctly sorted oldest to newest, regardless of insertion order. `ORDER BY` always produces a correctly sorted result whether or not an index exists; what the B-tree index changes is *how* that sort happens. Because the index's leaf entries are already stored in `created_at` order, the database can walk them directly instead of pulling every row and sorting it from scratch — the query is *correct* either way, but the presence of a matching B-tree index is what can turn an expensive separate sorting step into a much cheaper walk through data that was already in order.

## Q5. Filtering and Sorting on One Composite Index

**Topic Tag:** Hash, Composite, Partial, and Expression Indexes
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (composite index)

**Problem Statement**

HR wants Engineering staff listed alphabetically by last name. A single index spanning both `department` and `last_name` — in that order — can support filtering on department *and* the alphabetical ordering within it, together.

**Table: `employees_idx`**

| Column | Type | Description |
|---|---|---|
| `emp_id` | INTEGER | Unique identifier (PK) |
| `department` | VARCHAR(40) | Department name |
| `last_name` | VARCHAR(60) | Employee's last name |
| `salary` | DECIMAL(10,2) | Salary in ₹ |

Write a statement that creates a composite index on `(department, last_name)`, then a query returning `last_name` and `salary` for the `'Engineering'` department, sorted by last name.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE employees_idx (
    emp_id INTEGER PRIMARY KEY,
    department VARCHAR(40),
    last_name VARCHAR(60),
    salary DECIMAL(10,2)
);

INSERT INTO employees_idx (emp_id, department, last_name, salary) VALUES
(1, 'Engineering', 'Sharma', 95000.00),
(2, 'Engineering', 'Bose', 88000.00),
(3, 'Sales', 'Iyer', 72000.00);
```

**Output**

```
+------------+-----------+
| last_name  |  salary   |
+------------+-----------+
| Bose       |  88000.00 |
| Sharma     |  95000.00 |
+------------+-----------+
```

**Solution Query**

```sql
CREATE INDEX idx_dept_lastname ON employees_idx (department, last_name);

SELECT last_name, salary
FROM employees_idx
WHERE department = 'Engineering'
ORDER BY last_name;
```

*Column order in a composite index matters: `(department, last_name)` serves "filter by department, sorted by last name" cleanly, since department narrows things down first and last_name is already sorted within each department group.*

## Q6. Naming an Index Twice

**Topic Tag:** What is an Index?
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (duplicate index name)

**Problem Statement**

A developer wanted to add a second index to a reservations table, for a different column, and reused a name that was already taken.

**Table: `reservations_idx`**

| Column | Type | Description |
|---|---|---|
| `reservation_id` | INTEGER | Unique identifier (PK) |
| `customer_id` | INTEGER | Customer identifier |
| `booking_date` | DATE | Date of the booking |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE reservations_idx (
    reservation_id INTEGER PRIMARY KEY,
    customer_id INTEGER,
    booking_date DATE
);

INSERT INTO reservations_idx (reservation_id, customer_id, booking_date) VALUES
(1, 101, '2026-04-01'), (2, 102, '2026-04-02');

CREATE INDEX idx_res ON reservations_idx (customer_id);
```

**Buggy Query (as submitted)**

```sql
CREATE INDEX idx_res ON reservations_idx (booking_date);
```

**Buggy Output**

```
ERROR:  relation "idx_res" already exists
```

**What's Wrong:** Index names share the same namespace as tables and other relations within a schema — `idx_res` was already claimed by the first index on `customer_id`, so trying to create a second, different index under the identical name fails outright rather than silently overwriting or renaming anything.

**Solution Query (Fixed)**

```sql
CREATE INDEX idx_res_booking_date ON reservations_idx (booking_date);
```

**Fixed Output**

```
+------------------------+
|       indexname        |
+------------------------+
| idx_res                |
| idx_res_booking_date   |
| reservations_idx_pkey  |
+------------------------+
```

*(Confirmed via `SELECT indexname FROM pg_indexes WHERE tablename = 'reservations_idx'` — three indexes now exist: the original `customer_id` index, the new `booking_date` index, and the primary key's automatic index.)*

## Q7. A Query Index Alone Could Answer

**Topic Tag:** Covering Indexes and Index-Only Scans
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (covering by coincidence)

**Problem Statement**

A product search tool creates a two-column index on `(sku, product_name)`. A lookup query asks for exactly those two columns, filtered by `sku`. Before running it, consider: does every column the query needs already live inside the index itself?

**Table: `products_search_idx`**

| Column | Type | Description |
|---|---|---|
| `product_id` | INTEGER | Unique identifier (PK) |
| `sku` | VARCHAR(20) | Stock-keeping unit code |
| `product_name` | VARCHAR(60) | Product name |
| `price` | DECIMAL(8,2) | Price in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE products_search_idx (
    product_id INTEGER PRIMARY KEY,
    sku VARCHAR(20),
    product_name VARCHAR(60),
    price DECIMAL(8,2)
);

INSERT INTO products_search_idx (product_id, sku, product_name, price) VALUES
(1, 'SKU-100', 'Wireless Mouse', 899.00),
(2, 'SKU-200', 'USB Hub', 450.00);

CREATE INDEX idx_sku_name ON products_search_idx (sku, product_name);
```

**Query to Analyze**

```sql
SELECT sku, product_name FROM products_search_idx WHERE sku = 'SKU-100';
```

**Your Task:** Does this query need anything from the underlying table that isn't already present in `idx_sku_name`?

**Answer**

```
+----------+------------------+
|   sku    |   product_name   |
+----------+------------------+
| SKU-100  | Wireless Mouse   |
+----------+------------------+
```

**Why:** Both requested columns — `sku` (the filter) and `product_name` (the output) — are already stored directly inside `idx_sku_name`. Nothing about `price` or `product_id` is ever touched. This means the index is *covering* for this specific query: every value the query needs can, in principle, be read straight from the index structure itself, without a separate trip to fetch the full table row — the exact scenario an "index-only scan" is built to take advantage of.

## Q8. An Index That Carries Extra Columns

**Topic Tag:** Covering Indexes and Index-Only Scans
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (INCLUDE clause)

**Problem Statement**

A real estate search tool always looks up a listing by its MLS number and immediately wants the address and price too. Rather than a composite index on all three columns (which would also sort by address and price, which nobody needs), PostgreSQL's `INCLUDE` clause lets extra columns ride along in the index purely for fast retrieval, without being part of the search key.

**Table: `real_estate_listings_idx`**

| Column | Type | Description |
|---|---|---|
| `listing_id` | INTEGER | Unique identifier (PK) |
| `mls_number` | VARCHAR(20) | MLS listing number |
| `address` | VARCHAR(80) | Property address |
| `price` | DECIMAL(12,2) | Price in ₹ |

Write a statement that creates an index on `mls_number` that also includes `address` and `price`, then a query returning `address` and `price` for MLS number `'MLS-5001'`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE real_estate_listings_idx (
    listing_id INTEGER PRIMARY KEY,
    mls_number VARCHAR(20),
    address VARCHAR(80),
    price DECIMAL(12,2)
);

INSERT INTO real_estate_listings_idx (listing_id, mls_number, address, price) VALUES
(1, 'MLS-5001', '12 Lake View Road', 8500000.00),
(2, 'MLS-5002', '9 Hill Crest Avenue', 6200000.00);
```

**Output**

```
+---------------------+-------------+
|       address       |    price    |
+---------------------+-------------+
| 12 Lake View Road   |  8500000.00 |
+---------------------+-------------+
```

**Solution Query**

```sql
CREATE INDEX idx_mls_covering ON real_estate_listings_idx (mls_number) INCLUDE (address, price);

SELECT address, price
FROM real_estate_listings_idx
WHERE mls_number = 'MLS-5001';
```

*`INCLUDE (address, price)` stores those two columns' values inside the index leaf entries without making them part of the sortable search key — a distinction the search key (`mls_number` alone) doesn't need, since nobody ranges or sorts by address or price here.*

## Q9. Should a Boolean Column Get Its Own Index

**Topic Tag:** When Not to Index: The Cost of Over-Indexing
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Decision-making (index selectivity)

**Problem Statement**

A subscriptions table has both `account_number` (unique per account) and `is_active` (mostly `TRUE`, a handful `FALSE`). The team wants to index one of them for a lookup tool and has asked which makes more sense to index.

**Table: `subscription_accounts_idx`**

| Column | Type | Description |
|---|---|---|
| `account_id` | INTEGER | Unique identifier (PK) |
| `account_number` | VARCHAR(20) | Account number |
| `is_active` | BOOLEAN | Whether the subscription is active |
| `plan_name` | VARCHAR(40) | Subscription plan |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE subscription_accounts_idx (
    account_id INTEGER PRIMARY KEY,
    account_number VARCHAR(20),
    is_active BOOLEAN,
    plan_name VARCHAR(40)
);

INSERT INTO subscription_accounts_idx (account_id, account_number, is_active, plan_name) VALUES
(1, 'ACC-9001', TRUE, 'Premium'),
(2, 'ACC-9002', TRUE, 'Basic'),
(3, 'ACC-9003', FALSE, 'Basic');
```

**Your Task:** Recommend which column to index, and explain why indexing the other one is generally a poor use of an index.

**Solution Query**

```sql
CREATE INDEX idx_account_number ON subscription_accounts_idx (account_number);

SELECT plan_name FROM subscription_accounts_idx WHERE account_number = 'ACC-9002';
```

**Output**

```
+------------+
| plan_name  |
+------------+
| Basic      |
+------------+
```

**Justification:** `account_number` is highly *selective* — each value matches at most one row, so an index there narrows a search from "every row" down to "exactly one" immediately, which is where indexes deliver their biggest win. `is_active` is the opposite: with only two possible values and one of them (`TRUE`) covering most of the table, an index on it can only ever narrow a search down to "most of the rows" or "a small fraction of them" — for the common case (`WHERE is_active = TRUE`), the query planner will often ignore the index entirely and just scan the table, since reading most of the table via an index isn't actually faster than reading it directly. Meanwhile, every index — including one that's rarely useful — still adds real cost: it must be updated on every `INSERT`/`UPDATE`/`DELETE` that touches the column, and it consumes disk space, for a benefit that in this case is marginal at best.

## Q10. A Composite Key for Exact Flight Lookups

**Topic Tag:** Hash, Composite, Partial, and Expression Indexes
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (composite index)

**Problem Statement**

An airline's ops dashboard always looks up a specific flight by number *and* date together — the same flight number flies daily, so neither column alone uniquely identifies a flight.

**Table: `flight_lookup_idx`**

| Column | Type | Description |
|---|---|---|
| `flight_id` | INTEGER | Unique identifier (PK) |
| `flight_number` | VARCHAR(10) | Flight number |
| `flight_date` | DATE | Date of the flight |
| `origin` | VARCHAR(10) | Origin airport code |

Write a statement that creates a composite index on `(flight_number, flight_date)`, then a query returning `origin` for flight `'AI202'` on `'2026-04-11'`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE flight_lookup_idx (
    flight_id INTEGER PRIMARY KEY,
    flight_number VARCHAR(10),
    flight_date DATE,
    origin VARCHAR(10)
);

INSERT INTO flight_lookup_idx (flight_id, flight_number, flight_date, origin) VALUES
(1, 'AI202', '2026-04-10', 'DEL'),
(2, 'AI202', '2026-04-11', 'DEL'),
(3, 'AI305', '2026-04-10', 'BOM');
```

**Output**

```
+--------+
| origin |
+--------+
| DEL    |
+--------+
```

```sql
FROM flight_lookup_idx

```

## Q13. Reconstruct the Query This Index Was Built For

**Topic Tag:** What is an Index?
**Difficulty:** Hard
**Type:** Reverse Engineering
**Skill Focus:** Reconstruct (covering index)

**Problem Statement**

An analyst already created the index below on an orders table, deliberately including two extra columns. Work out the query this index was almost certainly designed to serve well — one that filters on the search key and requests exactly the included columns.

**Table: `orders_idx13`**

| Column | Type | Description |
|---|---|---|
| `order_id` | INTEGER | Unique identifier (PK) |
| `customer_id` | INTEGER | Customer identifier |
| `order_date` | DATE | Date of the order |
| `total` | DECIMAL(10,2) | Order total in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE orders_idx13 (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER,
    order_date DATE,
    total DECIMAL(10,2)
);

INSERT INTO orders_idx13 (order_id, customer_id, order_date, total) VALUES
(1, 501, '2026-03-01', 1200.00), (2, 501, '2026-03-05', 800.00), (3, 502, '2026-03-02', 500.00);

CREATE INDEX idx_orders_cust ON orders_idx13 (customer_id) INCLUDE (order_date, total);
```

**Target Output**

```
+-------------+---------+
| order_date  |  total  |
+-------------+---------+
| 2026-03-01  | 1200.00 |
| 2026-03-05  |  800.00 |
+-------------+---------+
```

**Your Task:** Write the query — for customer 501 — that produces exactly this output, using only columns the index actually carries.

**Solution Query**

```sql
SELECT order_date, total
FROM orders_idx13
WHERE customer_id = 501
ORDER BY order_date;
```

*This is a query `idx_orders_cust` could satisfy as an index-only scan: `customer_id` is the search key, and `order_date`/`total` are both riding along via `INCLUDE` — nothing here needs a column the index doesn't already carry.*

**Topic Tag:** B-Tree Indexes
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (non-immutable function in an index)

**Problem Statement**

A developer wanted an index to speed up "how long ago was this logged" queries and tried building it directly on a computed age expression. It fails immediately.

**Table: `event_logs_idx`**

| Column | Type | Description |
|---|---|---|
| `log_id` | INTEGER | Unique identifier (PK) |
| `event_name` | VARCHAR(60) | Event name |
| `logged_at` | TIMESTAMP | When the event was logged |

```sql

);

(1, 'Login', '2026-03-01 10:00'), (2, 'Logout', '2026-03-01 11:00');
```


**Fixed Output**

```
+-------------+
| event_name  |
+-------------+
| Logout      |
+-------------+
```

*Indexing the raw, unchanging `logged_at` column directly — and doing the "how long ago" math in the query itself at query time — sidesteps the problem entirely, since `logged_at` never changes meaning after the fact the way `NOW() - logged_at` would.*

## Q20. An Index the Query Doesn't Actually Use

**Topic Tag:** Hash, Composite, Partial, and Expression Indexes
**Difficulty:** Medium
**Type:** Decision-Making
**Skill Focus:** Decision-making (expression must match exactly)

**Problem Statement**

A directory app built an expression index on `LOWER(full_name)` to support case-insensitive search. A query still filters on the raw `full_name` column without wrapping it in `LOWER()`. Both queries below return correct, identical data — but only one of them can actually use the index. Diagnose which, and recommend a fix.

**Table: `contacts_expr_idx`**

| Column | Type | Description |
|---|---|---|
| `contact_id` | INTEGER | Unique identifier (PK) |
| `full_name` | VARCHAR(60) | Contact's full name |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE contacts_expr_idx (
    contact_id INTEGER PRIMARY KEY,
    full_name VARCHAR(60)
);

INSERT INTO contacts_expr_idx (contact_id, full_name) VALUES
(1, 'Rohit Sinha'), (2, 'Divya Rao');

CREATE INDEX idx_lower_name ON contacts_expr_idx (LOWER(full_name));
```

**Query A (matches the expression)**

```sql
SELECT contact_id FROM contacts_expr_idx WHERE LOWER(full_name) = 'rohit sinha';
```

```
+-------------+
| contact_id  |
+-------------+
|           1 |
+-------------+
```

**Query B (doesn't match the expression)**

```sql
SELECT contact_id FROM contacts_expr_idx WHERE full_name = 'Rohit Sinha';
```

```
+-------------+
| contact_id  |
+-------------+
|           1 |
+-------------+
```

| `action_type` | VARCHAR(20) | Type of action |
| `log_note` | VARCHAR(200) | Free-text note |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE audit_log_idx (
    log_id INTEGER PRIMARY KEY,
    actor_id INTEGER,
    action_type VARCHAR(20),
    log_note VARCHAR(200)
);

INSERT INTO audit_log_idx (log_id, actor_id, action_type, log_note) VALUES
(1, 1, 'LOGIN', 'note a'), (2, 2, 'UPDATE', 'note b');
```

**Your Task:** Write the index (or indexes) you'd actually create, and explain what you'd say to the new engineer.

**Solution Query**

```sql
CREATE INDEX idx_actor_id ON audit_log_idx (actor_id);

SELECT action_type FROM audit_log_idx WHERE actor_id = 1;
```

**Output**

```
+---------------+
|  action_type  |
+---------------+
| LOGIN         |
+---------------+
```

**Justification:** Every index is a standing cost, not a one-time convenience: it must be updated on every `INSERT` into the table (an audit log, of all tables, is likely to be *write-heavy*), it takes up disk space, and an unused index provides literally zero benefit to any query while still paying that cost forever. "Just in case" indexing optimizes for a hypothetical future query at the expense of every write happening today. The right move is indexing `actor_id` — the column genuinely being filtered on — and revisiting the decision only if and when a new, real query pattern actually shows up, rather than speculatively indexing `action_type` or `log_note` against queries that may never be written.

## Q29. A Table with Five Indexes and Slow Writes

**Topic Tag:** When Not to Index: The Cost of Over-Indexing
**Difficulty:** Hard
**Type:** Decision-Making
**Skill Focus:** Decision-making (index maintenance cost)

**Problem Statement**

A products table has picked up five separate single-column indexes over time, added by different engineers solving different problems. Bulk product imports have gotten noticeably slower. Diagnose the likely cause and recommend an approach.

**Table: `overindexed_products`**

| Column | Type | Description |
|---|---|---|
| `product_id` | INTEGER | Unique identifier (PK) |
| `sku` | VARCHAR(20) | Stock-keeping unit |
| `product_name` | VARCHAR(60) | Product name |
| `category` | VARCHAR(30) | Product category |
| `color` | VARCHAR(20) | Product color |
| `size_label` | VARCHAR(10) | Size label |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE overindexed_products (
    product_id INTEGER PRIMARY KEY,
    sku VARCHAR(20),
    product_name VARCHAR(60),
    category VARCHAR(30),
    color VARCHAR(20),
    size_label VARCHAR(10)
);

CREATE INDEX idx_op_sku ON overindexed_products (sku);
CREATE INDEX idx_op_name ON overindexed_products (product_name);
CREATE INDEX idx_op_category ON overindexed_products (category);
CREATE INDEX idx_op_color ON overindexed_products (color);
CREATE INDEX idx_op_size ON overindexed_products (size_label);
```

**Current Indexes**

```sql
SELECT indexname FROM pg_indexes WHERE tablename = 'overindexed_products' ORDER BY indexname;
```

```
+-----------------------------+
|          indexname          |
+-----------------------------+
| idx_op_category             |
| idx_op_color                |
| idx_op_name                 |
| idx_op_size                 |
| idx_op_sku                  |
| overindexed_products_pkey   |
+-----------------------------+
```

**Your Task:** Diagnose why bulk imports slowed down, and recommend how the team should decide which of these five indexes to keep.

**Answer:** Every one of these five indexes has to be updated on *every single `INSERT`* into the table, in addition to the table row itself — a bulk import of thousands of products means each new row triggers six total structure updates (five indexes plus the primary key), not one. This is the direct cost side of the read/write tradeoff: indexes make specific *reads* faster at the price of making *every write* slower, and that price scales with however many indexes exist, regardless of whether all five are actually earning their keep. The right next step isn't assuming all five are useless, nor assuming all five are essential — it's checking actual usage (PostgreSQL tracks per-index scan counts in `pg_stat_user_indexes`) and dropping whichever indexes show zero or near-zero real-world lookups, keeping only the ones actively serving genuine query patterns. An index that's never used by any query is pure cost with no offsetting benefit — exactly the over-indexing trap this lesson is about.

## Q30. A Unique Index That Finds a Real Problem

**Topic Tag:** When Not to Index: The Cost of Over-Indexing
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (UNIQUE index on non-unique data)

**Problem Statement**

A team wants to enforce one account per email going forward, and tries adding a unique index to a table that — unbeknownst to them — already has a duplicate email from a past data entry mistake.

**Table: `customer_accounts_idx`**

| Column | Type | Description |
|---|---|---|
| `account_id` | INTEGER | Unique identifier (PK) |
| `email` | VARCHAR(80) | Customer's email |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE customer_accounts_idx (
    account_id INTEGER PRIMARY KEY,
    email VARCHAR(80)
);

INSERT INTO customer_accounts_idx (account_id, email) VALUES
(1, 'meera.shah@mail.com'), (2, 'karan.m@mail.com'), (3, 'meera.shah@mail.com');
```

**Buggy Query (as submitted)**

```sql
CREATE UNIQUE INDEX idx_unique_email ON customer_accounts_idx (email);
```

**Buggy Output**

```
ERROR:  could not create unique index "idx_unique_email"
DETAIL:  Key (email)=(meera.shah@mail.com) is duplicated.
```

**What's Wrong:** A `UNIQUE` index isn't just a performance tool — it's a genuine data-integrity constraint, and PostgreSQL refuses to create one that the *existing* data already violates. Account 1 and account 3 both have `'meera.shah@mail.com'`, so enforcing uniqueness right now is impossible without first resolving that duplicate — this error is doing exactly its job, surfacing a real data quality problem the team didn't know about.

**Solution Query (Fixed)**

```sql
DELETE FROM customer_accounts_idx a
USING customer_accounts_idx b
WHERE a.account_id > b.account_id AND a.email = b.email;

CREATE UNIQUE INDEX idx_unique_email ON customer_accounts_idx (email);
```

**Fixed Output**

```
+-------------+------------------------+
| account_id  |         email          |
+-------------+------------------------+
|           1 | meera.shah@mail.com    |
|           2 | karan.m@mail.com       |
+-------------+------------------------+
```

*The duplicate (account 3, the higher `account_id`) is removed first, and only then does `CREATE UNIQUE INDEX` succeed — going forward, any attempt to insert another `'meera.shah@mail.com'` account will now be rejected immediately, exactly the guarantee the team wanted in the first place.*
