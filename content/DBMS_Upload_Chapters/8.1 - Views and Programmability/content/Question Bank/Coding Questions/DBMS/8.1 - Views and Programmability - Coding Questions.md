# Views and Programmability — Coding Question Bank

Dialect: **PostgreSQL** (`plpgsql` for procedures, functions, and triggers — the same dialect this chapter's own lessons use). Every statement in this bank has been executed against a live PostgreSQL 16 instance; the `Output` shown for each question is the actual result — including several questions where the "buggy" statement genuinely throws a PostgreSQL error, reproduced verbatim.

**Question Types used in this bank:**
- **Write the Query** — a problem statement, a schema, and you write the `CREATE VIEW`/`PROCEDURE`/`FUNCTION`/`TRIGGER` (plus a verification query).
- **Bug Hunt** — a statement someone already wrote is shown along with its (genuinely erroring) output; find and fix the mistake.
- **Predict the Output** — a statement is already written; state exactly what happens before checking the answer.
- **Compare & Justify** — two or more approaches are plausible; pick the better one and explain why.
- **Reverse Engineering** — you're shown a target result; work out the definition behind it.
- **Decision-Making** — a concrete symptom or design question is shown; diagnose it and recommend an approach.

## Q1. Naming the "Active Members" Query

**Topic Tag:** Views: Naming a Query and Reusing It
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A gym's front desk repeatedly runs the same filter — active members and their plan — dozens of times a day. A view lets that query be named once and reused by anyone, without retyping the `WHERE` clause every time.

**Table: `gym_members_v`**

| Column | Type | Description |
|---|---|---|
| `member_id` | INTEGER | Unique identifier (PK) |
| `member_name` | VARCHAR(60) | Member's name |
| `plan_type` | VARCHAR(20) | Membership plan |
| `is_active` | BOOLEAN | Whether the membership is currently active |

Write a statement that creates a view named `active_members_view` returning `member_name` and `plan_type` for active members, then query it.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE gym_members_v (
    member_id INTEGER PRIMARY KEY,
    member_name VARCHAR(60),
    plan_type VARCHAR(20),
    is_active BOOLEAN
);

INSERT INTO gym_members_v (member_id, member_name, plan_type, is_active) VALUES
(1, 'Varun Oberoi', 'Premium', TRUE),
(2, 'Kiran Shetty', 'Basic', FALSE),
(3, 'Naina Chopra', 'Premium', TRUE);
```

**Output**

```
+---------------+------------+
|  member_name  | plan_type  |
+---------------+------------+
| Naina Chopra  | Premium    |
| Varun Oberoi  | Premium    |
+---------------+------------+
```

**Solution Query**

```sql
CREATE VIEW active_members_view AS
SELECT member_name, plan_type FROM gym_members_v WHERE is_active = TRUE;

SELECT * FROM active_members_view ORDER BY member_name;
```

*Once created, `active_members_view` can be queried exactly like a table — `SELECT * FROM active_members_view` — without anyone needing to remember or retype the underlying filter.*

## Q2. A View Spanning Two Tables

**Topic Tag:** Views: Naming a Query and Reusing It
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve

**Problem Statement**

A reporting tool wants a simple, reusable "who ordered what" view combining customers and orders, so nobody has to rewrite the join every time.

**Table: `customers_v`**

| Column | Type | Description |
|---|---|---|
| `customer_id` | INTEGER | Unique identifier (PK) |
| `customer_name` | VARCHAR(60) | Customer's name |

**Table: `orders_v`**

| Column | Type | Description |
|---|---|---|
| `order_id` | INTEGER | Unique identifier (PK) |
| `customer_id` | INTEGER | References `customers_v.customer_id` |
| `amount` | DECIMAL(8,2) | Order amount in ₹ |

Write a statement that creates a view named `order_summary_view` joining the two tables, returning `customer_name` and `amount`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE customers_v (
    customer_id INTEGER PRIMARY KEY,
    customer_name VARCHAR(60)
);

CREATE TABLE orders_v (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER,
    amount DECIMAL(8,2)
);

INSERT INTO customers_v VALUES (1, 'Tanya Bose'), (2, 'Karan Malhotra');
INSERT INTO orders_v VALUES (1, 1, 1200.00), (2, 2, 850.00);
```

**Output**

```
+-----------------+----------+
|  customer_name  |  amount  |
+-----------------+----------+
| Karan Malhotra  |  850.00  |
| Tanya Bose      | 1200.00  |
+-----------------+----------+
```

**Solution Query**

```sql
CREATE VIEW order_summary_view AS
SELECT c.customer_name, o.amount
FROM customers_v c JOIN orders_v o ON c.customer_id = o.customer_id;

SELECT * FROM order_summary_view ORDER BY customer_name;
```

## Q3. Does an UPDATE Through a View Reach the Table

**Topic Tag:** Updatable Views and Their Limitations
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (simple updatable views)

**Problem Statement**

A view selects a single table's columns with a plain `WHERE` filter — no joins, no aggregation. Before running an `UPDATE` directly against this view, predict whether the change actually reaches the underlying `products_v` table.

**Table: `products_v`**

| Column | Type | Description |
|---|---|---|
| `product_id` | INTEGER | Unique identifier (PK) |
| `product_name` | VARCHAR(60) | Product name |
| `price` | DECIMAL(8,2) | Price in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE products_v (
    product_id INTEGER PRIMARY KEY,
    product_name VARCHAR(60),
    price DECIMAL(8,2)
);

INSERT INTO products_v VALUES (1, 'USB Cable', 250.00), (2, 'Desk Lamp', 800.00);

CREATE VIEW cheap_products_view AS
SELECT product_id, product_name, price FROM products_v WHERE price < 500;
```

**Statement to Analyze**

```sql
UPDATE cheap_products_view SET price = 300.00 WHERE product_id = 1;
```

**Your Task:** Does `products_v` (the base table) reflect this change afterward?

**Answer**

```
+-------------+---------------+---------+
| product_id  | product_name  |  price  |
+-------------+---------------+---------+
|          1  | USB Cable     |  300.00 |
|          2  | Desk Lamp     |  800.00 |
+-------------+---------------+---------+
```

**Why:** Yes — `cheap_products_view` is what PostgreSQL calls "automatically updatable": it selects from exactly one table, applies no aggregation, no `DISTINCT`, and no set operations. For a view this simple, PostgreSQL can unambiguously translate `UPDATE cheap_products_view SET price = 300.00 WHERE product_id = 1` back into the equivalent `UPDATE products_v SET price = 300.00 WHERE product_id = 1` automatically, with no special setup required. This automatic translation is only possible because there's exactly one row in the base table that could correspond to each row in the view — the moment a view involves a join or a `GROUP BY`, that one-to-one correspondence breaks down, which is exactly what the next few questions explore.

## Q4. A Materialized View's First Snapshot

**Topic Tag:** Materialized Views
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Summarize

**Problem Statement**

A monthly sales report runs an expensive aggregation repeatedly throughout the day. A materialized view computes it once and stores the *result*, not just the query — subsequent reads are fast, at the cost of the data being a snapshot rather than always current.

**Table: `sales_data_v`**

| Column | Type | Description |
|---|---|---|
| `sale_id` | INTEGER | Unique identifier (PK) |
| `region` | VARCHAR(20) | Sales region |
| `amount` | DECIMAL(10,2) | Sale amount in ₹ |

Write a statement that creates a materialized view named `monthly_sales_mv`, summing `amount` per `region`, then query it.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE sales_data_v (
    sale_id INTEGER PRIMARY KEY,
    region VARCHAR(20),
    amount DECIMAL(10,2)
);

INSERT INTO sales_data_v VALUES (1, 'North', 5000.00), (2, 'South', 3000.00);
```

**Output**

```
+---------+--------------+
| region  | total_sales  |
+---------+--------------+
| North   |    5000.00   |
| South   |    3000.00   |
+---------+--------------+
```

**Solution Query**

```sql
CREATE MATERIALIZED VIEW monthly_sales_mv AS
SELECT region, SUM(amount) AS total_sales FROM sales_data_v GROUP BY region;

SELECT * FROM monthly_sales_mv ORDER BY region;
```

*Unlike a regular view, this result is physically stored — querying `monthly_sales_mv` reads the stored snapshot directly, without re-running the `GROUP BY` aggregation each time.*

## Q5. A Materialized View That Didn't Notice New Data

**Topic Tag:** Materialized Views
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (staleness until REFRESH)

**Problem Statement**

A new sale gets recorded in `sales_data_v`. A dashboard querying `monthly_sales_mv` afterward should show the updated total — but it doesn't, and nobody touched the materialized view's definition.

**Table:** `sales_data_v`, **Materialized View:** `monthly_sales_mv` *(from Q4)*

**New Sale Recorded**

```sql
INSERT INTO sales_data_v VALUES (3, 'North', 2000.00);
```

**Buggy Query (as run right after the insert)**

```sql
SELECT * FROM monthly_sales_mv ORDER BY region;
```

**Buggy Output**

```
+---------+--------------+
| region  | total_sales  |
+---------+--------------+
| North   |    5000.00   |
| South   |    3000.00   |
+---------+--------------+
(North should now total 7000.00, but the materialized view still shows the old 5000.00)
```

**What's Wrong:** A materialized view is a genuine, physical snapshot — it does not automatically re-run its defining query when the underlying table changes, unlike a regular view (which always recomputes fresh on every read, as Q3 implicitly relied on). The new ₹2,000 North sale is real and already committed to `sales_data_v`, but `monthly_sales_mv` has no way of knowing that until it's explicitly told to catch up.

**Solution Query (Fixed)**

```sql
REFRESH MATERIALIZED VIEW monthly_sales_mv;

SELECT * FROM monthly_sales_mv ORDER BY region;
```

**Fixed Output**

```
+---------+--------------+
| region  | total_sales  |
+---------+--------------+
| North   |    7000.00   |
| South   |    3000.00   |
+---------+--------------+
```

*This staleness isn't a flaw to be "fixed" once and forgotten — it's the fundamental tradeoff a materialized view makes: fast reads of a precomputed snapshot, in exchange for needing a deliberate `REFRESH` (run manually, or scheduled) any time the underlying data changes and the view needs to catch up.*

## Q6. A Procedure That Updates Two Tables Together

**Topic Tag:** Stored Procedures
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (grouped operation)

**Problem Statement**

Checking out a library book means two things happening together: the book's status changes, and a log entry records who borrowed it. A stored procedure wraps both statements into one named, reusable operation.

**Table: `library_books_v`**

| Column | Type | Description |
|---|---|---|
| `book_id` | INTEGER | Unique identifier (PK) |
| `title` | VARCHAR(80) | Book title |
| `status` | VARCHAR(20) | Available / Checked Out |

**Table: `checkout_log_v`**

| Column | Type | Description |
|---|---|---|
| `log_id` | SERIAL | Unique identifier (PK) |
| `book_id` | INTEGER | Book that was checked out |
| `borrower_name` | VARCHAR(60) | Borrower's name |

Write a procedure `checkout_book(p_book_id, p_borrower_name)` that updates the book's status and logs the checkout, then call it.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE library_books_v (
    book_id INTEGER PRIMARY KEY,
    title VARCHAR(80),
    status VARCHAR(20)
);

CREATE TABLE checkout_log_v (
    log_id SERIAL PRIMARY KEY,
    book_id INTEGER,
    borrower_name VARCHAR(60)
);

INSERT INTO library_books_v VALUES (1, 'Clean Code', 'Available'), (2, 'Effective Java', 'Available');
```

**Output**

```
library_books_v:
+---------+-----------------+--------------+
| book_id |      title      |    status    |
+---------+-----------------+--------------+
|       1 | Clean Code      | Checked Out  |
|       2 | Effective Java  | Available    |
+---------+-----------------+--------------+

checkout_log_v:
+---------+----------------+
| book_id | borrower_name  |
+---------+----------------+
|       1 | Rohan Mehta    |
+---------+----------------+
```

**Solution Query**

```sql
CREATE PROCEDURE checkout_book(p_book_id INTEGER, p_borrower_name VARCHAR)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE library_books_v SET status = 'Checked Out' WHERE book_id = p_book_id;
    INSERT INTO checkout_log_v (book_id, borrower_name) VALUES (p_book_id, p_borrower_name);
END;
$$;

CALL checkout_book(1, 'Rohan Mehta');
```

*One `CALL` guarantees both statements run together, every time — no caller can accidentally update the book's status while forgetting to log it, or vice versa.*

## Q7. Two Updates from One Call

**Topic Tag:** Stored Procedures
**Difficulty:** Medium
**Type:** Predict the Output
**Skill Focus:** Analyse (multi-statement procedure)

**Problem Statement**

A procedure applies a late fee by running two separate `UPDATE` statements — one adjusting the balance, one incrementing a fee counter. Before calling it, predict the final state of both columns.

**Table: `accounts_v`**

| Column | Type | Description |
|---|---|---|
| `account_id` | INTEGER | Unique identifier (PK) |
| `balance` | DECIMAL(10,2) | Account balance in ₹ |
| `fee_count` | INTEGER | Number of fees applied so far |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE accounts_v (
    account_id INTEGER PRIMARY KEY,
    balance DECIMAL(10,2),
    fee_count INTEGER
);

INSERT INTO accounts_v VALUES (1, 1000.00, 0);

CREATE PROCEDURE apply_late_fee(p_account_id INTEGER, p_fee DECIMAL)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE accounts_v SET balance = balance - p_fee WHERE account_id = p_account_id;
    UPDATE accounts_v SET fee_count = fee_count + 1 WHERE account_id = p_account_id;
END;
$$;
```

**Statement to Analyze**

```sql
CALL apply_late_fee(1, 50.00);
```

**Your Task:** Predict both `balance` and `fee_count` after this single call.

**Answer**

```
+-------------+----------+------------+
| account_id  | balance  | fee_count  |
+-------------+----------+------------+
|          1  |  950.00  |         1  |
+-------------+----------+------------+
```

**Why:** Both `UPDATE` statements inside the procedure body run as part of the same `CALL` — `balance` drops from 1000.00 to 950.00 (the ₹50 fee subtracted), and `fee_count` increments from 0 to 1, in a single logical operation from the caller's perspective. This is the same "wrap multiple statements into one guaranteed unit" value proposition as Q6, just with both statements touching the same row instead of two different tables.

## Q8. A Function for a Reusable Calculation

**Topic Tag:** User-Defined Functions
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Transform

**Problem Statement**

A catalog needs discounted prices computed the same way, consistently, everywhere it's needed — a user-defined function names that calculation once and returns a value usable inside any `SELECT`.

**Table: `catalog_items_v`**

| Column | Type | Description |
|---|---|---|
| `item_id` | INTEGER | Unique identifier (PK) |
| `item_name` | VARCHAR(60) | Item name |
| `price` | DECIMAL(8,2) | List price in ₹ |

Write a function `calculate_discounted_price(price, discount_pct)` returning the discounted price rounded to 2 decimals, then use it in a `SELECT`.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE catalog_items_v (
    item_id INTEGER PRIMARY KEY,
    item_name VARCHAR(60),
    price DECIMAL(8,2)
);

INSERT INTO catalog_items_v VALUES (1, 'Backpack', 2000.00), (2, 'Water Bottle', 400.00);
```

**Output**

```
+----------------+-------------------+
|   item_name    | discounted_price  |
+----------------+-------------------+
| Backpack       |          1700.00  |
| Water Bottle   |           340.00  |
+----------------+-------------------+
```

**Solution Query**

```sql
CREATE FUNCTION calculate_discounted_price(p_price DECIMAL, p_discount_pct DECIMAL)
RETURNS DECIMAL
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN ROUND(p_price * (1 - p_discount_pct / 100), 2);
END;
$$;

SELECT item_name, calculate_discounted_price(price, 15) AS discounted_price
FROM catalog_items_v
ORDER BY item_name;
```

*Unlike a procedure (`CALL`ed for its side effects), a function is invoked with plain `SELECT` and returns a value directly usable in an expression — here, once per row, just like a built-in function such as `ROUND` or `UPPER`.*

## Q9. One Function, or the Same Formula Everywhere

**Topic Tag:** User-Defined Functions
**Difficulty:** Medium
**Type:** Compare & Justify
**Skill Focus:** Decision-making (DRY via a function)

**Problem Statement**

Two engineers need the same 20%-off calculation in several different reports. One suggests writing `ROUND(price * (1 - 20.0 / 100), 2)` inline everywhere it's needed; the other suggests calling the `calculate_discounted_price` function from Q8. Both produce identical numbers today — you've been asked which to standardize on.

**Table:** `catalog_items_v` *(same as Q8)*

**Function Version**

```sql
SELECT item_name, calculate_discounted_price(price, 20) AS discounted_price
FROM catalog_items_v
ORDER BY item_name;
```

**Inline Version**

```sql
SELECT item_name, ROUND(price * (1 - 20.0 / 100), 2) AS discounted_price
FROM catalog_items_v
ORDER BY item_name;
```

**Output (identical for both)**

```
+----------------+-------------------+
|   item_name    | discounted_price  |
+----------------+-------------------+
| Backpack       |          1600.00  |
| Water Bottle   |           320.00  |
+----------------+-------------------+
```

**Justification:** Today, with a fixed 20% rate, both give the same answer — but the function version has exactly one place where the discount formula lives. If the business later decides discounts should round differently, or cap at a maximum, or apply a minimum floor price, that logic changes in the function's body *once*, and every query calling `calculate_discounted_price` picks up the fix automatically. The inline version means finding and updating every single copy-pasted `ROUND(price * (1 - x / 100), 2)` scattered across every report — and missing even one leaves an inconsistency that's easy to overlook. A function is the right call whenever the same formula is likely to be reused in more than one place, exactly the same "name it once, reuse it" reasoning behind views in this chapter's first lesson, just applied to a calculation instead of a query.

## Q10. Logging Every New Hire Automatically

**Topic Tag:** Triggers
**Difficulty:** Medium
**Type:** Write the Query
**Skill Focus:** Retrieve (automatic side effect)

**Problem Statement**

HR wants every new employee insertion automatically logged to an audit table — without relying on every application or script that might insert an employee to remember to log it separately. A trigger fires the logging automatically, at the database level, no matter what inserted the row.

**Table: `employees_trg_v`**

| Column | Type | Description |
|---|---|---|
| `emp_id` | INTEGER | Unique identifier (PK) |
| `emp_name` | VARCHAR(60) | Employee's name |

**Table: `employee_audit_v`**

| Column | Type | Description |
|---|---|---|
| `audit_id` | SERIAL | Unique identifier (PK) |
| `emp_id` | INTEGER | Employee that was inserted |
| `action` | VARCHAR(20) | What happened |

Write a trigger function and trigger that inserts an audit row whenever a new employee is inserted, then insert an employee and confirm the audit log picked it up automatically.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE employees_trg_v (
    emp_id INTEGER PRIMARY KEY,
    emp_name VARCHAR(60)
);

CREATE TABLE employee_audit_v (
    audit_id SERIAL PRIMARY KEY,
    emp_id INTEGER,
    action VARCHAR(20)
);
```

**Output**

```
employees_trg_v:
+---------+-------------+
| emp_id  |  emp_name   |
+---------+-------------+
|      1  | Farhan Ali  |
+---------+-------------+

employee_audit_v:
+---------+-----------+
| emp_id  |  action   |
+---------+-----------+
|      1  | INSERTED  |
+---------+-----------+
```

**Solution Query**

```sql
CREATE FUNCTION log_employee_insert() RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO employee_audit_v (emp_id, action) VALUES (NEW.emp_id, 'INSERTED');
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_employee_insert
AFTER INSERT ON employees_trg_v
FOR EACH ROW EXECUTE FUNCTION log_employee_insert();

INSERT INTO employees_trg_v VALUES (1, 'Farhan Ali');
```

*Nobody explicitly told the database to populate `employee_audit_v` — the plain `INSERT INTO employees_trg_v` triggered it automatically, via `NEW`, a special reference (available inside trigger functions) to the row that was just inserted.*

## Q14. Deleting Through a Simple View

**Topic Tag:** Updatable Views and Their Limitations
**Difficulty:** Easy
**Type:** Write the Query
**Skill Focus:** Retrieve (updatable view, DELETE)

**Problem Statement**

A pharmacy wants a view of pending prescription refills, and confirms that removing a row through that view (once it's been handled) removes it from the base table too.

**Table: `prescriptions_v`**

| Column | Type | Description |
|---|---|---|
| `prescription_id` | INTEGER | Unique identifier (PK) |
| `patient_name` | VARCHAR(60) | Patient's name |
| `status` | VARCHAR(20) | Pending / Filled |

Write a statement that creates view `unfilled_refills_view` for `status = 'Pending'`, then deletes prescription 1 through the view.

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE prescriptions_v (
    prescription_id INTEGER PRIMARY KEY,
    patient_name VARCHAR(60),
    status VARCHAR(20)
);

INSERT INTO prescriptions_v VALUES (1, 'Kavya Nair', 'Pending'), (2, 'Rohit Sinha', 'Filled');
```

**Before**

```
+-------------------+---------------+----------+
| prescription_id   | patient_name  |  status  |
+-------------------+---------------+----------+
|                1  | Kavya Nair    | Pending  |
|                2  | Rohit Sinha   | Filled   |
+-------------------+---------------+----------+
```

**Solution Query**

```sql
CREATE VIEW unfilled_refills_view AS
SELECT prescription_id, patient_name FROM prescriptions_v WHERE status = 'Pending';

DELETE FROM unfilled_refills_view WHERE prescription_id = 1;
```

**Output (base table after the DELETE)**

```
+-------------------+---------------+---------+
```

## Q15. Can't Update What's Already Been Summed

**Topic Tag:** Updatable Views and Their Limitations
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (aggregated views aren't updatable)

**Problem Statement**

A view sums sales by region. Someone tries to "correct" a total by updating it directly through the view — Postgres refuses outright.

**Table: `sales_rows_v`**

| Column | Type | Description |
|---|---|---|
| `sale_id` | INTEGER | Unique identifier (PK) |
| `region` | VARCHAR(20) | Sales region |
| `amount` | DECIMAL(10,2) | Sale amount in ₹ |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE sales_rows_v (
    sale_id INTEGER PRIMARY KEY,
    region VARCHAR(20),
    amount DECIMAL(10,2)
);

INSERT INTO sales_rows_v VALUES (1, 'North', 5000.00), (2, 'South', 3000.00);

CREATE VIEW sales_totals_view AS
SELECT region, SUM(amount) AS total FROM sales_rows_v GROUP BY region;
```

**Buggy Statement (as attempted)**

```sql
UPDATE sales_totals_view SET total = 9999.00 WHERE region = 'North';
```

**Buggy Output**

```
ERROR:  cannot update view "sales_totals_view"
DETAIL:  Views containing GROUP BY are not automatically updatable.
HINT:  To enable updating the view, provide an INSTEAD OF UPDATE trigger or an unconditional ON UPDATE DO INSTEAD rule.
```

## Q19. When a Regular View Beats a Materialized One

**Topic Tag:** Materialized Views
**Difficulty:** Hard
**Type:** Compare & Justify
**Skill Focus:** Decision-making (view vs. materialized view tradeoff)

**Problem Statement**

The same store-sales aggregation exists as both a regular view and a materialized view. One always reflects the current data; the other is fast but can drift stale. You've been asked to explain when each is the right choice for a real application.

**Regular View (always fresh)**

```sql

SELECT store_name, SUM(amount) AS total_sales FROM store_sales_v GROUP BY store_name;

SELECT * FROM store_sales_regular_view ORDER BY store_name;
```

```
+------------------+---------------+
|    store_name    | total_sales   |
+------------------+---------------+
| Downtown Store   |     5000.00   |
| Mall Store       |     2500.00   |
+------------------+---------------+
```

**Materialized View (still stale, not yet refreshed)**

```sql
SELECT * FROM store_sales_mv ORDER BY store_name;
```

```
+------------------+---------------+
|    store_name    | total_sales   |
+------------------+---------------+
| Downtown Store   |     4000.00   |
| Mall Store       |     2500.00   |
+------------------+---------------+
```

**Your Task:** Recommend which to use for (a) a live "current inventory value" dashboard that must never show outdated numbers, and (b) a monthly executive report built from a genuinely expensive multi-table aggregation, refreshed nightly.

The deciding question is always: does this specific use case tolerate a snapshot, or does it genuinely require the current truth?

```sql
CREATE PROCEDURE clean_all_rooms(p_room_ids INTEGER[])
LANGUAGE plpgsql
AS $$
DECLARE
    rid INTEGER;
BEGIN
    FOREACH rid IN ARRAY p_room_ids LOOP
        UPDATE hotel_rooms_v SET status = 'Clean' WHERE room_id = rid;
```

```
+---------+--------------+---------+
```

## Q26. A Function That Forgets to Return

**Topic Tag:** User-Defined Functions
**Difficulty:** Medium
**Type:** Bug Hunt
**Skill Focus:** Debug (missing RETURN in every branch)

**Problem Statement**

A function only has an `IF`, with no `ELSE` — for any age 25 or older, execution reaches the end of the function body having never hit a `RETURN` at all.

```sql
CREATE FUNCTION risky_tier(p_age INTEGER)

$$;
```

## Q29. A Trigger That Blocks a Delete

**Topic Tag:** Triggers
**Difficulty:** Hard
**Type:** Predict the Output
**Skill Focus:** Analyse (trigger raising an exception)

**Problem Statement**

A trigger is meant to prevent locked accounts from ever being deleted, by raising an exception when someone tries. Before attempting to delete a locked account, predict what happens.

**Table: `locked_accounts_v`**

| Column | Type | Description |
|---|---|---|
| `account_id` | INTEGER | Unique identifier (PK) |
| `is_locked` | BOOLEAN | Whether the account is locked |

**Dataset Creation Query (Backend)**

```sql
CREATE TABLE locked_accounts_v (
    account_id INTEGER PRIMARY KEY,
    is_locked BOOLEAN
);

INSERT INTO locked_accounts_v VALUES (1, TRUE), (2, FALSE);

CREATE FUNCTION prevent_locked_delete() RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF OLD.is_locked THEN
        RAISE EXCEPTION 'Cannot delete a locked account';
    END IF;
    RETURN OLD;
END;
$$;

CREATE TRIGGER trg_prevent_locked_delete
BEFORE DELETE ON locked_accounts_v
FOR EACH ROW EXECUTE FUNCTION prevent_locked_delete();
```

**Statement to Analyze**

```sql
DELETE FROM locked_accounts_v WHERE account_id = 1;
```

**Your Task:** Account 1 has `is_locked = TRUE`. Predict what happens when this `DELETE` runs.

**Answer**

```
ERROR:  Cannot delete a locked account
CONTEXT:  PL/pgSQL function prevent_locked_delete() line 4 at RAISE
```

**Why:** The `BEFORE DELETE` trigger runs `prevent_locked_delete()` before the deletion is allowed to proceed, checking `OLD.is_locked` (`OLD` refers to the row *about to be* deleted, the trigger's counterpart to `NEW` in Q28). Since account 1 is locked, the trigger's `RAISE EXCEPTION` fires, and the entire statement is aborted — the row is never actually deleted. This is a genuinely powerful pattern: a trigger can enforce a business rule ("locked accounts are undeletable") at the database level itself, so the rule holds no matter what application, script, or careless manual query attempts the delete — there's no way to bypass it by simply forgetting to check `is_locked` in one particular piece of code.

**Answer:** The trigger itself is a legitimate and often-correct choice — enforcing a business rule at the database level guarantees it holds regardless of which application or script touches the table, exactly the value demonstrated in Q29. The real problem the new engineer ran into isn't the trigger's *existence*, it's its *invisibility*: triggers are easy to miss during code review (they don't appear anywhere near the `DELETE` statement that fails because of them) and easy to forget about entirely once written, which turns a deliberate safeguard into a confusing, undocumented trap for the next person. The fix isn't removing the trigger — it's making it discoverable: a clear, consistent naming convention (`trg_prevent_locked_delete` already does this reasonably well by naming its purpose), schema documentation that calls out which tables have trigger-enforced rules, and — ideally — an error message specific and clear enough (as `prevent_locked_delete()`'s `RAISE EXCEPTION 'Cannot delete a locked account'` already is) that anyone hitting it immediately understands *why*, without needing to go spelunking through the schema to find the trigger that caused it.
